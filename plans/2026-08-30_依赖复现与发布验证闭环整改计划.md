## 背景

本机 uv `0.11.32` 读取现有 `uv.lock` 时要求更新，说明仓库没有固定生成锁文件所需的 uv CLI 版本，当前锁文件元数据与工具行为已经漂移。根 README 的三端能力清单也落后于实际目录。镜像发布目前只要求同一 Commit SHA 的四个轻量 Push 工作流成功，没有要求 pytest、Vitest、production build 和 Playwright 的完整验证证据。

## 目标

- 在 Backend 配置和所有使用 uv 的 GitHub Actions 中固定一致的 uv CLI 版本。
- 使用固定版本正式重建 `uv.lock`，并让 `uv sync --locked` 可复现通过。
- 按实际公开模块修正 README 的 Backend、Admin 和 Web 能力清单。
- 将现有人工 Browser E2E 工作流扩展为人工完整验证工作流。
- 完整验证成功后生成绑定目标 Commit SHA 和 Workflow Run 的 GitHub Artifact。
- `Publish Images` 在构建镜像前通过 GitHub API 校验同一 Commit SHA 的成功完整验证 Artifact。
- 同步测试策略、Actions 手册、发布手册、uv 指南、Changelog 和计划索引。

## 非目标

- 不改变日常 Push、Pull Request 和定时 CI 的轻量验证范围。
- 不自动触发 pytest、Vitest、production build、Playwright 或真实数据库迁移。
- 不在本地执行本轮未被用户逐项点名的重型验证。
- 不修改产品业务功能、API 契约、数据库结构和三端 UI。
- 不提交、推送、创建 Pull Request、发布镜像或部署生产环境。

## 现状分析

- `apps/backend/pyproject.toml` 只配置了相对 `exclude-newer`，没有通过 `required-version` 约束 uv CLI。
- Backend、E2E 和 Security 工作流固定了 `setup-uv` Action 提交，但没有固定 Action 安装的 uv CLI 版本。
- 当前 `uv.lock` 在 uv `0.11.32` 下产生元数据更新，修改前的锁文件无法通过 `uv sync --locked`。
- README 未列出已经存在的 Backend `assets`、`settings`，Admin `assets`、`settings`、`account`、`welcome` 和 Web `site` 能力。
- `ci-e2e.yml` 已人工执行前端 production build 和 Playwright，但没有执行 Backend pytest 与 Admin/Web Vitest，也没有产生可供发布流程核验的持久证据。
- `publish-images.yml` 只核验四个自动轻量 Push 工作流，Browser E2E 成功与否不影响发布资格。
- 首次远端完整验证 Run `33264016191` 针对合并提交 `669f9c05b38e0402b5150ea3052f6d53ecbf5bf9` 执行，Backend pytest 因工作流只允许 `127.0.0.1`，而 6 个既有测试使用 `localhost` Origin，全部在业务断言前返回 `CSRF_REJECTED`。
- 首次 Run 共 236 项 Backend 测试通过、6 项失败，覆盖率降至 `77.54%`；后续 Vitest、production build、Playwright 和 Artifact 上传均因前置失败未执行。

## 方案设计

1. 在 `[tool.uv]` 中设置精确 `required-version`，并在所有 `setup-uv` 步骤中设置同一 `version` 输入。
2. 使用该版本运行正式锁定命令更新现有 `uv.lock`，再以 `uv sync --locked` 验证锁文件与配置一致。
3. 以实际领域和 Feature 公开目录为事实来源修正 README，仅补齐遗漏项，不删减既有说明。
4. 扩展人工工作流，要求输入完整 Commit SHA，校验目标提交属于默认分支，并分别运行 Backend pytest、Admin/Web Vitest 与 production build、真实浏览器跨栈 E2E。
5. 只有全部重型验证 Job 成功时才上传包含 Commit SHA、Workflow Run ID 和验证集合的 Artifact；Artifact 名称同时包含目标 SHA。
6. 镜像发布在现有轻量 Push 门禁之后查找成功的人工完整验证 Run，下载未过期 Artifact 并逐字段核验目标 SHA 和验证集合；找不到可信证据时停止发布。
7. 工作流仍由人工分别触发，完整验证证据不会扩大镜像发布或生产部署授权。
8. 完整验证环境同时允许真实 E2E 使用的 `127.0.0.1` 与 Backend API 测试夹具使用的 `localhost`，继续保持 Web 与 Admin 端口隔离和精确 Origin 白名单。

## 风险与回滚

- 精确固定 uv 会阻止开发者使用其他版本生成锁文件；升级 uv 时必须在专项变更中同步 Backend 配置、工作流和锁文件。
- 完整验证工作流耗时与 Runner 消耗会上升；它保持人工触发，不进入普通 Push、Pull Request 或定时链路。
- 测试 Runner 同时允许两种本机回环主机名会增加测试环境的允许 Origin 数量，但不引入通配符、外部域名或生产配置变化；回滚时恢复原两行环境变量即可。
- GitHub Artifact 有保留期；过期后需要为同一 Commit SHA 重新人工运行完整验证，发布流程不能复用过期证据。
- GitHub API 或 Artifact 下载故障会阻止镜像发布；保持失败关闭并由操作人员在平台恢复后重试。
- 工作流错误可通过回退本计划的配置和文档修改恢复，已存在的历史 Workflow Run 与 Artifact 不会被本地回滚删除。

## 实施结果

1. 在 Backend `[tool.uv]` 中增加 `required-version = "==0.11.32"`，并为 Backend CI、完整验证和 Security 的 `setup-uv` 显式设置同一版本；使用该版本重新解析 `uv.lock` 后，依赖集合回归当前仓库锁定结果，`uv sync --locked --python 3.14` 通过且锁文件无剩余 Git 漂移。
2. README 按实际目录补齐 Backend `assets`、`settings`，Admin `assets`、`settings`、`account`、`welcome`，Web `site`、`user`，没有删除既有母版说明。
3. `CI - Browser E2E` 已扩展为人工 `CI - Full Validation`：只接受完整小写 Commit SHA，从默认分支启动并验证目标属于默认分支历史，依次执行 Alembic 隔离迁移、Backend pytest、Admin/Web Vitest、production build 和 Chromium Playwright。
4. 完整验证只有在全部重型步骤成功后才上传保留 30 天的 `full-validation-<完整 SHA>` Artifact，清单包含 Commit SHA、Workflow Run ID、Run Attempt 和完整验证集合。
5. `Publish Images` 在镜像构建前通过 GitHub Actions API 查找同 SHA 未过期 Artifact，核验所属 Run 的触发事件、默认分支、成功结论和工作流路径，再调用结构化 PowerShell 门禁检查全部字段；缺失、重复、额外或不一致字段均失败关闭。
6. 新增证据门禁正反例，覆盖有效证据、SHA 不一致、Run 不一致、字段缺失、字段重复、额外字段和非法 Run Attempt，并纳入根 `check:guards`。
7. 测试策略、uv 指南、Actions 手册、发布回滚手册、Pull Request 模板、Changelog、根索引和计划索引已同步；项目卫生按 `project-hygiene` 里程碑模式完成。
8. Backend Ruff、格式、Mypy、Import Linter、源码编译、应用导入、OpenAPI 导出与 API Client 漂移检查通过；Admin/Web typecheck、lint 通过；YAML、JSON、uv 版本一致性、工作流关键不变量、Markdown、文档、工作区、依赖、模块边界、生产配置和全部治理夹具通过。
9. 本轮按授权边界未在本地执行 pytest、Vitest、production build、Playwright、浏览器自动化和真实数据库迁移，也未触发 GitHub 完整验证、镜像发布或生产部署。18 个本轮生成的 `__pycache__` 已清理，3000 和 3001 端口均未监听。
10. 本地检查点 `094caede24fadf2657873c1b50a426fadd06a2a9` 已推送至 `codex/full-validation-evidence`；PR [#22](https://github.com/jinmozhe/pinjie-fullstack-base/pull/22) 的 13 项必需检查全部通过并按 rebase 方式合并，远端 `main` 生成提交 `669f9c05b38e0402b5150ea3052f6d53ecbf5bf9`。
