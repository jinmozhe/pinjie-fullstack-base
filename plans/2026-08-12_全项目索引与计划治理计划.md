## 2. 背景

本仓库是可派生为 CMS、电商、博客和企业站等业务仓库的通用全栈母版。现有根 `AGENTS.md`、三个应用级 `AGENTS.md`、`docs/README.md` 和 `plans/README.md` 已分别承担规则、文档和计划规范，但缺少一个能够在任务开始时统一说明项目身份、当前阶段、三端开发目标、权威来源和全部计划文档的全项目索引。

FastNav 的 `PROJECT_INDEX.md` 证明了集中导航规则、文档和计划的价值。本项目需要吸收其任务路由和状态总览能力，同时保持 Monorepo 母版边界，避免复制文档正文或把 Backend、Admin、Web 拆成彼此孤立的计划体系。

## 3. 目标

1. 建立 `PROJECT_INDEX.md` 作为全项目任务导航和当前事实入口。
2. 明确 `plans/` 属于整个全栈 Monorepo，计划以完整业务能力或工程目标为单位。
3. 在索引中分别展示 Backend、Admin、Web 及跨栈范围的当前开发目标。
4. 建立计划永久保护规则，确保现存计划原文和索引记录始终保留。
5. 明确总索引、计划规范、文档索引、ADR 和 Changelog 的职责边界。
6. 为未来 CMS 等派生项目提供项目身份、母版基线和业务范围登记方式。

## 4. 非目标

1. 不修改 Backend、Admin、Web 或共享包的运行代码。
2. 不新增 `plans/active/`、`plans/archive/` 或 `plans/plans-index.md`。
3. 不创建 `.agents/AGENTS.md`，也不改变现有 Antigravity 桥接机制。
4. 不删除、移动或重命名任何现有计划文档。
5. 不生成依赖锁文件、OpenAPI 契约或 API Client。

## 5. 现状分析

1. 根 `AGENTS.md` 已定义仓库级规则和三个应用的作用域路由。
2. `.agents/rules/` 仅负责 Antigravity 加载桥接，符合 ADR 0002。
3. `docs/README.md` 已是 `docs/` 的完整专项索引。
4. `plans/README.md` 只定义计划格式和确认门槛，尚未明确全栈归属、状态和永久保护。
5. 当前没有 `PROJECT_INDEX.md` 和 `CHANGELOG.md`。
6. Backend、Admin、Web 目前均处于工程骨架阶段，尚无运行源码和活动功能计划。

## 6. 方案设计

1. 新建 `PROJECT_INDEX.md`，包含项目身份、执行入口、当前开发计划、全部计划登记、系统状态、权威来源、派生项目入口和维护规则。
2. 根 `AGENTS.md` 强制所有任务先读取总索引，实现类任务继续读取 `plans/README.md` 和匹配计划。
3. `plans/README.md` 定义全栈计划归属、四状态模型、固定章节、全栈影响矩阵、完成条件和计划保护红线。
4. 新建 ADR 0004 固化总索引和计划生命周期决策，不修改 ADR 0002。
5. 新建 `CHANGELOG.md` 记录已经交付但尚未发布的项目治理能力。
6. 同步根 README、文档索引和仓库结构说明。

## 10. 风险与回滚

1. 风险：总索引复制过多专项内容，后续形成多份事实来源。控制方式是总索引只记录入口、当前状态和一句话用途。
2. 风险：计划状态和索引状态不同步。控制方式是计划状态变化必须在同一次修改中同步总索引。
3. 风险：计划文件被自动整理删除。控制方式是把禁止 AI 删除、移动、重命名和替换计划写入根规则与计划规范。
4. 回滚：逐个回退本计划列出的治理文件修改；本次不涉及运行代码、数据库和外部系统。
