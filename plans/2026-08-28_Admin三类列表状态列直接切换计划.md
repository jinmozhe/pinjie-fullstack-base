## 背景

Admin 的管理员列表“身份”列已经使用可点击 Tag 直接切换超级管理员身份，但 `/admins`、`/users` 和 `/roles` 的“状态”列仍为只读 Tag。管理员和用户需要从操作列或更多菜单切换状态，角色只有编辑或批量状态入口。用户确认三页状态列均增加与“身份”列一致的直接切换能力。

## 目标

- `/admins`、`/users`、`/roles` 的正常列表状态 Tag 可直接点击切换。
- 三页使用一致的 Tag 按钮、Tooltip、ARIA 文案和单行紧凑布局。
- 单行状态切换显示准确的行级 loading，避免重复提交。
- 无更新权限时只显示只读 Tag，不渲染可点击按钮。
- 管理员本人状态继续禁止从当前管理页面修改，并显示原因。
- 用户回收站继续展示生命周期状态，不提供状态切换。
- 保留现有操作菜单、操作列和批量状态入口，避免弱化既有功能。

## 非目标

- 不修改 Backend 状态端点、权限代码、数据库和 OpenAPI。
- 不删除管理员更多菜单和用户操作列中的原有启停入口。
- 不改变批量启停、用户回收站、管理员身份和角色编辑逻辑。
- 不增加确认弹窗或密码二次确认。

## 现状分析

- 管理员已有 `statusMutation` 调用独立状态端点，并限制当前管理员修改自己。
- 用户操作列直接调用独立状态端点，需要收敛为可复用 mutation 以支持行级 loading。
- 角色没有独立单条状态端点，但现有角色更新端点支持提交名称、说明和 `is_active`，可安全复用。
- 三页状态显示均使用“正常/停用”Tag，适合提取共享的内联状态切换组件。
- 服务端继续负责管理员状态保护、资源权限、CSRF、事务和审计，前端限制只用于交互体验。

## 方案设计

1. 新增共享 `StatusToggleTag`，统一正常/停用 Tag、点击按钮、Tooltip、ARIA、只读和 loading 状态。
2. 管理员状态列复用现有 `statusMutation`；当前管理员和无更新权限时保持只读。
3. 用户新增单条 `statusMutation`，状态列和原操作列启停入口共用同一 mutation。
4. 用户回收站状态列继续显示“可恢复/不可恢复”，不接入状态切换。
5. 角色新增单条状态 mutation，通过现有 `updateRole` 提交当前名称、说明和目标状态。
6. 保留三页批量 mutation 和原操作入口，行级 mutation pending 时只锁定对应行状态按钮。
7. 更新测试源码，断言三页状态列请求体、权限只读和管理员本人保护。

## 风险与回滚

- 风险：状态列和原操作入口同时提交，造成重复请求。
- 控制：两处共用同一 mutation，行级 pending 时禁用对应入口。
- 风险：管理员本人通过状态列停用自己。
- 控制：沿用当前页面的本人限制，只渲染带原因 Tooltip 的只读 Tag；服务端继续最终保护。
- 风险：角色状态更新遗漏名称或说明。
- 控制：状态 mutation 从当前行提交完整现有字段，只改变 `is_active`。
- 风险：无权限用户仍可点击状态 Tag。
- 控制：共享组件在非交互模式只渲染 Tag，不创建按钮，测试源码覆盖。
- 回滚：恢复三页状态列只读 Tag，移除共享组件和单行角色 mutation，不涉及后端或数据回滚。
