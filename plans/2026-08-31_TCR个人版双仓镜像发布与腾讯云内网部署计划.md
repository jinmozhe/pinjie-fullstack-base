# TCR 个人版双仓镜像发布与腾讯云内网部署计划

## 当前状态和结果

- 状态：实施中
- 结果：不适用
- 实施边界：保留 GHCR 现有不可变发布与供应链证据，增加免费的腾讯云 TCR 个人版作为腾讯云服务器的运行镜像分发源，并让生产部署继续固定完整镜像 digest。
- 实施授权：用户已于 2026-08-31 确认 `pinjie-fullstack-base` 命名空间、三个私有仓库、`tcr-publisher` 发布身份及 GitHub `image-publishing` Environment 配置，并明确授权第一阶段修改发布工作流以及执行一次 TCR 测试构建与镜像推送；Git 提交、代码推送、正式镜像发布、生产配置和生产部署继续分别授权。

## 关联需求

- `BASE-OPS-005`：保留 Backend、Web 和 Admin 三张独立生产镜像及不包含真实密钥的容器交付路径。
- `BASE-OPS-006`：让腾讯云服务器能够从可验证的镜像来源执行安全升级和失败恢复。
- `BASE-OPS-007`：继续分离 CI、完整验证、镜像发布和生产部署，新增 TCR 不扩大任何既有授权。
- `BASE-OPS-008`：TCR 前置条件、发布、digest 核验或拉取失败时必须失败关闭。
- `BASE-OPS-009`：保留完整 Commit SHA、SBOM、构建来源证明和固定 digest 的不可变发布链。
- `BASE-OPS-010`：继续把当前 Compose 定位为单机可恢复部署，不因使用云镜像仓库宣称高可用。
- `BASE-SEC-001`：TCR 用户名、固定密码和其他访问凭证不得写入仓库、日志或镜像。
- `BASE-SEC-003`：工作流、SSH 和部署摘要不得输出 TCR 密码或完整登录指令。
- `BASE-SEC-004`：镜像发布、生产部署、回滚和凭证轮换继续分别授权并具有停止条件。
- `BASE-SEC-005`：GHCR 继续承载镜像扫描、SBOM 和构建来源证明，TCR 分发不能绕过供应链门禁。
- `BASE-SEC-006`：使用 GitHub Workflow、Environment 和部署记录追踪发布与部署；明确记录 TCR 个人版缺少云厂商操作审计的剩余风险。
- `BASE-QUAL-001`：禁止把 TCR 个人版表述为具备 SLA、专属实例或完整生产保障。
- `BASE-QUAL-004`：双仓 digest 不一致、标签冲突、凭证失败或内网路径不成立时显式停止。
- `BASE-DOC-001`：同步项目阶段、活动计划和权威入口。
- `BASE-DOC-003`：在既有不可变发布 ADR 中记录双仓角色和 TCR 个人版限制。
- `BASE-DOC-004`：使用同一份全栈计划追踪工作流、腾讯云接入、部署和文档变化。
- `BASE-DOC-006`：让发布、部署、1Panel 和容器运行文档与实际镜像来源保持一致。

## 背景

当前 `Publish Images` 只把 Backend、Web 和 Admin 三张镜像发布到 GHCR，`Deploy Production` 也只校验和使用 GHCR 引用。生产服务器位于腾讯云，直接从 GHCR 拉取镜像可能受跨境或跨运营商公网链路影响，导致首次部署和回滚下载速度不稳定。

用户已选择免费的腾讯云容器镜像服务 TCR 个人版。腾讯云官方文档当前说明，个人版限额免费、不承诺 SLA，属于共享服务；中国大陆主要部署在广州，并支持北京、上海、成都等部分地域跨地域内网访问，实际支持范围以控制台为准。个人版还缺少企业版提供的 VPC 访问控制、镜像版本不可变、漏洞扫描、专属实例和操作审计。

本方案把 GHCR 保留为发布证据和异地副本，把 TCR 个人版作为腾讯云运行环境的分发镜像源。免费服务的限制必须由双仓校验、固定 digest、GitHub 审批记录和显式故障处理补偿，不能写成与 TCR 企业版等价的生产保障。

## 目标

- 保留 GHCR 现有镜像、Trivy、SBOM、provenance、完整 Commit SHA 和 digest 证据链。
- 使用同一次 BuildKit 构建把同一候选镜像内容按 digest 推送到 GHCR 与 TCR，禁止为 TCR 重新构建第二份镜像。
- 逐张验证 GHCR 与 TCR 的 manifest digest 完全一致，不一致时停止发布。
- 三张镜像全部验证成功后，才在两个仓库创建 `sha-<完整 Commit SHA>` 标签。
- TCR 个人版没有服务端不可变保护时，由工作流执行写前冲突检查、写后 digest 复核和部署前再次复核。
- 生产 Compose 使用 `ccr.ccs.tencentyun.com/<命名空间>/<镜像>@sha256:<digest>` 拉取三张镜像。
- 腾讯云服务器仅在个人版支持的内网地域范围内采用 TCR 作为生产拉取源，并通过实际拉取验证速度收益。
- TCR 故障时保持显式失败；使用 GHCR 执行应急部署必须重新取得部署授权并核对同一 digest。
- 同步 ADR、GitHub Actions、发布回滚、容器运行和 1Panel 运维文档。

## 非目标

- 不购买或启用 TCR 企业版，不引入企业版费用、SLA 或 VPC 专属访问能力。
- 不使用阿里云 ACR、Docker Hub 或自建 Harbor 代替本次 TCR 个人版方案。
- 不删除、替换或弱化 GHCR 现有发布、扫描、SBOM、provenance 和回滚能力。
- 不创建 `latest`、分支标签或缺失版本回退，也不允许生产按可变标签部署。
- 不自动从 TCR 降级到 GHCR，避免网络或权限故障被静默掩盖。
- 不修改 Backend、Admin、Web 业务源码、OpenAPI、API Client、数据库模型或迁移。
- 不在生产服务器构建镜像，也不通过 SCP 传输镜像 tar 文件。
- 不把真实 TCR 凭证写入 `.env.example`、仓库文件、Workflow Summary、命令行日志或部署记录。
- 本计划创建阶段不修改工作流，不配置云端资源，不发布镜像，不部署生产。

## 现状分析

- `.github/workflows/publish-images.yml` 使用 Buildx 按内容 digest 向 GHCR 推送候选镜像，随后执行 Trivy、GitHub provenance attestation 和 digest 证据上传，最终才创建不可变 SHA 标签。
- `.github/workflows/deploy-production.yml` 在 GitHub Runner 登录 GHCR，验证 `sha-<commit>` 与输入 digest 一致，再把 GHCR 完整 digest 引用传入远程 Compose。
- `compose.prod.yml` 已通过必填的 `BACKEND_IMAGE`、`WEB_IMAGE` 和 `ADMIN_IMAGE` 接受任意完整镜像引用，无需修改服务定义。
- TCR 个人版固定使用 `ccr.ccs.tencentyun.com`，命名空间全局唯一，现有三个单层镜像名称符合个人版仓库命名边界。
- TCR 个人版缺少服务端版本不可变。工作流可以拒绝已存在的冲突标签并在写入后复核，但无法阻止具备仓库写权限的人员在工作流外覆盖标签。
- TCR 个人版缺少漏洞扫描和 OCI Artifact 托管保证。GHCR 必须继续作为 Trivy、SBOM 和 provenance 的权威证据来源。
- TCR 个人版缺少云厂商操作审计。GitHub Workflow、Environment 审批、Artifact 和生产部署记录可以追踪受控发布流程，但不能证明 TCR 控制台外部操作从未发生。
- TCR 个人版使用固定 Registry 密码。实施前必须核验是否可以通过 CAM 子账号把发布写权限与生产只读权限分离；无法实现时不得直接把主账号或高权限凭证接入生产流程。
- 当前生产远程脚本没有登录 TCR。私有仓库拉取需要在服务器安全配置只读 Registry 凭证，或者通过受保护的生产 Environment 注入短期可控凭证。

## 方案设计

### 1. 双仓职责

| 仓库 | 职责 | 部署使用 | 保障边界 |
| --- | --- | --- | --- |
| GHCR | 权威发布证据、SBOM、provenance、Trivy 扫描目标、异地副本 | TCR 故障时经独立授权应急使用 | 保留现有 GitHub 权限和不可变 SHA 标签门禁 |
| TCR 个人版 | 腾讯云服务器的运行镜像分发源 | 默认按完整 digest 拉取 | 限额免费、共享服务、无 SLA、无服务端不可变和操作审计 |

两个仓库必须指向同一构建内容。TCR 只承担分发角色，不能取代 GHCR 的供应链证据。

### 2. 腾讯云资源与凭证前置

1. 在腾讯云控制台确认生产 CVM 地域是否属于 TCR 个人版支持的内网访问范围。
2. 初始化 TCR 个人版固定 Registry 密码，创建一个全局唯一的私有命名空间，并保留三个现有单层仓库名：
   - `pinjie-fullstack-backend`
   - `pinjie-fullstack-web`
   - `pinjie-fullstack-admin`
3. 优先创建两个独立 CAM 子账号或等价 Registry 身份：
   - 发布身份：只允许向目标命名空间推送和读取。
   - 生产身份：只允许读取目标命名空间。
4. 若个人版无法实现上述最小权限隔离，记录实际权限范围并取得用户专项确认，禁止使用腾讯云控制台登录密码或主账号高权限密钥替代 Registry 凭证。
5. GitHub 创建受保护的 `image-publishing` Environment，保存发布凭证；现有 `production` Environment 只保存部署校验所需的只读凭证。
6. 非敏感配置使用 GitHub Environment Variables：
   - `TCR_REGISTRY=ccr.ccs.tencentyun.com`
   - `TCR_NAMESPACE=<全局唯一命名空间>`
7. 敏感配置使用 GitHub Environment Secrets：
   - `TCR_PUBLISH_USERNAME`
   - `TCR_PUBLISH_PASSWORD`
   - `TCR_READ_USERNAME`
   - `TCR_READ_PASSWORD`
8. 生产服务器的 Docker 凭证目录必须由部署用户独占并限制文件权限。凭证轮换步骤进入 1Panel 运维手册，任何命令不得开启 shell trace 或输出密码。

### 3. OCI 与 digest 兼容性门禁

TCR 个人版没有 OCI Artifact 托管保证，现有 Buildx 输出包含 `provenance: mode=max` 和 `sbom: true`。正式修改发布链路前必须验证个人版能否接受同一 BuildKit 镜像索引，并保持与 GHCR 完全相同的 manifest digest。

兼容性验证必须满足：

1. 单次 BuildKit 构建配置两个 Registry 名称，并继续使用 `push-by-digest=true`。
2. GHCR 与 TCR 均可按输出 digest 执行 `imagetools inspect`。
3. 两边顶层 manifest digest 完全一致。
4. GHCR 的 SBOM、provenance 和 GitHub attestation 仍可生成并验证。
5. TCR 中的运行平台镜像可以由腾讯云 CVM 按完整 digest 拉取。

任一条件失败时停止实施，不自动改为二次构建、重写 manifest 或维护两套未经确认的 digest。确需双 digest 映射时，必须重新评审 ADR、发布证据结构和部署输入，并取得用户确认。

### 4. 镜像发布工作流

在 `.github/workflows/publish-images.yml` 中保持现有 validate、publish 和 finalize 三阶段，并增加以下门禁：

1. `publish` Job 绑定受保护的 `image-publishing` Environment。
2. 分别登录 GHCR 与 TCR，凭证只存在于对应 Job。
3. 每个矩阵项只执行一次 `docker/build-push-action`，镜像 exporter 同时包含 GHCR 与 TCR 目标仓库，并继续按 digest 推送无发布标签的候选内容。
4. 从构建输出取得候选 digest，分别解析 GHCR 和 TCR 候选内容，要求两边均存在且 digest 相同。
5. Trivy 继续扫描 GHCR 的精确 digest；相同 digest 证明 TCR 运行内容一致，不重复执行第二次漏洞扫描。
6. GitHub provenance attestation 继续绑定 GHCR subject；TCR 个人版缺少 OCI Artifact 保证，不将 TCR attestation 存在性作为假定事实。
7. 每个矩阵任务生成结构化证据，至少包含 Commit SHA、应用键、GHCR 仓库、TCR 仓库、GHCR digest、TCR digest 和 Workflow Run ID。
8. 新增结构化 PowerShell 校验器及负向夹具，拒绝缺失字段、额外字段、应用键错配、Commit SHA 错配、digest 格式错误和双仓 digest 不一致。
9. 三个矩阵任务全部成功后，`finalize` 先检查 GHCR 与 TCR 的全部 `sha-<commit>` 目标。任一现有标签指向不同 digest 时，整个发布失败。
10. 创建两个仓库的 SHA 标签后再次读取并核对 digest。工作流只在三张镜像的两个仓库全部核验成功时返回成功。
11. Workflow Summary 同时记录 GHCR 与 TCR 的完整 digest 引用，不输出凭证，不写入项目文档。

TCR 个人版缺少跨仓库事务。标签创建阶段可能出现部分可见状态，`Deploy Production` 必须要求整个 `Publish Images` Run 成功，不能只根据某个标签存在判断可部署。

### 5. 生产部署工作流

在 `.github/workflows/deploy-production.yml` 中保持完整 Commit SHA、三个 digest、GitHub `production` Environment 和并发锁，并调整镜像来源：

1. GitHub Runner 分别登录 GHCR 与 TCR。
2. 对每个应用同时解析 GHCR 和 TCR 的 `sha-<commit>` 标签，要求两边都与人工输入 digest 完全一致。
3. 远程 Compose 使用 TCR 完整 digest 引用，禁止写入 SHA 标签或其他可变标签。
4. 生产服务器在拉取前验证 TCR 登录状态；认证失败、manifest 不存在或网络不可达时停止部署。
5. 现有 Compose 哈希、临时镜像变量文件、`docker compose config --quiet`、拉取、等待和运行容器镜像引用核对继续保留。
6. `.deployment-version` 和 Workflow Summary 记录 Commit SHA、Compose 哈希、GHCR 证据引用与 TCR 运行引用。
7. TCR 故障时不自动切换 GHCR。操作人员可以在确认同一 digest、网络条件和回滚边界后，使用独立授权的部署执行 GHCR 应急引用。

### 6. 免费版运行边界

- 只有腾讯云控制台确认目标地域支持个人版内网访问，并且 CVM 实测拉取成功后，才能把 TCR 个人版描述为当前服务器的内网分发源。
- 无 SLA 意味着 TCR 故障可能阻止新部署和回滚镜像下载。运行中的容器不依赖 Registry 持续在线，但节点重建和镜像缓存失效会受到影响。
- GHCR 保留相同 digest 的异地副本。应急切换保持人工、显式、可审计，不能静默降级。
- 个人版配额和共享性能可能变化。实施和每次正式发布前应核对控制台状态，镜像保留策略必须保护当前生产和至少一个已验证回滚版本。
- TCR 个人版不能满足企业版的专属实例、VPC 网络控制、服务端不可变、云厂商审计和 SLA 能力。本方案只在用户接受这些约束的前提下使用。

## 实施顺序

1. 用户确认第一阶段发布兼容性边界，计划进入实施中；生产地域和只读身份继续作为部署阶段阻断条件。
2. 重新核对腾讯云官方文档和控制台，确认生产 CVM 地域、个人版内网支持范围、命名空间可用性和凭证权限模型。
3. 用户在腾讯云和 GitHub 中创建 TCR 个人版资源、私有命名空间、最小权限身份、Environment Variables 和 Secrets；真实值不进入对话记录或仓库。
4. 取得单独的远端兼容性验证授权后，验证 Buildx 双 Registry `push-by-digest`、SBOM、provenance 和双仓 digest 一致性。
5. 修改 `publish-images.yml`，实现单次构建双仓候选推送、结构化证据和双仓 SHA 标签 finalize。
6. 新增双仓证据校验脚本与成功、缺失、错配、额外字段、digest 冲突等负向夹具，并接入现有治理门禁。
7. 修改 `deploy-production.yml`，同时校验 GHCR 与 TCR，向远程 Compose 传递 TCR 完整 digest 引用。
8. 在生产服务器配置只读 TCR Registry 凭证，验证权限、文件模式和轮换步骤；该操作需要独立生产配置授权。
9. 同步 ADR 0008、Actions 手册、发布回滚手册、容器构建运行手册、1Panel 运维手册和 Changelog。
10. 运行本地轻量治理门禁，复读全部差异并清理验证产物。
11. 取得镜像发布授权后，对同一完整 Commit SHA 执行完整验证与双仓发布，核对三个应用的双仓 digest。
12. 在目标 CVM 使用干净镜像缓存或受控测试镜像验证 TCR 拉取成功和速度收益；生产部署仍需另行取得授权。
13. 回写实际实施、验证结果、限制和剩余问题，结束计划并同步两个索引。

## 风险与回滚

- **目标地域不支持个人版内网访问**：停止把 TCR 用作生产拉取源，保留现有 GHCR 流程并重新评估企业版或其他明确方案，禁止把公网拉取表述为内网优化成功。
- **TCR 个人版无 SLA**：新部署、节点重建和回滚拉取可能被服务故障阻塞。运行中容器保持现状；应急使用 GHCR 必须经过独立授权和同 digest 核验。
- **TCR 无服务端版本不可变**：具备写权限的身份可能覆盖 SHA 标签。部署始终按 digest，并在发布前后和部署前核验标签；同时限制写凭证持有者。
- **TCR 无操作审计**：GitHub 记录只能覆盖受控 Workflow，无法证明控制台外操作不存在。GHCR 继续作为供应链证据来源，TCR 权限必须最小化。
- **凭证权限无法分离**：若个人版只能提供范围过大的固定密码，停止生产接入并由用户决定是否接受风险或调整方案。
- **OCI、SBOM 或 provenance 不兼容**：若 TCR 无法接受与 GHCR 相同的镜像索引或 digest，停止实施并保留 GHCR。不得自动重建第二份镜像或弱化证据链。
- **双仓标签部分成功**：发布 Workflow 保持失败，部署 Workflow 拒绝使用；修复后仅允许对同一 Commit SHA 和 digest 幂等重试。
- **个人版配额耗尽或共享性能波动**：保护生产与回滚标签，定期检查版本配额。删除镜像属于独立高风险操作，必须核对 digest 和恢复来源后授权执行。
- **工作流回滚**：在未部署 TCR 镜像前，可通过普通反向提交恢复 GHCR-only 工作流。已经发布的 TCR 镜像不自动删除，避免破坏追溯和回滚来源。
- **生产回滚**：继续选择上一组已验证 digest，并确认数据库兼容。镜像仓库切换和应用回滚分别记录，不重新构建旧代码。
