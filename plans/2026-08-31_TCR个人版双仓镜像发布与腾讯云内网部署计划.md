## 背景

现有 `Publish Images` 已证明同一次 BuildKit 构建可以向 GHCR 和 TCR 个人版推送相同 digest，但 GitHub 托管 Runner 位于境外。实测发布 Run `33363036784` 总耗时约 34 分 07 秒，其中镜像构建只需 17 至 61 秒，向 TCR 推送 Backend 和 Web 分别约 19 分 08 秒和 30 分 48 秒。跨境上传镜像层是主要耗时。

同一 Commit 的 Full Validation Run `33362189121` 耗时 12 分 13 秒，代码验证可以继续留在 GitHub。把镜像构建移动到腾讯侧，只需要跨境同步体积较小的 Git 对象，镜像层在国内构建并直接推送 TCR，可以消除当前主要瓶颈。

腾讯云旧的 TCR 个人版镜像构建基于 CODING DevOps。腾讯云当前购买指南说明 CODING 标准版已于 2025-09-01 下线、2025-09-30 停止新购，并计划于 2028-09-30 停止服务，因此不作为新的长期基础设施。腾讯当前主推 CNB 云原生构建，社区版提供每个顶级组织每月 160 核时免费构建额度；未绑定预算且免费额度不足时任务会停止，可以避免自动产生费用。

## 目标

- GitHub 保持唯一权威代码仓库，继续执行四个轻量 Push 门禁和人工授权的 Full Validation。
- GitHub 只在指定完整 Commit SHA 通过规定门禁后，将同一 Git Commit 单向推送到 CNB 发布分支。
- CNB 使用根目录 `.cnb.yml` 构建 Backend、Web 和 Admin 三张镜像，并启用持久构建缓存。
- CNB 对三张镜像执行 Trivy 高危漏洞阻断，生成 SBOM、构建来源和结构化发布清单。
- CNB 只向 TCR 个人版推送候选镜像和 `sha-<完整 Commit SHA>` 标签，不再把 GHCR 作为每次发布的必需目标。
- 生产部署后续只使用 `ccr.ccs.tencentyun.com/pinjie-fullstack-base/<镜像>@sha256:<digest>`。
- 初始阶段不绑定 CNB 付费预算，免费额度耗尽时停止构建，避免意外费用。
- 迁移验证完成前保留当前双仓工作流和已发布镜像，具备明确回滚路径。

## 非目标

- 本阶段不购买 TCR 企业版、CNB 企业版或额外腾讯云构建服务器。
- 不使用已停止新购的 CODING DevOps 设计新流水线。
- 不在生产 CVM 上构建镜像，不安装 GitHub 自托管 Runner、Jenkins 或其他常驻构建服务。
- 不让 CNB 成为新的权威代码仓库，不在 CNB 直接开发或合并业务代码。
- 不创建 `latest`、分支标签或缺失版本回退，不让生产按可变标签部署。
- 不在迁移验证完成前删除 GHCR 镜像、TCR 镜像或 GitHub Environment；旧双仓 Workflow 设计保留在已核对 Commit 中作为可恢复基线，当前入口只保留一个可触发实现。
- 不修改 Backend、Admin、Web 业务源码、OpenAPI、API Client、数据库模型或迁移。
- 不在本计划文档中保存 CNB Token、TCR 密码、CAM 密钥或生产数据。
- 本阶段不配置生产服务器，不执行生产部署。

## 方案设计

### 1. 职责划分

| 系统 | 职责 | 不承担的职责 |
| --- | --- | --- |
| GitHub | 权威代码、PR、轻量 CI、Full Validation、固定 SHA 放行、向 CNB 单向交接源码 | 不构建或推送生产镜像 |
| CNB 社区版 | 接收固定 SHA、构建三张镜像、缓存、Trivy、SBOM、provenance、发布清单、推送 TCR | 不作为日常开发和代码评审主平台 |
| TCR 个人版 | 保存三张运行镜像并供腾讯云服务器拉取 | 不作为代码仓库，不提供企业版 SLA 和不可变保证 |
| 腾讯云 CVM | 按批准的完整 digest 拉取并运行镜像 | 不构建镜像，不持有发布写权限 |

### 2. GitHub 到 CNB 的源码交接

1. 保留现有完整 SHA 输入校验、默认分支祖先校验、四个 Push Workflow 成功校验和 Full Validation Artifact 校验。
2. 把镜像发布入口调整为源码交接，每次仍由完整 40 位 Commit SHA 驱动。
3. GitHub 使用独立受保护 Environment 保存 CNB 仓库写入凭证，Environment 只允许 `main`。
4. 校验通过后执行精确 Git Push，把指定 Commit SHA 更新到 CNB 的受控发布分支。
5. 禁止把未通过门禁的普通分支、Pull Request 代码或任意用户输入 URL 推送到 CNB。
6. 交接成功只表示源码进入 CNB，不代表镜像发布或生产部署成功。

建议使用以下配置名：

- Variable：`CNB_REPOSITORY_URL`
- Variable：`CNB_RELEASE_BRANCH=main`
- Variable：`CNB_PUSH_USERNAME=cnb`
- Secret：`CNB_PUSH_TOKEN`

### 3. CNB 仓库和密钥

1. CNB 私有仓库固定为 `pjwl/pinjie-fullstack-base`，发布分支固定为 `main`。
2. CNB 仓库只接收 GitHub 单向同步，不接受绕过 GitHub 门禁的直接业务提交。
3. 在 CNB 创建密钥仓库 `pjwl/pinjie-fullstack-base-secrets`，通过 Web 页面新增 `main/tcr-publish.yml`；现有固定密码由用户直接填写，不在对话中提供。
4. CNB 只需要 Docker Registry 登录信息，不需要 CAM `SecretId` 或 `SecretKey`。
5. 初始试运行不绑定腾讯云 CNB 预算，使用每月 160 核时免费额度；额度不足时允许构建显式停止。

CNB 需要以下配置名：

- `TCR_REGISTRY=ccr.ccs.tencentyun.com`
- `TCR_NAMESPACE=pinjie-fullstack-base`
- `TCR_PUBLISH_USERNAME`
- `TCR_PUBLISH_PASSWORD`

其中用户名和密码必须保存为 CNB Secret，不能写入 `.cnb.yml`。

密钥文件必须同时声明：

- `allow_slugs: ["pjwl/pinjie-fullstack-base"]`
- `allow_events: ["push"]`
- `allow_branches: ["main"]`

### 4. CNB 构建与发布

1. 在仓库根目录新增 `.cnb.yml`，只响应受控 `main` 分支 Push。
2. 使用固定版本或 digest 的构建环境和工具镜像，避免浮动工具链。
3. Backend、Web 和 Admin 使用现有 Dockerfile 构建，首次迁移保持三张镜像全部顺序构建，避免三条 Pipeline 共享 TCR 凭证和证据时增加跨 Pipeline 同步复杂度。
4. 三张镜像启用 TCR Registry BuildKit 缓存；后续有稳定耗时和额度数据后再评估并行与 Monorepo 按路径构建。
5. 候选镜像按内容 digest 推送 TCR，执行 Trivy `HIGH` 和 `CRITICAL` 漏洞阻断。
6. 使用 Buildx 生成 SBOM 与 provenance，并验证 TCR 可以按输出 digest 查询镜像。
7. 三张镜像全部成功后，才检查并创建 `sha-<完整 Commit SHA>` 标签。
8. 任一已有 SHA 标签指向不同 digest 时失败，不覆盖标签。
9. 写入标签后再次查询 digest，并生成结构化发布清单。
10. 任一镜像失败时整个发布失败，生产部署不得使用部分成功结果。

### 5. 发布证据

每次 CNB 发布至少保留以下字段：

- GitHub 完整 Commit SHA
- CNB 仓库和 Run 标识
- CNB 流水线配置版本
- Backend、Web、Admin 的 TCR 完整 digest 引用
- 三张镜像的 Trivy 结果
- 三张镜像的 SBOM 和 provenance 状态
- SHA 标签写前冲突检查和写后复核结果
- 构建开始时间、结束时间和总耗时

发布清单必须经过结构化校验。日志、Artifact 和摘要均不得包含 Token、Registry 密码或完整 Docker 登录命令。

### 6. GHCR 退出与回滚窗口

- CNB 首次成功发布只证明新链路可用；旧 GitHub 双仓 Workflow 设计和已发布镜像保留为 Git 历史回滚基线，不并行保留第二个可触发发布入口。
- 连续完成至少两次不同 Commit SHA 的 CNB 发布并核对证据后，才进入 GHCR 主链路退出评审。
- GHCR 退出时更新 ADR、运维文档和 Workflow；既有 GHCR 镜像保留，不自动删除。
- 迁移失败时通过普通反向提交恢复当前双仓 Workflow，继续使用已验证流程。
- GHCR 是否长期保留为异地灾备属于后续独立决策，不阻断本次 CNB 主链路验证。

### 7. 生产部署边界

- 本计划的 CNB 阶段止于构建、扫描、推送和发布证据核验。
- 生产部署仍须确认 CVM 地域、TCR 个人版访问路径和独立只读 Registry 身份。
- 服务器只保存 TCR 只读凭证，生产 Compose 只接受完整 digest 引用。
- TCR 故障时不自动切换其他 Registry，任何应急镜像来源都需要独立授权和 digest 核验。

## 实施顺序

1. 用户审阅本计划并确认 CNB 组织、私有仓库和受控发布分支信息。
2. 用户登录 CNB，创建顶级组织和私有仓库，不绑定付费预算。
3. 用户创建仅用于 GitHub 向目标 CNB 仓库推送的访问 Token，并直接配置到 GitHub 受保护 Environment。
4. 用户把现有 TCR 发布用户名和固定密码直接配置到 CNB 密钥仓库，不在对话或仓库中提供真实值。
5. 取得实现授权后新增 `.cnb.yml`，实现三镜像构建、缓存、Trivy、SBOM、provenance、候选发布、SHA 标签 finalize 和发布清单。
6. 调整 GitHub 发布入口，使其只校验固定 SHA 并向 CNB 交接源码，不再构建或推送镜像。
7. 增加 CNB 发布清单校验脚本和成功、缺失、错配、额外字段、digest 冲突等负向夹具。
8. 更新 ADR 0008、GitHub Actions、容器构建、发布回滚和运维文档。
9. 运行本地轻量治理门禁，复读全部差异并清理验证产物。
10. 取得本地检查点提交授权后精确暂存并提交当前任务文件。
11. 取得代码推送授权后推送 GitHub，等待四个轻量 Push 门禁成功。
12. 取得 Full Validation 授权后，对同一 Commit SHA 执行完整验证。
13. 取得 CNB 源码交接和镜像发布授权后触发首次 CNB 构建，核对三张 TCR 镜像、扫描、SBOM、provenance 和发布清单。
14. 使用第二个不同 Commit SHA 重复验证，证明缓存、幂等和不可变标签门禁有效。
15. 两次验证成功后评审 GHCR 主链路退出；生产配置和部署继续等待独立授权。
16. 回写实际结果、限制和剩余问题，并同步计划与项目索引。

## 风险与回滚

- **CNB 社区版无明确构建地域承诺**：首次运行记录源码同步、依赖下载和 TCR 推送耗时。若仍存在明显跨境瓶颈，停止迁移并评估腾讯云独立构建机。
- **CNB 免费额度耗尽**：初始不绑定预算，任务因额度不足停止。用户核对用量后再决定等待下月额度或专项授权预算。
- **GitHub 与 CNB 源码漂移**：只允许 GitHub Workflow 推送固定 Commit SHA；CNB 构建开始时复核 SHA，漂移时失败。
- **CNB Token 泄露**：Token 只进入 GitHub Secret，限制目标仓库权限并支持轮换。泄露时撤销 Token，旧镜像保持不变。
- **TCR 发布密码泄露**：密码只进入 CNB Secret。轮换后更新 CNB，禁止依赖 GitHub 中无法读取的 Secret 作为恢复来源。
- **TCR 个人版标签可覆盖**：发布前检查冲突，发布后复核 digest，生产始终按 digest 部署。
- **供应链证据弱化**：在 CNB 的 Trivy、SBOM、provenance 和发布清单全部验证前不退出 GHCR 主链路。
- **三仓部分成功**：CNB Run 保持失败，不产生完整发布清单，生产部署拒绝使用。
- **依赖源访问慢**：使用锁文件、BuildKit 缓存和固定基础镜像；只有实测仍慢时才评估可信镜像源或把固定基础镜像复制到 TCR。
