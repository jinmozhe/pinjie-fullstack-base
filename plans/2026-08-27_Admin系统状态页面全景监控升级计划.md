## 关联需求

- `BASE-BE-001`：提供可配置、可启动和可健康检查的 FastAPI 应用。
- `BASE-BE-006`：提供系统级公共能力入口，健康、配置、审计、限流和缓存等能力通过公共基础设施或 system 领域统一承载。
- `BASE-ADMIN-001`：提供可扩展的 B 端管理应用骨架。
- `BASE-ADMIN-003`：提供用户、管理员、角色、权限和系统管理的扩展位置。
- `BASE-ADMIN-004`：管理界面必须覆盖完整操作状态（加载、错误、重试、成功）。

- `BASE-API-001` / `BASE-API-002` / `BASE-API-003`：根 openapi.json 是唯一契约，API Client 自动生成与同步。

## 背景

Admin 管理端的系统状态页面（`/system`）目前仅消费公共接口 `/api/v1/system/status`，页面仅渲染单个简单的“可用/不可用”标签，展示内容单调且缺乏基础设施健康细节与运行时元数据。如果直接在前端发起多个并发请求去拉取不同模块的统计与状态，在大数据量或高频轮询场景下会导致网络扇出（Fan-out）和数据库大表慢查询。

## 目标

1. **后端聚合接口**：提供专用的管理端系统全景监控接口 `GET /api/v1/admin/system/overview`，单次 HTTP 请求聚合全部必要数据。
2. **三层数据分层处理**：
   - **实时探针层（实时、无缓存）**：PostgreSQL 连接与 Alembic 迁移检测、Redis 连通性检测，保证故障秒级真实报警。
   - **内存元数据层（纯内存、零 I/O）**：FastAPI/CPython 版本、服务启动时间、稳定运行时长（Uptime）、公开存储配置摘要和时区。
   - **业务资产统计层（走 Redis 缓存，TTL 120s）**：当前用户、启用管理员与角色、现存文件资产、保留期内安全审计日志数，降低精确统计频率。
3. **契约同步**：更新 OpenAPI 契约并自动重新生成 `@pinjie/api-client` 客户端方法与类型。
4. **前端看板重构**：重构 `SystemStatusPage.tsx`，以 Ant Design 6 / ProComponents 浅色高质感风格呈现四大板块：
   - **板块一：全局健康状态横幅**（实时探针延迟、Uptime 运行时长、版本、手动刷新与自动轮询开关）；
   - **板块二：核心基础设施健康矩阵**（PostgreSQL 数据库、Redis 缓存、本地文件存储、双轨安全引擎 4 张 ProCard）；
   - **板块三：核心业务资产与规模概览**（用户、管理员、资产、审计日志统计卡片）；
   - **板块四：系统运行环境与配置详情**（ProDescriptions 展示真实运行时版本、服务器时区和 CORS 信任源数量）。
5. **权限与失败语义**：新增 `system:overview:read`，Redis 必需依赖失败时与 Readiness 一致标记不可用，遥测失败不返回假数字。
6. **测试与质量门禁**：补充 Backend 与 Admin 测试代码，运行项目允许的轻量静态门禁；pytest、Vitest、Build 与浏览器验证继续按独立授权执行。

## 非目标

- 不修改现有面向容器和负载均衡器的公共探针 `/health/live` 与 `/health/ready`。
- 不引入外部重型 APM 框架（如 Prometheus/Grafana 或 OpenTelemetry Agent），保持全栈母版独立可运行与业务中立。
- 不修改 C 端 Web 应用及现有数据库表结构（无需新增 Alembic 迁移）。

## 现状分析

- 后端 `apps/backend/app/core/health.py` 中已有成熟的 `check_readiness` 探针（支持 PG `SELECT 1`、Alembic heads 校验和 Redis PING）。
- 后端已有全局 `app.state.resources` 与 `app.state.settings`，可在服务 lifespan 记录启动时间戳并计算准确 Uptime。
- 前端已有 `@tanstack/react-query` 统一数据流管理，可非常自然地支持 `refetchInterval`（自动轮询）与手动刷新。
- 前端现有 `SystemStatusPage.tsx` 结构简单，升级不会对其他业务模块造成破坏性影响。

## 方案设计

### 1. 后端接口设计 (Backend)

- 在 `app/domains/admin/schemas.py` 中定义响应模型：
  - `SystemOverviewRead`：
    - `status`: `"healthy" | "degraded" | "unavailable"`
    - `started_at`: `datetime`
    - `uptime_seconds`: `int`
    - `environment`: `str`
    - `release_version`: `str`
    - `python_version` / `fastapi_version`: 真实运行时版本
    - `timezone`: `str`
    - `cors_origin_count`: CORS 信任源数量，不返回完整来源
    - `infrastructure`:
      - `database`: `{"status": str, "latency_ms": float, "details": str}`
      - `redis`: `{"status": str, "latency_ms": float, "mode": str}`
      - `storage`: `{"driver": str, "public_base_url": str}`
      - `security`: 会话隔离、CSRF 和 Refresh 轮换机制摘要，不冒充健康探针
    - `telemetry`:
      - `user_count`: `int`
      - `admin_count`: `int`
      - `asset_count`: `int`
      - `audit_event_count`: `int | null`
      - `status` / `source` / `sampled_at`: 采样状态、来源和数据时间
- 在 `app/services/admin_management.py` 中新增 `get_system_overview()` 方法：
  - 执行实时 `check_database` 与 `check_redis` 测算真实延迟（`latency_ms`）；
  - 从统一 Key 工厂读取 `<project>:<environment>:system:telemetry:v1:overview`，未命中时以单次 SQL 往返统计并写入 Redis（TTL 120s）；
  - 默认单实例通过进程内锁合并缓存未命中请求，多实例边界写入可观测性文档；
  - 组装真实运行时版本、公开配置摘要、采样时间与 Uptime 秒数返回。
- 在 `app/domains/admin/management_router.py` 中暴露：
  - `GET /api/v1/admin/system/overview`，显式要求 `system:overview:read`。

### 2. 契约生成 (API Client)

- 导出后端 `openapi.json`。
- 运行 `pnpm generate-api` 重新生成 `packages/api-client`。

### 3. 前端实现 (Admin)

- 重构 `apps/admin/src/features/system/SystemStatusPage.tsx`：
  - 支持顶部刷新与自动轮询选择（关闭 / 15s / 30s / 60s）；
  - 4 个卡片网格响应式适配桌面与平板；
  - 带有状态指示、延迟 Tag、遥测采样时间与公开路径复制能力；
  - 覆盖完整的三态交互（Loading 骨架/Spin、Error 错误重试、Success 状态展示）。
- 更新 `apps/admin/src/features/system/SystemStatusPage.test.tsx` 单元测试。

## 风险与回滚

- **风险**：Redis 离线时精确统计回退可能增加数据库负载，多实例同时缓存未命中仍可能重复采样。
  - **规避**：精确统计使用单次 SQL 往返和明确超时；默认单实例以进程内锁合并请求，多实例启用高频轮询前增加分布式刷新锁或独立采集任务。
- **回滚**：按当前任务差异反向恢复端点、页面和生成契约，并重新生成 API Client；禁止覆盖同文件中的其他任务修改。
