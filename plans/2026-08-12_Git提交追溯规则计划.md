# Git 提交追溯规则计划

## 1. 当前状态

## 1.1 关联需求

`BASE-GEN-006`、`BASE-DOC-004`、`BASE-DOC-006`。

## 2. 背景

Git 已通过 Commit SHA、父提交和文件快照保存精确修改历史。若普通提交完成后再把该次 SHA 回写到计划、Changelog 或索引，回写本身会产生新的提交和新的 SHA，形成无法闭合的自引用循环，也会让长期文档充满重复记录。

项目仍需要明确少数跨越仓库历史边界的场景，例如正式发布、生产部署、派生项目、安全审计、故障回滚和阶段性交接。这些场景必须记录可验证的完整 Commit SHA 或受保护的不可变 Git Tag。

## 3. 目标

1. 明确 Git 历史是普通提交 SHA 和逐行差异的权威来源。
2. 禁止把每次普通提交 SHA 重复写入 Changelog、计划和全项目索引。
3. 明确必须记录完整 SHA 或不可变 Tag 的跨系统追溯场景。
4. 明确 `git-sync` 只在交付回复中报告提交和推送结果，不回写自身提交 SHA。

## 4. 非目标

1. 不修改个人全局 `git-sync` Skill。
2. 不给现有普通提交补写 SHA。
3. 不创建 Git Tag、GitHub Release、部署记录或交接记录。
4. 不修改 Git 历史、分支或远程仓库。

## 5. 现状分析

1. Git 本地仓库和 GitHub 已保存每次提交的文件状态、差异和完整 SHA。
2. `CHANGELOG.md` 记录已交付变化，`plans/*.md` 记录实施背景和验证，`.agents/agents-index.md` 记录当前事实和导航。
3. 派生项目已经要求记录母版标签或提交 SHA，但普通提交是否回写项目文档尚无明确规则。
4. `git-sync` 会在完成后报告提交哈希，本项目规则尚未明确禁止自动回写该哈希。

## 6. 方案设计

1. 在根 `AGENTS.md` 增加“Git 提交与追溯”规则。
2. 普通 Commit SHA 只由 Git 历史维护，不写入 Changelog、计划或全项目索引。
3. 正式发布、生产部署、派生项目基线、安全审计、故障回滚和阶段性交接记录完整 SHA 或受保护的不可变 Tag；部署、审计和回滚优先记录完整 SHA。
4. `git-sync` 在最终回复中报告 SHA，不为回写 SHA 创建后续提交。
5. 更新全项目索引和 Changelog，登记本规则与已交付变化。

## 10. 风险与回滚

1. 风险：规则过度要求所有记录都填写 SHA，增加无效维护。控制方式是只要求跨系统边界场景记录完整 SHA。
2. 风险：可移动 Tag 被误认为稳定依据。控制方式是只接受受保护的不可变 Tag，部署、审计和回滚优先记录完整 SHA。
3. 风险：`git-sync` 回写刚产生的 SHA 导致自引用循环。控制方式是明确只在交付回复中报告。
4. 回滚：通过后续普通提交调整规则，不改写 Git 历史。
