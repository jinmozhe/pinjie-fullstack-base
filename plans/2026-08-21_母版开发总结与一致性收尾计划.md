## 背景

2026-08-21 对仓库规则、文档、计划、源码、OpenAPI、生成客户端、数据库迁移、依赖、容器、GitHub Actions 和质量门禁完成全量只读审计。审计确认三个应用和通用业务核心能力已经形成可继续开发的母版主体，但生产 Compose、Backend 文件日志、OpenAPI 字段说明、数据库迁移实证、恢复演练、前端依赖图门禁和当前性文档仍存在未闭环事项。

本计划统一承接这些问题，目标是让代码、配置、契约、迁移、运维步骤、计划状态和当前事实重新对应，并依据 `docs/PROJECT_REQUIREMENTS.md` 的 13 条母版完成验收给出可核验结论。

## 目标

1. 修复 PostgreSQL 18 生产数据卷路径和 Backend 生产文件日志权限风险。
2. 为全部公开 OpenAPI Schema 字段提供准确中文说明，并增加自动防漂移测试。
3. 让根 README、三端 README、项目结构、依赖白名单、计划状态、索引和 Changelog 与当前实现一致。
4. 验证 Alembic 空库升级、已有库升级和重复升级，并让本地开发数据库达到当前 head。
5. 提供可执行且具备防误连保护的 PostgreSQL 备份恢复演练入口，并保存本次专用测试库演练结果。
6. 补齐 1Panel 单机生产运行手册，明确部署等级、环境变量、迁移、健康检查、日志、备份、恢复和回滚边界。

9. 逐条回写 67 项 `BASE-*` 需求追踪和 13 条母版完成验收结果，不把未执行项记录成通过。

## 现状分析

- `compose.prod.yml` 使用 PostgreSQL 18.4，却把命名卷挂载到 PostgreSQL 17 及以下使用的 `/var/lib/postgresql/data`。
- Backend 文件日志默认开启并创建相对路径 `logs/`；生产镜像以 UID 10001 运行，`/app` 没有可写目录，生产配置示例也没有显式关闭文件日志。
- 根 OpenAPI 的接口摘要和响应说明已中文化，但绝大多数 Schema 字段没有 `description`，与 `BASE-API-001` 和 Changelog 声明冲突。
- Alembic head 为 `20260820_01`，当前本机开发数据库停在 `20260815_01`；最新迁移缺少本机空库和已有库完整验证。
- Backend 和 Web README 仍描述阶段 B，Web README 还包含未安装依赖和具体商品页面假设。
- 项目结构文档和索引记录 290 个文件，审计时实际为 294 个，实施本计划后文件数还会继续变化。
- `pnpm-workspace.yaml` 实际允许 6 个依赖执行构建脚本，文档和 Changelog 只记录 `esbuild` 与 `sharp`。
- `plans/2026-08-20_GitHub CI线上失败修复计划.md` 与索引状态冲突，另外两份已结束计划保留未勾选验证和真实环境缺口。
- 备份恢复具有原则文档，但没有母版内的专用演练脚本和本次恢复实证；1Panel 生产手册仍标记为待补充。
- Backend 已有 import-linter 合同，现有前端边界脚本仍以文本扫描为主，不能完整证明循环依赖和动态导入边界。
- PRD 共 67 项 `BASE-*`；审计时有 5 项缺少计划级引用，本计划将补齐追踪入口并明确母版与派生项目责任。

## 方案设计

### 生产运行边界

1. 按 PostgreSQL 18 官方镜像目录约定，把生产命名卷挂载到 `/var/lib/postgresql`。
2. 生产 Compose 默认只输出标准错误流，对 Backend 和 request-log-consumer 显式设置 `LOG_FILE_ENABLED=false`。
3. 保留现有文件日志开关、路径、轮转、保留和压缩能力。需要文件落盘的部署必须配置明确的可写挂载和路径，运维文档给出受控示例。
4. 增加 Compose 配置检查或等价自动测试，防止 PostgreSQL 卷路径和生产日志策略再次漂移。

### OpenAPI 字段说明

1. 在 Backend Pydantic Schema 源码中为公开字段维护准确中文 `description`，不手工编辑 `openapi.json` 或生成客户端。
2. 对公共包装模型和重复语义复用明确的字段元数据，避免维护多份含义不一致的说明。
3. 增加 OpenAPI 测试，要求公开 Schema 属性都具有非空中文说明，同时允许程序标识继续使用英文。
4. 依次导出根 OpenAPI、生成 API Client，再验证 Admin 和 Web 类型、测试与构建。

### 数据库和恢复演练

1. 复核最新 revision 的升级、降级边界和幂等行为，不改写既有迁移历史。
2. 使用独立且名称以 `_test` 结尾的临时数据库验证空库升级、已有库升级和重复升级。
3. 在取得数据库操作授权后，把当前本地开发数据库升级到 head，仅执行已提交 Alembic revision。
4. 新增 PowerShell 备份恢复演练脚本。脚本必须校验环境、数据库名、源库和目标库隔离、工具存在性及确认参数，禁止指向生产库。
5. 演练使用专用临时 `_test` 数据库，验证 `pg_dump`、`pg_restore`、结构版本和基础数据一致性，结束后按授权清理临时库。

### 文档和治理同步

1. 更新根和三端 README 的当前能力、技术栈、启动命令和业务中立边界。
2. 重新生成项目结构清单和最终文件数，登记本计划新增文件。
3. 根据 Git 历史、锁文件和实际安装需求说明 6 项 `allowBuilds` 条目的来源与必要性，无法证明必要的条目不直接保留为既成事实。

5. 对计划状态冲突进行证据化收敛。已由后续验证覆盖的项目写明依据，仍未验证的项目保留为剩余问题。

7. 为历史原始方案增加醒目的历史资料边界，当前事实统一指向现行 ADR、架构和项目结构文档。
8. 更新 `.agents/agents-index.md` 和 `CHANGELOG.md`，只记录本次实际完成并验证的事实。

### 模块边界门禁

1. 保留现有 PowerShell 静态边界检查和 Backend import-linter 合同。
2. 优先使用仓库现有 TypeScript 编译能力构建 Admin、Web 的静态导入图；如果无法稳定覆盖，则评审并固定一个成熟依赖图工具作为开发依赖。

## 风险与回滚

- 风险：PostgreSQL 卷挂载修正会改变新容器的数据目录挂载方式，已有生产实例不能直接套用而不迁移数据。
- 控制：本次只修改母版配置和文档，不操作生产卷；手册明确新部署与既有部署迁移边界。
- 风险：大量 Schema 描述调整可能改变生成客户端注释并产生较大差异。
- 控制：不改变路径、字段名、类型、必填性和响应语义；使用契约差异检查确认只有文档元数据变化。
- 风险：依赖图门禁可能暴露既有循环或引入新的开发依赖。
- 控制：先盘点现有图，再区分真实违规与工具配置；新增依赖必须固定版本、审计来源并通过锁文件和安全门禁。
- 风险：数据库升级和恢复演练涉及创建、写入和删除临时数据库。
- 控制：仅使用名称以 `_test` 结尾的专用数据库，校验与开发和生产库隔离，并在执行前取得明确授权。
- 回滚：源码和文档改动可按文件差异回退；数据库只执行既有升级迁移，临时演练库独立创建；不对生产环境执行回滚。
