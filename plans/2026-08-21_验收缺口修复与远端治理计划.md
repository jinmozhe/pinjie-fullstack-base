## 关联需求

## 背景

2026-08-21 母版一致性收尾后，用户要求审计是否仍有未执行计划或需要继续完善的事项。审计确认没有活动计划，当前 `main` 与 `origin/main` 一致，四组自动 GitHub Actions 门禁通过，但仍发现以下未闭环事实：

- Backend Middleware 已绑定 `request_id` 和 `trace_id`，文件 Sink 使用 Loguru 默认文本格式，实际文件样本没有输出绑定的 `extra` 字段。
- 当前 Commit SHA 没有 GitHub Ubuntu Runner 上的人工 Browser E2E 成功记录。
- GitHub 远端没有 `main` Ruleset 或分支保护，也没有预配置的 `production` Environment；Dependabot vulnerability alerts、Secret Scanning、Push Protection 和 Private Vulnerability Reporting 均未启用。
- Web 没有 favicon，浏览器会请求不存在的 `/favicon.ico`。
- 两份历史计划使用规范之外的“已完成”状态，若干后续验证事实尚未回写到对应历史计划。

用户要求按“文件日志、线上 Browser E2E、GitHub 远端治理、favicon 与历史文档清理”的顺序继续执行。本计划承接该范围，并在实施前完成计划门禁确认。

## 目标

1. 让 Backend 文件日志稳定输出结构化 `request_id`、`trace_id`、method、route、status 和 duration 字段，同时保持 UTF-8、轮转、保留、压缩、异步队列及关闭时不创建文件的既有行为。
2. 增加真实文件写入自动测试，覆盖关联字段、中文文本、无 `extra` 普通日志和关闭文件日志四类场景。
3. 在日志修复提交推送且四组自动门禁成功后，为同一 Commit SHA 人工触发 `CI - Browser E2E`，等待结束并保存成功或失败证据。
4. 在不发布镜像、不部署生产的前提下，补齐仓库可用的 GitHub 安全治理：漏洞告警、秘密扫描、推送保护、私有漏洞报告、Actions 来源限制、`main` Ruleset 和 `production` Environment。
5. 为 Web 增加可被 Next.js Metadata 识别的真实 favicon 资产，并验证桌面、移动端渲染和资源请求。
6. 纠正历史计划状态枚举与已被后续验证覆盖的记录，修正母版计划、索引和 Changelog 中关于文件日志验收的过强表述。

## 现状分析

### Backend 文件日志

- `apps/backend/app/core/middleware.py` 使用 `logger.bind()` 绑定请求关联字段。
- `apps/backend/app/core/logging.py` 的 stderr Sink 在生产环境使用 JSON 序列化，但文件 Sink 没有 `serialize=True` 或显式包含 `extra` 的格式。
- Loguru 默认文本格式不输出绑定的 `extra` 字典，因此现有文件日志不能满足可观测性文档对请求关联字段的要求。
- 当前测试只通过 Monkeypatch 检查 Sink 参数，没有真实写入并读取日志文件。

### Browser E2E

- `.github/workflows/ci-e2e.yml` 仅允许 `workflow_dispatch`，不属于 Push 或镜像发布门禁。
- 本地最终矩阵已有 8 项通过、8 项按设计跳过，但当前 SHA 缺少 Ubuntu Runner 和完整 Chromium 的线上证据。

### GitHub 远端治理

- 仓库当前为公开仓库，只有 `jinmozhe` 一位协作者或管理员。
- `CODEOWNERS` 已存在，但没有 Ruleset 或 branch protection，不能强制执行评审和自动检查。
- 单维护者无法对自己的 Pull Request 完成独立批准，因此本阶段只能强制 Pull Request、会话解析和自动状态检查，审批数保持为 0；增加第二位可信协作者后再提升为至少 1 次独立审批。
- `production` Environment 尚不存在。当前只能把现有管理员配置为必要 Reviewer；在没有第二位 Reviewer 时保留自审风险，且不写入任何生产 Secrets 或 Variables。
- Actions 默认允许所有来源。仓库工作流已经固定 Action Commit SHA，可在完整盘点现有 `uses:` 后配置精确允许列表和 SHA Pinning；若当前 GitHub 计划或 API 不支持，则保持原设置并记录平台缺口，禁止部分配置后宣称完成。

### Web 与历史文档

- `apps/web/src/app` 没有 `icon.*`，仓库没有可复用的品牌图标资产。
- `plans/2026-08-20_Admin技术栈文档一致性审计计划.md` 和 `plans/2026-08-20_CI失败修复计划.md` 顶部使用“已完成”，不符合计划状态枚举。
- 历史未勾选项只能追加后续证据，不删除或改写当时事实；仍没有证据的项继续保持未完成。

## 方案设计

### 文件日志结构化

1. 文件 Sink 使用 Loguru JSON Lines 序列化，使绑定字段稳定进入 `record.extra`，并保证没有关联字段的普通日志也能正常写入。
2. 保留 stderr Sink 的现有环境行为和文件 Sink 的轮转、保留、ZIP、UTF-8、异步队列、安全异常诊断边界。
3. 测试使用临时目录和真实 Loguru Sink 写入，等待队列完成后读取 JSON Lines，断言请求关联字段和中文文本；测试结束恢复统一日志配置，避免污染其他用例。
4. 关闭文件日志时继续断言目录和文件均不创建。

### 线上 Browser E2E

1. 日志修复及必要文档变更完成并通过本地门禁后，创建普通 Git 提交并推送 `main`。
2. 等待当前 SHA 的 Governance、Backend、Frontend、Security 四组自动工作流全部成功。
3. 人工触发 `CI - Browser E2E` 的 `main`，等待最终状态并核对使用的 Commit SHA。
4. 失败时读取首个有效错误和上传的诊断产物，在同一计划中修复、重新验证、提交和触发；不通过重试掩盖不稳定性。

### GitHub 远端治理

1. 变更前通过 GitHub API 导出现有仓库、Actions、Environment、Ruleset 和安全设置摘要，作为回滚依据；不得输出 Token 或 Secrets。
2. 启用 Dependabot vulnerability alerts、Secret Scanning、Push Protection 和 Private Vulnerability Reporting，并逐项读取 API 确认。
3. 盘点所有工作流使用的 Action owner/repository，配置精确允许列表和可用的完整 SHA Pinning；任何不支持项单独记录，不扩大到允许所有第三方 Action。
4. 为 `main` 创建 Ruleset：目标为默认分支，禁止删除和非快进更新，要求通过 Pull Request 合并、会话解析及四组自动状态检查；由于只有一位协作者，初始必要审批数为 0，不虚构 Code Owner 独立审批。
5. 创建 `production` Environment，使用现有管理员作为必要 Reviewer；不写入部署 Variables 或 Secrets，不触发 Deploy Production。
6. 每项远端变更后重新读取设置验证；若平台套餐、权限或 API 拒绝，停止该项并记录准确剩余风险，不通过弱化配置制造假成功。

### favicon 与文档治理

1. 仓库没有现有品牌资产，因此使用 Next.js 官方 `ImageResponse` 在
   `apps/web/src/app/icon.tsx` 生成简洁、可辨识、无业务领域假设的方形 PNG，
   并由 App Router 自动接入 Metadata。当前会话没有可用的内置图像生成服务，
   未调用需要外部 API Key 的降级脚本。
2. 验证 production build、favicon 响应、桌面和移动端页面、控制台资源错误与横向溢出。
3. 把两份历史计划状态改为“已结束”，保留原结果和历史过程。
4. 对已有后续证据覆盖的历史未勾选项追加日期、命令、结果和承接计划链接；线上 Browser E2E 只有在本计划工作流成功后才能回写为已验证。
5. 同步可观测性文档、原文件日志计划、母版收尾计划、项目索引和 Changelog，使当前事实与验证证据一致。

## 风险与回滚

- 风险：文件日志从默认文本变为 JSON Lines，现有人工阅读和日志采集规则需要适配。
- 控制：只改变可选文件 Sink，stderr 行为保持不变；文档明确字段位置并用真实文件测试固定契约。
- 回滚：恢复文件 Sink 原配置即可；已有日志文件不修改或删除。
- 风险：Ruleset 或 Actions 允许列表可能阻断正常 Push、Pull Request 或工作流。
- 控制：变更前盘点全部 Check 和 Action，保留管理员 Bypass 回滚路径，每项配置后立即回读；失败时使用保存的远端摘要恢复对应设置。
- 回滚：删除本计划创建的 Ruleset、恢复 Actions 策略和安全功能原状态；不改变 Git 历史。
- 风险：单维护者无法实现独立代码评审和生产审批。
- 控制：明确记录为剩余风险，当前只实施可验证的自动门禁与必要 Reviewer；未来添加第二位可信维护者后提高审批要求。
- 风险：favicon 生成结果可能不符合未来派生项目品牌。
- 控制：使用业务中立的母版图标；派生项目必须替换成自身品牌资产。
- 回滚：移除本次新增图标并恢复原 Metadata 行为；不影响 API 或数据。
