## 背景

当前 `.github/workflows/publish-images.yml` 在把指定 Commit 快进交接到 CNB 前，强制要求同 SHA、未过期且字段完整的 Full Validation Artifact。该 Artifact 来自人工运行的 pytest、Vitest、两端 production build、PostgreSQL、Redis 和 Chromium Playwright，覆盖面高但耗时较长。

日常低风险改动仍会通过 Governance、Backend、Frontend 和 Security 四个轻量 Push 工作流，也会在 CNB 中接受 Docker 构建、Trivy、SBOM、provenance、不可变 SHA 标签和 digest 复核。用户要求保留严格模式，同时允许对已经人工评估的低风险改动显式选择快速模式，跳过 Full Validation Artifact 门禁。

Docker 构建和 Trivy 不能替代业务逻辑、数据库交互和浏览器流程验证。因此快速模式属于有记录的风险选择，不能宣称完整验证通过，也不能成为默认值。

## 目标

1. 为 `Handoff Source to CNB` 增加 `strict` 与 `fast` 两种明确模式。
2. 默认使用 `strict`，继续执行现有 Full Validation Artifact 的全部真实性校验。
3. 只有人工显式选择 `fast` 并填写非空原因时才跳过 Full Validation Artifact。
4. 两种模式都继续强制同 SHA 的四个轻量 Push 工作流、默认分支祖先、三个应用 `ready` 和模块边界。
5. 快速模式在 GitHub Job Summary 中记录 Commit、操作者、模式、跳过事实和原因。
6. 保持 CNB 三端按需构建、Trivy、SBOM、provenance、不可变标签和 TCR digest 校验不变。
7. 增加机器夹具，防止未来把快速模式改成默认值、弱化轻量门禁或静默跳过记录。

## 非目标

- 不删除或缩减 `.github/workflows/ci-e2e.yml`。
- 不改变 Full Validation Artifact Schema、内容、保留期或校验脚本。
- 不自动根据文件路径决定 `strict` 或 `fast`，选择权由取得发布授权的操作人员承担。
- 不允许快速模式绕过 Governance、Backend、Frontend、Security、应用状态或模块边界。
- 不修改 CNB 构建、TCR 发布、Compose、数据库、Redis 或应用业务源码。
- 不承诺快速模式的耗时，也不承诺 Docker 构建成功等同于应用功能正确。
- 不自动提交、推送、触发 GitHub Workflow、发布镜像或部署生产。

## 现状分析

- `publish-images.yml` 当前只有 `commit_sha` 输入。
- Full Validation Artifact 查询、Run 归属校验、下载和 Schema 校验位于 `validate` Job，当前无条件执行。
- 四个轻量 Push 工作流校验在 Full Validation 之前无条件执行。
- 应用 `ready` 和模块边界校验在 Full Validation 之后无条件执行。
- `check-full-validation-evidence.ps1` 和现有负向夹具已经严格校验证据，本计划继续复用。
- 当前没有机器检查来约束源码交接工作流的验证模式、默认值和快速模式审计记录。

## 方案设计

### 1. 工作流输入

新增 `validation_mode` 选择项，允许值精确为 `strict`、`fast`，默认值固定为 `strict`。新增可选字符串 `fast_mode_reason`，只在快速模式使用，描述中明确禁止填写密钥和敏感信息。

工作流内部再次校验模式值。快速模式要求原因去除空白后非空、只能占一行且长度不超过 200 个字符；不满足时在访问 CNB 前失败。

### 2. 条件化 Full Validation

现有 Full Validation Artifact 步骤只在 `validation_mode == strict` 时执行。严格模式保持 Artifact 名称、所属 Run、默认分支、工作流路径、成功结论、Commit SHA、Run ID 和证据字段的全部校验，不允许降级或 `continue-on-error`。

快速模式跳过该步骤，但不跳过前后的四个轻量 Push 工作流、应用状态和模块边界。`validate` Job 只有所有适用步骤成功后才允许 `handoff` Job 执行。

### 3. 审计记录

验证结束后统一写入 GitHub Job Summary：

- 完整 Commit SHA。
- `strict` 或 `fast` 模式。
- GitHub Actor。
- 严格模式对应的 Full Validation Run ID。
- 快速模式明确记录 Artifact 未要求，并记录人工填写的原因。

快速模式只代表跳过该项门禁，不能把 Summary 或后续 CNB 构建表述为 Full Validation 成功。

### 4. 使用边界

`strict` 用于数据库迁移、认证授权、权限、公开 API、OpenAPI、共享包、依赖与锁文件、Dockerfile、发布与安全脚本、跨端功能和正式版本。

`fast` 只用于操作人员已经审查影响范围、能够接受未运行 pytest、Vitest 和 Playwright 风险的低风险变更。存在疑问时选择 `strict`。

## 风险与回滚

- **快速模式漏测**：镜像能够构建仍可能包含业务错误。默认保持严格，快速模式要求明确选择、原因和 Summary 记录。
- **静默降级**：条件表达式错误可能让严格模式跳过证据。模式夹具固定输入默认值、选项和步骤条件。
- **轻量门禁被绕过**：后续重构可能把四个 Push 工作流一起条件化。夹具要求这些步骤、应用状态和模块边界在两种模式下无条件存在。
- **原因注入或泄密**：原因只允许单行、限制长度，界面描述和文档禁止填写密码、Token 或个人敏感信息。
- **严格模式回归**：保留原 Full Validation 证据脚本和负向夹具，严格路径继续 Fail Closed。
- **回滚**：普通反向提交恢复 Full Validation 无条件步骤，禁止改写 Git 历史；该变更不涉及数据库和生产数据。
