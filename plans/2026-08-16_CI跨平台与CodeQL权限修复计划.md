# CI 跨平台与 CodeQL 权限修复计划

## 当前状态和结果

- 状态：已结束
- 结果：已完成

## 关联需求

- 无。本计划修复既有 CI 配置缺陷，不改变产品能力或验收范围。

## 背景

GitHub Actions 中应用测试均已通过，但 `CI - Governance` 和 `Security` 工作流持续失败。已确认 Governance 失败发生在 Linux PowerShell 读取点文件时，Security 失败发生在私有仓库 CodeQL 上传结果阶段。两处失败均属于既有 CI 配置问题。

## 目标

1. 让文本卫生检查在 Linux PowerShell 中正确读取被 Git 跟踪的点文件。
2. 让 Governance 正反例脚本在全部断言和清理成功后显式返回成功。
3. 以当前个人私有仓库可运行的 Semgrep Community Edition 替换无法启用的 CodeQL，覆盖 Python、JavaScript 和 TypeScript 静态安全扫描。
4. 保持现有安全扫描、失败关闭策略和应用行为不变。
5. 完成仓库治理检查，并明确线上 GitHub Actions 复验所需的独立推送授权。
6. 建立独立的 GitHub Actions 工作流说明，完整记录 push、Pull Request、镜像发布、生产部署和排障流程。

## 非目标

- 不修改 Backend、Admin、Web 或 API Client 源码。
- 不调整依赖版本、数据库或应用业务逻辑。
- 不弱化静态代码扫描、文本卫生检查或其他 CI 门禁。
- 不创建 Semgrep 云端账号、Token、项目或源码上传链路。
- 不在本计划确认时自动提交、推送或触发线上工作流。

## 现状分析

- `scripts/ci/check-text-files.ps1` 使用 `Get-Item -LiteralPath` 获取文件信息；Linux PowerShell 对 `.agents/rules/.markdownlint.json` 等点文件需要显式包含隐藏项，当前 Governance Run 因找不到该文件而失败。
- `.github/workflows/security.yml` 的两个 CodeQL Job 只声明 `contents: read` 和 `security-events: write`；CodeQL 分析和 SARIF 生成完成后，请求 Actions Run 元数据时返回 `Resource not accessible by integration`。
- 首次修复推送后，线上 Run `31895224445` 已确认文本检查通过，但正反例脚本在打印成功消息后仍返回退出码 1；最后一个预期失败的子进程遗留 `$LASTEXITCODE=1`，脚本成功路径没有显式重置退出码。
- 追加修复推送后，Governance Run `31895430392` 已成功。Security Run `31895224446` 已不再报告 Actions 元数据读取权限错误，当前明确失败于 `Code scanning is not enabled for this repository`。
- GitHub 官方文档确认，Code scanning 适用于公开仓库，或启用了 GitHub Code Security 的 GitHub Team、Enterprise Cloud、Enterprise Server 组织仓库。当前个人名下私有仓库的 Advanced Security 设置页没有 Code scanning 启用项。
- 首次执行 Semgrep CE `p/default` 扫描 245 个文件、应用 523 条规则，发现 6 个阻断项：生产部署摘要步骤存在 5 处 GitHub 表达式直接进入 Bash，Admin Nginx 健康响应使用 `add_header` 设置内容类型，uv 缺少新发布依赖冷却期，pnpm 缺少新发布依赖、奇异传递依赖和信任降级保护。
- 本地 `main` 正确跟踪 `origin/main`，工作区在创建本计划前为干净状态。

## 方案设计

1. 将文本检查中的文件读取改为 `Get-Item -Force -LiteralPath $fullPath`，仅修复点文件读取，不改变扫描范围和编码规则。
2. 在 Governance 正反例脚本的成功路径末尾显式 `exit 0`；任何断言或清理异常都会在到达该语句前传播并保持失败。
3. 删除当前仓库无法运行的两个 CodeQL Job，以单一 Semgrep CE SAST Job 扫描 Python、JavaScript 和 TypeScript 源码。
4. 沿用仓库已固定的 `astral-sh/setup-uv` Action，固定 Semgrep CLI `1.173.0`，使用官方 `p/default` 规则集。
5. 使用 Semgrep `1.173.0` 实际支持的 `semgrep scan --error --strict --metrics off`，让安全发现、规则或解析警告和内部错误都失败关闭，并禁止使用指标上报；扫描只在 GitHub Runner 内执行，不配置 Semgrep Token 或结果上传。
6. 运行 Semgrep、本地文本检查、Markdown 检查、工作区治理和模块边界检查，复读配置与差异。
7. 将生产部署摘要中的 GitHub 表达式全部转入步骤级环境变量，并在 Bash 中使用带引号的变量，避免工作流输入形成 Shell 注入。
8. 使用 Nginx `default_type` 声明健康响应类型，并为 uv 和 pnpm 增加七天新版本冷却期及 pnpm 供应链信任保护。
9. 提交推送后复验 Security 工作流。

## 风险与回滚

- 风险：Semgrep `p/default` 规则集由官方 Registry 持续维护，规则更新可能产生新的安全发现；这是安全规则数据库的预期更新行为，CLI 版本保持固定。
- 风险：Semgrep CE 不提供 GitHub Code scanning 告警面板和跨 Run 告警生命周期，结果以失败日志为准。
- 风险：Semgrep CE 与 CodeQL 的规则和数据流分析能力不同，不能宣称检测结果完全等价；当前方案满足个人私有仓库可执行、无云端账号和失败关闭要求。
- 风险：七天依赖冷却期会拒绝自动选择刚发布的版本；紧急安全修复需要在独立评审中明确调整冷却边界，不能通过关闭整个策略绕过。
- 风险：pnpm 信任策略和奇异传递依赖保护可能让新依赖安装失败；新增依赖时必须审查包来源、发布时间和信任变化。
- 风险：本地 Windows 验证无法完全替代 GitHub Ubuntu Runner，最终结论需要推送后观察线上工作流。
- 回滚：具备 GitHub Code Security 授权后，可在专项计划中恢复 CodeQL 并重新验证，禁止与 Semgrep 无期限双轨运行。
- 回滚：移除 `Get-Item` 的 `-Force` 可恢复原行为，但 Linux 点文件读取会重新失败。
- 回滚：四项新增修复均可按文件独立回退；回退部署环境变量会恢复 Shell 注入风险，回退依赖策略会恢复新发布依赖和信任降级风险。
