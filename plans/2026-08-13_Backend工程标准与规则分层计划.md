## 3. 背景

当前 `apps/backend/AGENTS.md` 已定义技术栈、分层、领域依赖、事务、数据库、安全、测试和契约同步等基本规则，能够约束工程骨架和早期设计，但尚未完整表达配置启动、Router 与 Schema、最外层事务、迁移不可变性、Redis、外部 HTTP、日志审计、健康探针和质量门禁等实现级标准。

项目现有 `module-boundaries.md`、`error-model.md`、`authentication-authorization.md`、`testing-strategy.md` 和 `observability-reliability.md` 分别承载跨应用或跨角色的专题架构契约。它们需要继续作为各主题的权威来源，不能被 Backend 工程手册复制或替代。

经讨论确认，项目采用两层 Backend 规则结构：`apps/backend/AGENTS.md` 保存长期红线、读取路由和执行边界；新增 `docs/architecture/backend-engineering-standard.md` 保存 FastAPI、Pydantic、SQLAlchemy、Alembic、PostgreSQL、Redis 和相关基础设施的具体实现标准。当前不新增独立 `constitution.md`。

## 4. 目标

1. 强化 `apps/backend/AGENTS.md`，使其能够作为 Backend 宪法级约束和 AI 执行入口。
2. 新增 Backend 工程标准，统一描述具体实现方式、禁止模式和验证要求。
3. 明确五份专题架构文档的权威职责和按任务读取条件。
4. 建立 `AGENTS.md`、Backend 工程标准、专题架构文档和运维手册之间的清晰引用关系。
5. 避免同一完整规则在多份文档重复维护，降低规则漂移和 AI 漏读风险。
6. 保持通用母版定位，不引入具体业务领域假设。

## 5. 非目标

1. 不新增独立 `constitution.md` 或其他同级最高权威文档。
2. 不删除、合并、移动或重命名现有五份专题架构文档。
3. 不修改 Router、Service、Repository、Model、Schema、测试或其他 Python 源码。
4. 不修改 `pyproject.toml`、环境变量模板、依赖锁文件、Alembic 迁移、CI、Compose 和部署工作流。
5. 不实现 Backend 启动、数据库连接、Redis、认证、审计、健康检查或可观测性能力。
6. 不为尚未实现的质量检查伪造已通过状态。
7. 不提交、推送、发布或部署本次修改。

- 五份专题架构文档已覆盖模块依赖、错误、认证授权、测试和可靠性主题。

### 6.2 主要缺口

- Backend 规则尚未明确按任务类型读取工程标准和专题文档的路由。
- 配置集中读取、生产必需项校验和启动失败策略缺少具体规范。

- 共享异步 HTTP Client、分项超时、有限重试和写入结果未知缺少统一写法。
- 结构化日志、关联 ID、敏感字段白名单和审计失败策略缺少 Backend 落地说明。
- Startup、Liveness 和 Readiness 的 FastAPI 实现要求与质量门禁命令尚未集中定义。

## 7. 方案设计

### 7.1 文档权威层级

```text
根 AGENTS.md
-> 全仓库长期规则和任务入口

apps/backend/AGENTS.md
-> Backend 宪法级约束、P0 禁令、读取路由和执行边界

docs/architecture/backend-engineering-standard.md
-> Backend 具体实现标准、禁止模式和验证命令

五份专题架构文档
-> 各主题跨应用、跨角色的唯一架构契约

docs/operations/
-> 本地启动、部署、备份、恢复和事故处理步骤
```

### 7.2 Backend 任务读取路由

任何 Backend 任务先读取根 `AGENTS.md`、`PROJECT_INDEX.md` 和 `apps/backend/AGENTS.md`。

- 仅讨论产品范围或高层原则时，按实际主题读取相关架构文档。
- 详细技术设计、实施计划、代码实现和代码评审必须完整读取 Backend 工程标准。
- 跨领域依赖、数据所有权和共享包变更读取 `module-boundaries.md`。
- API 错误、异常、外部调用和失败隔离读取 `error-model.md`。
- 身份、权限、资源授权和审计读取 `authentication-authorization.md`。
- 实施计划、代码实现、代码评审和完成验收读取 `testing-strategy.md`。
- 日志、Trace、健康探针、容量、可靠性和部署设计读取 `observability-reliability.md`。
- 本地启动、部署、备份、恢复和事故操作读取对应 `docs/operations/` 手册。

同一任务首次进入详细设计或实现阶段时完整读取一次 Backend 工程标准；标准发生变化、任务跨越较长周期或上下文无法确认时重新读取。

- AI 修改授权边界、必读文档路由和最小充分验证要求。
- 对 Backend 工程标准和五份专题文档的明确引用。

详细类模板、代码示例、配置字段、测试 Fixture 和完整命令序列不在 `AGENTS.md` 重复维护。

### 7.4 Backend 工程标准职责

新增 `docs/architecture/backend-engineering-standard.md`，包含：

1. 作用范围、规范词和权威引用表。
2. 配置集中管理、环境来源和生产启动 Fail Fast。
3. 应用工厂、Router 集中注册、依赖注入和传输层边界。
4. Pydantic Schema、响应契约、分页、时间和 OpenAPI 规范。
5. Service、最外层事务、嵌套调用、异常链和外部副作用。
6. Repository、SQLAlchemy async、加载策略、锁、并发和查询边界。
7. Model、约束、索引、时间、UUID、金额和 JSONB 规范。
8. Alembic revision 不可变性、禁止生产 `create_all`、迁移审查和验证。
9. Redis 权威边界、命名空间、TTL、缓存一致性和失败语义。
10. 外部 HTTP Client 生命周期、分项超时、有限重试、幂等和结果未知。
11. 结构化日志、`request_id`、`trace_id`、脱敏和审计失败策略。
12. Startup、Liveness、Readiness、优雅停机和事件循环阻塞禁令。
13. 测试落地、外部网络隔离、架构门禁和质量命令序列。
14. 代码评审清单和规则冲突处理方式。

工程标准只描述当前母版已经确定的约束。依赖具体运行源码才能确定的类名、路径、命令或实现细节应标为后续阶段 B 待落地，不虚构当前事实。
