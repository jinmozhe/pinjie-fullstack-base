# 开发迭代与 GitSync 分层验证规则计划

- 结果：已完成

## 关联需求

## 背景

当前规则要求按影响范围验证，但没有明确区分频繁开发迭代与最终 Git 交付。小范围修改期间重复运行独立 Playwright、Backend 全量 pytest 和 Admin 全量测试，会延长反馈周期，并且后续修改会使已经完成的全量结果失效。

用户确认本地修改最终通过显式 `$git-sync` 提交和推送，因此开发阶段只运行受影响的定向测试，三个耗时验证统一延后到 `$git-sync`，再按最终差异和影响范围执行。

## 目标

1. 明确开发迭代、功能交接和 `$git-sync` 三个验证时机。
2. 开发阶段只运行最小充分的定向测试，不默认启动独立 Playwright 或运行两端全量测试。
3. `$git-sync` 在最终差异上按影响范围运行 Backend 全量 pytest、Admin 全量测试和条件式 Playwright。
4. 未调用 `$git-sync` 时，交付说明明确标记全量验证待执行。
5. 同步根规则、Backend、Admin 和测试策略；通用 `git-sync` Skill 保持项目中立，通过读取仓库规则获得本项目验证要求。

## 非目标

1. 不降低覆盖率阈值、测试质量、CI 门禁或合并保护。
2. 不要求每次 `$git-sync` 无条件运行与改动无关的全量测试。
3. 不修改测试框架、测试脚本、GitHub Actions 或产品代码。
4. 本计划不执行提交、推送、PR 或自动合并。
5. 不修改个人 `git-sync` Skill 或其他仓库外规则。

## 现状分析

- 根规则要求最小充分验证，同时又要求应用进入 `ready` 后运行全部质量命令，缺少执行时机说明。
- Backend 规则把全量 pytest 列为完成门禁，没有区分定向反馈与最终交付。
- Admin 规则要求功能改动运行测试和适用 E2E，没有区分定向 Vitest 与完整覆盖率命令。
- `git-sync` Skill 已按通用方式要求读取仓库 `AGENTS.md`、任务计划并按影响范围验证，无需写入本项目命令。

## 方案设计

### 开发阶段

- 只运行直接受影响的测试文件、测试类或测试用例。
- 不默认运行 Backend 全量 pytest、`pnpm --filter @pinjie/admin test` 或独立 Playwright。
- 类型检查、Lint、构建和契约生成继续按实际影响与现有规则执行。

### GitSync 阶段

- Backend 受影响时运行 Backend 全量 pytest。
- Admin 受影响时运行 `pnpm --filter @pinjie/admin test`。
- 页面布局、交互、路由、浏览器认证、文件上传或关键跨栈流程受影响时运行独立 Playwright。
- 全量验证必须基于准备提交的最终差异；验证后继续修改相关代码时，重新运行对应验证。
- 任一适用验证失败时停止提交和推送。

### 状态表达

- 未调用 `$git-sync` 时可以报告本地实现和定向验证结果，但必须把适用的全量测试标记为“待 `$git-sync` 执行”。
- 未执行的全量测试不得表述为通过、可合并或完整跨栈验收完成。
- 用户明确要求提前运行某项全量验证时，按本次授权执行并如实记录。

## 风险与回滚

- 风险：开发阶段只跑定向测试可能延后发现跨模块回归。通过 `$git-sync` 对最终差异执行受影响应用全量测试，并在失败时阻止提交和推送。
- 风险：将 Playwright 机械绑定到每次同步仍会浪费时间。只在浏览器行为或关键跨栈流程受影响时执行。
- 风险：未调用 `$git-sync` 时出现验证状态误解。最终说明强制列出待执行全量验证。
- 回滚：恢复本计划涉及的规则和策略条目，不影响产品代码、数据和既有测试资产。
