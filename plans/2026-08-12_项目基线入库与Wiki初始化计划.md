## 3. 目标

1. 修复根 `.env.example`，使其成为 UTF-8 无 BOM、内容可读且仅包含公开模板值的部署层变量模板。
2. 审计并提交剩余项目基线文件，使远程主仓库具备完整、可导航的 Monorepo 骨架。
3. 运行当前项目已具备条件的最小充分验证，明确尚未生成的依赖锁文件和尚未实现的运行代码。
4. 推送当前 `main` 分支。
5. 初始化同名 GitHub Wiki，并以推送后的主仓库 `HEAD` 为唯一来源同步 `docs/` 下全部已跟踪文件。
6. 保持真实环境变量、密钥、缓存、构建产物和未入库工作区内容不进入主仓库或 Wiki。

## 4. 非目标

1. 不实现 Backend、Admin 或 Web 业务代码。
2. 不新增尚未确认的依赖，不伪造 `pnpm-lock.yaml` 或 `apps/backend/uv.lock`。
3. 不修改根 `openapi.json` 或 `packages/api-client/src/` 的生成语义。
4. 不发布 GHCR 镜像，不执行部署或生产变更。
5. 不删除、移动或重命名任何现有计划文档。

## 5. 现状分析

1. 主仓库 `main` 当前只有治理基线提交 `3b4e262`。
2. 48 个未跟踪文件包括应用级规则、Antigravity 桥接、环境模板、GitHub Actions、应用配置、共享包、Compose、ADR、架构原始方案、蓝图和运维文档。

4. `.gitignore` 已忽略真实 `.env`、依赖目录、缓存和构建产物，并允许提交 `.env.example`。
5. GitHub Wiki 远程尚不存在，需要先创建首页完成初始化，再按 `git-sync` 规则同步主仓库 `HEAD` 中全部 `docs/`。

## 6. 方案设计

1. 根据 `compose.prod.yml` 的实际变量，重写根 `.env.example`，只保留 `GITHUB_ORG`、`IMAGE_TAG` 和公开占位值。
2. 对全部剩余文件执行文本卫生、Markdown 链接、JSON/YAML/TOML/INI 解析、常见秘密模式和忽略规则检查；同步修复审计发现的既有乱码和换行损坏。
3. 按当前已配置脚本执行可用的静态验证；缺少依赖或运行源码时明确记录跳过原因，并通过工作流就绪门禁阻止骨架阶段误触发无效构建或部署。
4. 显式暂存本计划确认的全部剩余项目基线文件和本次治理回写文件，不使用 `git add .` 或 `git add -A`。
5. 提交并推送主仓库后，通过 GitHub 页面初始化 Wiki。
6. 将 Wiki 克隆到系统临时目录，以主仓库新 `HEAD` 导出的 `docs/` 为唯一来源，同步全部文件并维护 `.docs-sync-manifest`，提交信息包含主仓库完整 SHA。

## 10. 风险与回滚

1. 风险：公开模板包含真实凭据。控制方式是逐项检查占位值并运行常见秘密模式扫描。
2. 风险：骨架配置之间存在路径或变量漂移。控制方式是核对 Compose、工作流、README 和结构文档的引用关系。
3. 风险：依赖尚未安装导致无法运行构建。控制方式是只执行当前具备条件的检查，缺失项进入剩余问题。
4. 风险：Wiki 初始化或推送失败。控制方式是主仓库与 Wiki 分开提交，Wiki 失败不回滚主仓库。
5. 风险：Wiki 同步覆盖独立页面。控制方式是使用 `.docs-sync-manifest`，只管理从 `docs/` 同步的路径。
6. 回滚：主仓库和 Wiki 均通过后续普通提交修正，不改写历史；环境模板可依据本计划记录恢复。外部发布和部署不在本次范围。
