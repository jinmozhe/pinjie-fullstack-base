## 目标

1. 升级 Admin 运行镜像中当前 Alpine 仓库能够修复的全部已安装包。
2. 保持 Trivy `HIGH/CRITICAL`、`--ignore-unfixed` 和非零退出门禁不变。
3. 扫描失败时在 CNB 日志输出精简漏洞表格。
4. 扫描失败时保存原始 JSON、已生成的 digest、metadata 和精简摘要附件。
5. 通过模拟 Trivy 的自动测试覆盖 Admin 阻断和三镜像全部通过两条路径。
6. 完成 Git 交付后重新执行 Full Validation、GitHub 到 CNB 源码交接和 CNB 到 TCR 发布，直到三张正式 SHA 镜像成功。

## 非目标

- 不降低漏洞严重级别，不忽略已有修复版本的漏洞。
- 不使用失败 Run 的 `candidate-*` 镜像部署。
- 不在本地构建三张镜像。
- 不触发生产服务器部署、数据库迁移、回滚、Tag、Release 或 GHCR 发布。
- 不修改 Admin 页面逻辑、接口契约或 UI。

## 现状分析

- Backend 与 Web 候选镜像扫描完成，Admin 扫描返回代码 `1`。
- Admin 候选镜像运行层来自固定 digest 的 `nginx:1.29-alpine`，扫描识别为 Alpine 3.23。
- Admin Dockerfile 的 `apk upgrade` 带有固定包名列表，列表外的已安装包不会升级。
- `cnb-scan-images.sh` 使用 JSON 文件输出和 `--exit-code 1`，因此失败详情不会进入标准输出。
- `.cnb.yml` 只在正常阶段保存附件，扫描失败后没有可下载的原始证据。

## 方案设计

### Admin 运行镜像

保留固定基础镜像 digest、Nginx 配置、非 Root 用户和健康检查，只把定向包升级改为
`apk upgrade --no-cache`，使用镜像当前已配置的 Alpine 仓库升级全部已安装包。

### 扫描日志

每张镜像先生成退出码固定为零的原始 JSON。随后使用同一严重级别和
`--ignore-unfixed` 参数生成表格并执行阻断。阻断时把镜像引用和表格写入
`scan-failure-summary.txt`，同时输出到 CNB 日志，再返回原始非零状态。

### 失败附件

CNB `failStages` 在正常阶段失败后执行。它保证存在失败摘要，将当前证据目录打包为
`cnb-failure-evidence.tar.gz`，再使用固定 digest 的附件插件保存。临时 Docker 登录配置位于证据目录外，
不会进入附件；`endStages` 继续执行凭证清理。

### 自动验证

新增 Node 夹具，使用临时目录和模拟 Trivy 命令验证：

1. Admin 漏洞返回非零，摘要包含镜像、CVE 和修复版本，原始 JSON 保留。
2. Backend 和 Web 已完成证据保留，Admin SBOM 不被伪造为成功。
3. 三镜像无阻断漏洞时生成三份 JSON 与三份 SBOM，且不残留失败摘要。

## 风险与回滚

- **完整升级引入行为变化**：只升级同一 Alpine 分支当前仓库中的已安装包，保留固定基础镜像和 Nginx 主版本；CNB 健康、扫描和 Full Validation 失败时停止发布。
- **扫描时间增加**：表格阻断扫描复用同一 Trivy DB 和镜像缓存，只增加一次候选分析；以真实 CNB 分阶段耗时复核。
- **扫描器故障被误认为漏洞**：JSON 或表格命令异常同样失败，摘要明确记录失败阶段，不把异常表述为漏洞通过。
- **失败附件泄密**：只归档 `.cnb/evidence`；Registry 用户名、密码和 Docker 配置均不在该目录。
- **附件插件失败**：原始流水线状态仍为失败，日志摘要保留；附件失败不能把发布改为成功。
- **回滚**：通过普通反向提交恢复 Dockerfile、扫描脚本和 CNB 配置；已存在候选标签和历史构建记录不删除。
