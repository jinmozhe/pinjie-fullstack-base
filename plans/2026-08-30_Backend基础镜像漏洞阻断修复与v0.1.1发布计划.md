## 背景

`v0.1.0` 对应提交 `230de3cda8ee7c46c144cb254d4f05e3d73dffdd` 的完整远端验证已经通过，但 `Publish Images` Run `33267308587` 在 Backend 候选镜像的 Trivy 扫描阶段失败。扫描发现 Debian 39 个 High 和 Python 2 个 High，Critical 为 0；Web 与 Admin 矩阵任务随后因 `fail-fast` 被取消，最终不可变标签没有发布。

Backend Dockerfile 固定的 `python:3.14.7-slim-trixie` Linux amd64 digest 已落后于 Docker Hub 当前同标签摘要。漏洞包未出现在项目 `pyproject.toml` 或 `uv.lock` 中，修复应从固定基础镜像版本入手，并由新的候选镜像扫描证明结果。

Backend 修复后的第二次发布 Run `33270084793` 已证明 Backend 候选镜像通过 Trivy、SBOM、provenance 和 digest 证据门禁，但同时暴露 Web 与 Admin 运行基础层的新漏洞。Web 包含 Alpine OpenSSL 2 个 High，以及官方 Node 镜像全局 npm 目录中的 7 个 High 和 1 个 Critical；Admin 的 Alpine 3.23.4 运行层包含 13 个 High。计划范围因此扩展到三端生产运行镜像，继续使用同一计划完成发布闭环。

## 目标

1. 更新 Backend 的固定 Python 基础镜像 digest，同时保留标准 CPython 3.14.7 slim-trixie 技术基线。
2. 升级 Web 与 Admin runtime 中已存在修复版本的 Alpine 系统包，并从 Web runtime 移除运行不需要的全局 npm 工具链。
3. 保持 Trivy High/Critical Fail Closed、SBOM、provenance 和同 SHA 完整验证门禁不变。
4. 通过功能分支、Pull Request 和 rebase 合并把修复交付到 `main`。
5. 对同一新提交完成远端完整验证并成功发布 Backend、Web、Admin 三张 GHCR 镜像，取得三个固定 digest。
6. 为镜像发布成功的同一提交创建不可变 `v0.1.1` Tag 和正式 GitHub Release。

## 非目标

- 不移动、覆盖或删除现有 `v0.1.0` Tag 和 GitHub Release。
- 不降低、跳过或增加 Trivy 漏洞豁免。
- 不触发生产部署，不连接生产服务器，不修改生产配置或 Secret。
- 不修改应用业务逻辑、公开 API、数据库模型、迁移、Admin 或 Web 产品功能。

## 现状分析

- 完整验证 Run `33266778572` 已证明 `v0.1.0` 源码通过 pytest、Vitest、production build 和 Playwright，但证据只能绑定原提交。
- Backend 候选镜像扫描失败是发布根因；Web 与 Admin 的失败状态来自矩阵取消，不能解释为各自独立漏洞或构建缺陷。
- 旧基础镜像 digest 为 `sha256:ce40764625a4ff50df3548277632e7f96c4e77fe75fa848aae9885476e7df5a4`。
- Docker Hub 官方 API 返回当前 Linux amd64 digest 为 `sha256:5b945726c4d7ffe6595dc7498ad17fd0397e373c5181c24819a7028e8b1276dc`。
- 基础镜像 digest 更新会产生新 Commit SHA，因此必须重新获得四项 Push 工作流和同 SHA 完整验证 Artifact。
- Web Run `33270084793` 的 Trivy 路径证据显示 Node 漏洞全部位于 `/usr/local/lib/node_modules/npm/`，Next standalone 应用自身未报告 High/Critical；runtime 只通过 `node apps/web/server.js` 启动，不需要 npm 或 npx。
- Admin 同一 Run 的 13 个 High 全部来自 Alpine 系统包，修复版本已在 Trivy 数据库中登记；候选镜像构建时应只升级命中的运行包，避免修改 Nginx 配置和前端静态产物。

## 方案设计

1. 将 Backend builder 与 runtime 阶段统一固定到 Docker Hub 当前的 Python 3.14.7 slim-trixie Linux amd64 digest。
2. 若更新摘要后仍有基础镜像可修复漏洞，在 runtime 精确安装已修复的系统包；移除生产运行不需要且携带脆弱 vendored 代码的全局构建工具，不修改应用 `.venv` 锁定依赖。
3. Web runtime 仅升级命中的 OpenSSL 包并删除全局 npm 目录及 npm/npx 入口，保留 Node、standalone 产物、健康检查和非 Root 用户不变。
4. Admin runtime 仅升级 Trivy 命中的 c-ares、curl、OpenSSL、libexpat、libxml2 和 nghttp2 包，保留 Nginx 配置、静态产物、健康检查和非 Root 用户不变。
5. 运行仓库轻量门禁、Markdown lint、工作区与边界检查，确认代码和文档无漂移。
6. 在 `pre-pr` 收尾中同步本计划、计划索引、项目索引和 Changelog；发布运维手册已经覆盖候选镜像漏洞修复与重走验证链路，无需重复修改。
7. 提交并推送功能分支，创建目标为 `main` 的 Pull Request，等待必需检查后以 rebase 方式合并。
8. 等待合并提交对应的 Governance、Backend、Frontend 和 Security 四项 Push 工作流全部成功。
9. 人工触发同 SHA `CI - Full Validation`，成功后触发 `Publish Images`。
10. `Publish Images` 成功并核对三个 digest 后，创建 `v0.1.1` Tag 和正式 GitHub Release，全部绑定同一提交。
11. 若候选镜像扫描仍失败，保留安全门禁并依据新日志继续修复，通过新的提交和完整验证重走发布链路。

## 风险与回滚

- 新基础镜像可能仍包含 High/Critical 漏洞。回滚方式是停止发布并依据 Trivy 证据选择后续修复版本，禁止关闭扫描。
- 基础镜像更新可能改变系统库行为。由完整 pytest、production build 和 Playwright 验证应用行为，由三镜像扫描验证供应链门禁。
- 已发布 Tag 不允许移动。合并前可通过普通反向提交回滚；`v0.1.1` 发布后发现问题时创建后续修复版本，不覆盖现有 Tag、Release 或镜像标签。
- GHCR 候选内容可能在最终标签创建前可见。只有整个 `Publish Images` 工作流成功且 Summary 给出三个 digest 后才能用于部署。
