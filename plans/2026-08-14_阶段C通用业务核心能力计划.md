## 3. 背景

阶段 B 已建立可运行的 Backend、Admin、Web、OpenAPI、生成 API Client、数据库、Redis、测试和容器基础。当前仓库仍没有登录、会话、用户账户、管理员、RBAC、安全审计和对应前端流程。

`pinjie-standard` 提供通用后端骨架，已经实现 C 端密码与短信认证、B 端认证、角色权限、菜单、登录日志、审计日志和请求日志。`fastapi-mini-standard` 在此基础上增加电商领域，并修复了事务所有权、可信代理、审计失败策略、请求日志可靠性和依赖装配等问题。两个项目都能提供实现证据，但其 Bearer Token、Redis 会话权威、手机号与第三方登录、JSONB 权限集合和部分旁路失败策略不能直接成为本母版契约。

阶段 C 必须先回答以下问题：

1. 母版默认支持哪些登录方式、会话和账户功能。
2. JWT 的算法、Claims、有效期、校验和失效规则是什么。
3. 浏览器如何保存凭据，如何防止 CSRF、Token 泄露和 C/B 端混用。
4. Middleware、Dependency、Router、Service、Repository 各自负责什么。
5. RBAC、用户、管理员、会话、日志和审计使用哪些表及约束。
6. 哪些日志必须阻断高风险操作，哪些可作为异步观测信号。
7. Admin 与 Web 要交付哪些真实页面、状态和端到端旅程。

## 4. 目标

1. 交付用户名与密码的 C 端注册、登录、刷新、退出、当前用户、资料、密码和会话管理。
2. 交付独立的 B 端管理员登录、刷新、退出、当前管理员和敏感操作二次确认。
3. 交付用户管理、管理员管理、角色管理、权限目录和角色授权。
4. 交付 PostgreSQL 权威、Redis 加速的单次使用 Refresh Token Rotation 和整族重放撤销。
5. 交付 Cookie 会话、CSRF、可信来源校验、登录限流、账号状态和凭据版本失效。
6. 交付应用访问日志、登录安全事件、业务审计事件和可选请求元数据日志的明确分工。
7. 交付 Admin 登录与受保护布局、用户与 RBAC 管理、日志查询页面。
8. 交付 Web 注册、登录、退出、用户中心和会话管理页面。
9. 同步 OpenAPI、生成 API Client、数据库迁移、初始化工具和跨栈测试。
10. 保持母版业务中立，派生项目可以增加短信、微信、邮件、组织、租户和具体业务领域。

## 5. 非目标

1. 不实现短信验证码、微信、OAuth 社交登录、邮箱验证和找回密码服务。
2. 不实现商品、订单、支付、退款、佣金、钱包、媒体等电商领域。
3. 不实现复杂 ABAC、组织树、多租户、数据范围权限和跨组织委派。
4. 不实现 OAuth2 Authorization Server、第三方 API Key、机器账号和服务间身份。
5. 浏览器 Profile 不把 Access Token、Refresh Token 或管理员确认 Token 保存到 `localStorage`、Zustand、URL 或页面源码；未来公开客户端 Profile 必须使用独立安全契约。
6. 不提供运行时创建、修改或删除权限代码的功能。权限代码由源码目录维护。
7. 不使用数据库动态配置保存密钥、密码、JWT Secret、Cookie Secret 或数据库连接。
8. 不把完整请求体、响应体、Authorization、Cookie、密码或 Token 保存到日志表。
9. 不迁入参考项目的默认管理员密码、真实连接信息、上传目录、缓存、数据库或业务数据。
10. 不在本轮修改源码。本轮只完成计划、SPEC 和项目索引同步。

## 6. 现状分析

### 6.1 本项目前置事实

- Backend 已有标准 CPython 3.14、FastAPI、Pydantic v2、SQLAlchemy 2 async、asyncpg、Alembic、PostgreSQL、Redis、Loguru 和 uv。
- `ResponseModel[T]` 当前成功响应为 `code/message/data/request_id`，错误响应为 `code/message/details/request_id`。
- `request_context_middleware` 已生成或接收受限格式的 `request_id` 与 `trace_id`，并设置基础安全响应头。
- 数据库请求会话和嵌套事务工具已存在，最外层 Application Service 必须拥有提交与回滚。
- Redis 由应用生命周期创建，当前支持 `disabled` 和 `required` 两态。
- 标准库 `uuid.uuid7()` 已通过 `app/core/identifiers.py` 统一封装，阶段 C 不引入 `uuid6` 或 `uuid-utils`。
- Admin 与 Web 已接入 Vitest、RTL、jsdom、MSW、Playwright 和 axe 基础设施。

### 6.2 `pinjie-standard` 的具体实现

| 能力 | 当前实现证据 | 行为摘要 |
| --- | --- | --- |
| 密码与 JWT | `app/core/security.py` | `pwdlib` Argon2id 在线程池执行；PyJWT 使用单一 `SECRET_KEY` 和可配置 `ALGORITHM`；Access Claims 只有 `sub`、`exp`、`type=access` 和可选扩展 |
| C 端身份 | `app/api/deps.py` | 从 `Authorization: Bearer` 取 Token；C 端只拒绝 `aud=backend`，没有强制 C 端 audience；查库检查用户存在、未删除、激活 |
| B 端身份 | `app/api/deps.py` | 强制 `aud=backend`，读取 `tv` 并与管理员 `token_version` 比较；预加载角色 JSONB 权限码 |
| C 端会话 | `app/domains/auth/service.py` | Access 默认 30 分钟；Refresh 默认 7 天；会话绝对上限 30 天；Redis `RENAME` 消费旧 Token，重放时撤销当前族；`user_sessions` 只作审计记录 |
| B 端会话 | `app/domains/admin/service.py` | Refresh Token 与 Session ID 都是随机串；Redis 保存 Token 到 Session、Session 到 Admin 映射；重放撤销会话；数据库没有 B 端会话权威记录 |
| 浏览器契约 | auth/admin schemas 与 routers | Access 和 Refresh 都返回 JSON，由调用方保存；刷新与退出通过请求体提交 Refresh Token；没有 Cookie 与 CSRF 契约 |
| 统一响应 | `app/core/response.py`、`exceptions.py` | 成功和失败都使用 `ResponseModel`；额外包含 `timestamp`；校验错误被改成 HTTP 400，详情放在 `data.errors` |
| 请求中间件 | `app/core/middleware.py` | 生成 UUID v7 请求 ID，接受合规客户端 `X-Request-ID`，直接信任 Cloudflare 和 `X-Forwarded-For`，记录访问日志和安全头 |
| 审计中间件 | `app/core/audit.py` | 拦截 `/admin/`，按路径和方法推断动作，截取并脱敏请求体，使用独立 Session 写库；失败记录错误后放行 |
| 请求日志 | `app/core/request_persist.py` | 可采样抓取请求与响应，推入 Redis List，后台批量写 `sys_request_logs`；入队或写库失败主要记录错误 |
| 限流 | `app/core/rate_limit.py` | Redis Sorted Set 滑动窗口，由多条非原子命令组成；Redis 异常时放行 |
| RBAC | `app/db/models/admin.py`、admin routers | 管理员与角色多对多；角色以 JSONB 保存 `permission_codes`；权限和菜单支持运行时 CRUD；超级管理员绕过权限集合 |
| 初始化 | `scripts/seed_admin.py`、`sync_permissions.py` | 当前提交中的管理员脚本含公开默认密码；权限通过正则扫描 `require_permission` 调用后同步 |
| 测试 | `tests/` | 有应用、迁移、回滚、配置和少量权限测试；认证 Rotation、Cookie、CSRF、重放和完整 RBAC 失败路径覆盖不足 |

### 6.3 `fastapi-mini-standard` 的演进细节

| 能力 | 相对 `pinjie-standard` 的变化 | 可借鉴结论 |
| --- | --- | --- |
| 可信代理 | 只在直连地址属于 `TRUSTED_PROXY_CIDRS` 时读取转发头，并补充 Trusted Host、HTTPS 与更多安全头 | 真实 IP 必须由一个可信入口解析，安全依赖不得自行重复猜测 |
| 可选身份 | 仅完全未提供 Token 时返回匿名；提供了损坏或过期 Token 时返回 401 | 可选身份不能吞掉无效凭据 |
| 请求主体关联 | Dependency 把 `current_user_id` 或 `current_admin_id` 写入 `request.state` | 横切日志可读取已经认证的主体，但不能代替 Service 授权 |
| 事务 | 增加 `app/db/transaction.py` 和 `@transactional`，最外层事务提交，失败回滚并补偿 Redis Key | 本项目沿用已有 `transaction_scope`，令牌和数据库跨资源写入必须有补偿顺序 |
| 依赖装配 | 增加 `app/services/auth/dependencies.py`、admin 工作流和 Port | 跨领域组合进入 Application Service，Router 不实例化 Repository |
| 登录日志 | `DatabaseLoginAuditWriter` 使用独立事务，写入失败关闭登录入口 | 登录安全事件属于认证结果的一部分，不能静默丢失 |
| 业务审计 | 管理工作流把业务变更与 `record_audit_log` 放入同一事务，并测试审计失败回滚 | 语义化审计应位于 Service，不依赖路径推断 |
| 审计预写 | 管理写请求先写 `response_status=102` 意图，失败返回 503，完成后更新结果 | 可用于补充网络层证据，但 Service 事务审计仍是业务事实来源 |
| 请求日志 | 增加本地 spool、ready/processing 队列、消费者心跳、孤儿恢复、死信和 ACK 后删除 | 异步日志必须定义确认、恢复和死信，简单 List 消费不足以证明可靠 |
| 限流 | 改为 Redis `INCR` 固定窗口，Redis 故障返回 503 | 安全限流必须 Fail Closed；仍需把自增和 TTL 建立合并为原子操作 |
| Redis Key | 增加项目与环境命名空间 | 本项目还需增加领域、用途和版本段，且 Key 中不得出现原始 Token 或用户名 |
| 初始化管理员 | 密码改为环境变量必填，长度至少 12；没有默认密码；重置时递增 `token_version` | 采用一次性显式 CLI 和无默认凭据 |
| 测试 | 增加事务、审计回滚、Redis 命名空间、请求日志恢复、迁移安全和真实 PostgreSQL 测试 | 结构测试有价值，但阶段 C 还必须补真实 Cookie、CSRF、Rotation 和跨栈旅程 |

### 6.4 两个参考项目的通用 API 面与真实调用链

两个参考项目通过 `app/api_router.py` 聚合路由，再由应用入口统一挂载到 `/api/v1`。阶段 C 只参考其中跨业务通用部分，`fastapi-mini-standard` 的电商路由不进入本母版。

| 分组 | 两个参考项目已有端点 | 当前请求与响应契约 | 阶段 C 处理 |
| --- | --- | --- | --- |
| C 端认证 | `POST /auth/register`、`/login`、`/refresh`、`/logout`、`/sms/send`、`/sms/login`、`/password` | 登录和注册返回 JSON Access/Refresh 双 Token；刷新和退出从请求体读取原始 Refresh Token | 保留用户名密码主流程，移除短信；改为 HttpOnly Cookie、CSRF 和无 Token 响应 |
| C 端扩展认证 | mini 增加 `/auth/wechat/login`、`/bind/wechat`、`/wechat/scan`、`/wechat/complete` | 微信身份、扫码状态和手机号绑定进入认证 Service | 归入派生项目，不进入阶段 C |
| C 端用户 | `GET/PATCH/DELETE /users/me` | Bearer Access Token 解析后读取、修改或软删除当前用户 | 保留并补充密码、会话列表、会话撤销与注销证据保留 |
| B 端认证 | `POST /admin/login`、`/refresh`、`/logout`、`/password`、`/security/confirm`、`/token/revoke-current`，`GET /admin/me` | JSON 双 Token；敏感确认返回短时 Token；管理员 Access 带 `aud=backend` 和 `tv` | 改为独立 B 端 Cookie、Secret、audience、Session、CSRF 和一次性确认 Token |
| 管理员 | `/admin/admins` 列表、新增、详情、编辑、删除、启停、重置密码和分配角色 | `require_permission()` 负责端点权限，Service 执行状态保护 | 保留管理能力，改用独立状态、凭据和会话端点，增加最后超级管理员与自操作约束 |
| 角色权限 | `/admin/roles` CRUD、排序与权限分配；`/admin/permissions` CRUD 与分组 | 角色以 JSONB 数组保存权限码，权限表可运行时修改 | 改为关系表；源码权限目录权威；Admin 只读目录并只分配已登记权限 |
| 菜单 | `/admin/menus` 返回当前管理员菜单树；`/admin/menu-items` 运行时 CRUD | 菜单、权限与路由分别维护 | 阶段 C 不建动态菜单表，前端代码维护导航并按服务端权限过滤 |
| 运维日志 | `/admin` 下提供登录日志、审计日志、请求日志、仪表盘和系统配置接口 | `ResponseModel` 包络分页结果；权限码控制查询和配置写入 | 保留三类安全日志查询；动态系统配置和业务仪表盘排除 |

两个参考项目的认证与授权执行链如下：

1. Router 接收 Pydantic 请求体，调用领域 Service，使用 `ResponseModel.success()` 返回统一包络。
2. `app/core/security.py:create_access_token()` 使用 PyJWT、单一 `SECRET_KEY` 和配置算法签发 Access Token。基础 Claims 只有 `sub`、`exp`、`type=access`，B 端通过 `extra_claims` 增加 `aud=backend` 和 `tv`。
3. `app/api/deps.py:get_token_from_header()` 从 `Authorization: Bearer` 提取 Token。`get_current_user()` 和 `get_current_admin()` 调用 `jwt.decode()` 并查 PostgreSQL 主体状态，JWT 解析没有放在 Middleware。
4. C 端关闭 PyJWT audience 自动校验，只手工拒绝 `aud=backend`。B 端也关闭自动校验，再手工要求 `aud=backend` 并核对管理员 `token_version`。两端都没有强制 `iss`、`sid`、`jti`、`iat`、`nbf` 和 `token_type` 完整 Claims。
5. `require_permission()` 合并管理员所有角色的 JSONB `permission_codes`。超级管理员直接通过，普通管理员按字符串集合判断；资源归属与目标状态仍由具体 Service 自行处理。
6. C 端 `AuthService.refresh_token()` 以原始 Refresh Token 拼 Redis Key，通过 `RENAME` 把可用 Key 移到 consumed Key。首个请求生成新 Token，旧 Token 再次出现时按 Session Family 撤销；`user_sessions` 记录设备与活跃信息，但不承担 Token 单次消费权威。
7. B 端同样以 Redis 保存 Refresh Token、Session 与管理员映射，数据库只有管理员 `token_version`，没有独立的管理员 Session 与 Refresh Token 权威表。
8. `RequestLogMiddleware` 建立 request ID、真实 IP、Loguru 上下文、访问日志和安全响应头。`fastapi-mini-standard` 增加可信代理 CIDR、Trusted Host 和可选 HTTPS 跳转；身份 Dependency 在认证成功后把主体 ID 写入 `request.state`，供后续日志关联。
9. `AuditLogMiddleware` 处理管理端写请求。`pinjie-standard` 按 URL 和方法推断动作且失败放行；mini 增加意图预写和 503 失败关闭，并在部分 Application Service 中把语义化审计与业务变更放入同一事务。
10. 请求持久化由 Middleware 采集后异步入 Redis，再由消费者写 PostgreSQL。pinjie 使用简单 List；mini 增加 spool、processing、ACK、孤儿恢复与死信。阶段 C 将统一为无正文的 Redis Stream metadata 模式。

统一响应方面，两个参考项目的成功与失败都使用 `code/message/data/request_id/timestamp`，异常处理器把校验错误改为 HTTP 400，并把错误数组放入 `data.errors`。本项目阶段 B 已有 `ResponseModel` 与独立 `ErrorResponse`，所以阶段 C 延续 `code/message/data/request_id` 成功包络、`code/message/details/request_id` 错误包络和 HTTP 422 校验语义，避免响应时间戳与失败数据字段形成第二套契约。

## 7. 方案设计

### 7.1 功能边界和角色

| 角色 | 阶段 C 可执行操作 |
| --- | --- |
| 匿名用户 | 注册、登录、刷新已有会话；访问公开系统状态 |

### 7.3 模块和职责

```text
HTTP Request
  -> Middleware: Request/Trace、可信来源、访问日志、安全响应头
  -> Dependency: Cookie、CSRF、JWT、会话、当前主体、端点权限
  -> Router: HTTP 参数、状态码、ResponseModel
  -> Application Service: 用例、事务、资源授权、审计、跨领域 Port
  -> Domain Service/Policy: 纯规则和状态转换
  -> Repository: SQL 查询、锁、flush、refresh
  -> PostgreSQL: 用户、管理员、RBAC、会话、登录事件、审计事实
  -> Redis: 限流、锁、缓存、短时确认、请求日志 Stream
```

- JWT 解析不进入 Middleware。Middleware 无法可靠表达公开、可选身份和不同 audience，也不应为所有请求强制查会话。
- Router 不创建 Repository，不执行 SQL，不提交事务，不拼装权限集合。
- Dependency 完成身份真实性、会话有效性和端点权限入口；Service 在事务中检查目标资源与最终授权。
- Service 写入业务变更时，同一事务写入语义化审计事件。审计失败必须回滚高风险变更。
- 登录失败事件使用独立事务，因为失败登录没有可提交的业务事务。

### 7.4 统一响应与错误 SPEC

阶段 C 保留当前项目契约，不复制参考项目的 `timestamp` 和失败 `data`：

```json
{
  "code": "OK",
  "message": "OK",
  "data": {},
  "request_id": "019..."
}
```

```json
{
  "code": "AUTH_SESSION_EXPIRED",
  "message": "登录状态已失效",
  "details": null,
  "request_id": "019..."
}
```

| 场景 | HTTP | 业务码 |
| --- | --- | --- |
| Pydantic 字段错误 | 422 | `VALIDATION_ERROR` |
| 用户名重复 | 409 | `USER_USERNAME_CONFLICT` |
| 登录凭据错误 | 401 | `AUTH_INVALID_CREDENTIALS` |
| Access 缺失、过期、签名或 Claims 无效 | 401 | `AUTH_REQUIRED` 或 `AUTH_TOKEN_INVALID` |
| 会话撤销、绝对过期或 Token 重放 | 401 | `AUTH_SESSION_REVOKED`、`AUTH_SESSION_EXPIRED`、`AUTH_REFRESH_REUSE_DETECTED` |
| 已认证但账号停用 | 403 | `AUTH_ACCOUNT_DISABLED` |
| CSRF 或来源校验失败 | 403 | `CSRF_REJECTED` |
| RBAC 权限不足 | 403 | `PERMISSION_DENIED` |
| 目标不存在 | 404 | `USER_NOT_FOUND`、`ADMIN_NOT_FOUND`、`ROLE_NOT_FOUND` |
| 状态冲突或最后超级管理员保护 | 409 | `STATE_CONFLICT`、`LAST_SUPERUSER_PROTECTED` |
| 登录或敏感接口超限 | 429 | `RATE_LIMITED`，响应包含 `Retry-After` |
| Redis、安全审计或会话权威依赖不可用 | 503 | `SERVICE_UNAVAILABLE` |

错误 `details` 只包含字段位置、稳定原因码或安全的重试信息。登录响应不能说明用户名是否存在。未知异常只返回通用 500，完整堆栈只进入服务端结构化日志。

### 7.5 C 端账户与认证 SPEC

1. 母版默认使用小写规范化用户名和密码注册，用户名 3 至 50 个字符，允许字母、数字、点、下划线和连字符。
2. 密码长度 12 至 128 个 Unicode 字符，不强制特殊字符组合，不做静默截断或自动空白修剪。
3. 邮箱为可选资料字段，阶段 C 不声称已验证，不用它执行登录和找回。
4. `REGISTRATION_MODE` 只允许 `open` 或 `closed`。生产必须显式配置；`closed` 返回 403，不伪装成功。
5. 注册、登录和密码修改在提交前完成限流。用户名不存在时执行固定的虚拟密码校验，减少明显时序差异。
6. 登录成功必须在同一 PostgreSQL 事务内创建会话、首个 Refresh 摘要和成功登录事件，事务提交后才能设置 Cookie。
7. 修改密码需要当前密码，成功后递增 `credential_version` 并撤销除当前会话之外的全部会话；当前会话重新签发 Access 和 Refresh。
8. 注销账户需要当前密码与 CSRF，撤销全部会话，清除登录标识并匿名化可识别资料，保留最小审计关联。注销不能物理删除安全事件。
9. 可选身份只在完全没有 C 端 Access Cookie 时返回匿名。Cookie 存在但损坏、过期或失效时返回 401。

### 7.6 B 端管理员认证 SPEC

1. B 端使用独立 Cookie、JWT Secret、`aud`、会话表、Refresh 表、限流桶和 CSRF Token。
2. 管理员由显式初始化 CLI 或已授权管理员创建，禁止公开注册。
3. 登录按规范化用户名与可信客户端 IP 双维度限流。连续 5 次失败进入 15 分钟账号加 IP 锁定，并提供稳定 `Retry-After`。
4. 管理员 JWT 必须包含 `credential_version`。密码、角色、超级管理员状态、账号状态变化时递增版本并撤销相关会话。
5. 超级管理员只绕过 RBAC 权限集合，不绕过账号状态、资源规则、CSRF、会话、二次确认和审计。
6. 删除管理员、重置其他管理员密码、授予超级管理员、修改角色权限和撤销他人会话需要 5 分钟一次性二次确认。
7. 不能停用或删除当前登录管理员，不能删除、停用或降级最后一个激活超级管理员。

### 7.7 JWT SPEC

| 项目 | C 端 | B 端 |
| --- | --- | --- |
| 算法 | `HS256`，代码固定 allowlist | `HS256`，代码固定 allowlist |
| Secret | `WEB_JWT_SECRET`，生产必填且至少 32 字节 | `ADMIN_JWT_SECRET`，与 C 端不同 |
| issuer | `pinjie-fullstack-base`，可通过严格配置改为派生项目标识 | 同左 |
| audience | `pinjie-web` | `pinjie-admin` |
| 有效期 | 15 分钟 | 10 分钟 |
| 时钟偏差 | 最多 30 秒 | 最多 30 秒 |
| 必需 Claims | `iss/aud/sub/sid/jti/iat/nbf/exp/token_type/credential_version` | 同左 |
| `token_type` | 固定 `access` | 固定 `access` |
| `sub` | User UUID 字符串 | Admin UUID 字符串 |
| `sid` | User Session UUID | Admin Session UUID |

校验步骤固定为：解析 Header，拒绝未知算法和缺失字段；使用对应端 Secret 验签；强制验证 `exp/iat/nbf/iss/aud/sub/sid/jti/token_type/credential_version`；解析 UUID；查询会话缓存，缓存未命中时回源 PostgreSQL；检查主体状态、会话撤销与版本；最后返回当前主体。JWT 中不保存角色、权限快照、手机号、邮箱、真实姓名或其他个人信息。

参考项目的 `aud=backend` 手工判断将改为 PyJWT 强制 audience 校验。C/B Secret 隔离后，即使调用方伪造 `aud` 也不能跨端使用。Token 解码只接受代码内固定算法，不从环境或 Token Header 动态选择。

### 7.8 密码哈希与阻塞隔离

- 使用 Argon2id，初始参数 `memory_cost=65536 KiB`、`time_cost=3`、`parallelism=4`、salt 16 字节、hash 32 字节。
- 密码 hash 与 verify 使用 `run_in_threadpool`，并通过进程内有界 Semaphore 限制并发，防止登录洪峰占满 Worker。
- 实施时在目标 Linux x86_64 容器做基准。单次验证目标 100 至 500 ms；若超出目标，只能在计划中记录硬件数据后调整参数。
- 成功验证旧参数 hash 时使用 pwdlib 的升级能力重新哈希。升级写入属于当前登录事务。
- 密码、hash、验证码、Token 和 Secret 不进入任何日志、响应详情或审计 changed fields。

### 7.9 Refresh Token、Cookie 与 CSRF SPEC

#### Refresh Token

1. Refresh Token 使用 48 字节随机值；阶段 C Browser Cookie Profile 只通过 HttpOnly Cookie 传输。未来 Public Client Bearer Profile 通过独立端点与契约一次性返回，不能复用浏览器登录响应。
2. 数据库保存 HMAC-SHA256 摘要、Session ID、签发时间、闲置过期、绝对过期、消费时间、替代 Token ID、撤销时间和原因。
3. Refresh 闲置有效期 7 天，会话绝对有效期 30 天。每次成功 Refresh 只延长闲置期，不延长绝对期限。
4. Refresh 使用 PostgreSQL 行锁完成单次消费和新 Token 创建。旧 Token 再次出现时撤销整个 Session Family，记录高严重度登录安全事件并返回 401。
5. Redis 只缓存 Session 状态和承担短时互斥。缓存缺失必须回源 PostgreSQL；Redis 中不出现原始 Refresh Token。
6. 登出只有在 PostgreSQL 撤销提交成功后返回 200 和清除 Cookie。数据库不可用时返回 503，不能返回假成功。

#### Cookie

| Cookie | HttpOnly | Secure | SameSite | Path | Max-Age |
| --- | --- | --- | --- | --- | --- |
| `pinjie_web_access` | 是 | 生产必须是 | `Lax` | `/` | 15 分钟 |
| `pinjie_web_refresh` | 是 | 生产必须是 | `Lax` | `/api/v1/auth` | 7 天 |
| `pinjie_web_csrf` | 否 | 生产必须是 | `Lax` | `/` | 30 天以内，与会话一致 |
| `pinjie_admin_access` | 是 | 生产必须是 | `Lax` | `/` | 10 分钟 |
| `pinjie_admin_refresh` | 是 | 生产必须是 | `Lax` | `/api/v1/admin/auth` | 7 天 |
| `pinjie_admin_csrf` | 否 | 生产必须是 | `Lax` | `/` | 30 天以内，与会话一致 |

所有 Cookie 不设置 `Domain`。生产环境缺少 HTTPS 或 Cookie Secure 配置时拒绝启动。登录、刷新和退出响应设置 `Cache-Control: no-store`。

#### CSRF

- 所有使用 Cookie 身份的 `POST/PUT/PATCH/DELETE` 请求必须同时通过 Origin allowlist 和 `X-CSRF-Token` 校验。
- CSRF Token 为每个 Session 随机生成，浏览器可读 Cookie 保存原值，PostgreSQL 会话保存 HMAC 摘要。
- C 端和 B 端使用不同 Header 上下文和 Cookie，Token 与 Session 绑定，比较使用常量时间函数。
- 登录和注册没有既有 Session，仍校验 Origin，并由 SameSite、精确 CORS 和登录限流共同保护。登录成功后创建 CSRF Token。
- Admin/Web HTTP 客户端统一读取对应 CSRF Cookie并添加 Header；页面与 Store 不保存认证 Token。

### 7.12 RBAC 与导航 SPEC

1. 权限代码格式为复数资源加动作，例如 `users:read`、`roles:permissions:assign`。
2. 各领域通过公开 `permission_catalog.py` 导出 `PermissionDefinition`，聚合目录是代码权威来源。
3. `require_permission()` 只接受类型化 Permission Code，不接受任意页面字符串。
4. `scripts/sync_permissions.py --check` 比较源码目录与数据库；`--apply` 需要显式执行。运行时不自动创建或删除权限。
5. 角色与权限使用关系表，避免参考项目 JSONB 失去外键、索引和重命名一致性。
6. 权限或角色变化时递增受影响管理员的 credential version，撤销权限缓存与现有会话，确保收权立即生效。
7. Admin 导航由前端代码路由目录生成并按权限隐藏。隐藏只改善体验，后端仍执行权限与资源授权。
8. 阶段 C 不创建 `sys_menus` 动态菜单表，也不开放权限 CRUD，降低路由、菜单和服务端权限漂移。

### 7.13 Middleware、日志和审计 SPEC

| 机制 | 位置 | 记录内容 | 失败策略 |
| --- | --- | --- | --- |
| Request Context | Middleware | request ID、trace ID、开始时间、可信客户端 IP | 无法建立上下文时请求失败 |
| 安全响应头与 CORS | Middleware | 精确 Origin、Credentials、安全头 | 配置非法时拒绝启动 |
| 访问日志 | Middleware 到 Loguru stdout/stderr | method、route template、status、duration、脱敏主体、request/trace/release | 写日志失败不改变业务结果，但必须可观测；容器不依赖本地文件日志 |
| JWT 与 Session | Dependency | Cookie 解析、Claims、会话、主体状态 | 失败返回 401/403/503 |
| CSRF | Dependency | Origin 与 CSRF 摘要 | 失败返回 403 |
| 端点权限 | Dependency | Permission Code | 默认拒绝，失败返回 403 |
| 登录安全事件 | 独立 Security Port | 成功与失败、稳定原因、主体摘要、来源和关联 ID | 写入失败关闭登录或刷新结果 |
| 审计意图 | 已认证 Dependency/Application 层 | 明确 action、主体、请求关联和目标线索，初始结果 `started` | 高风险写操作无法预写意图时返回 503 |
| 业务审计终结 | Application Service 与独立失败终结器 | 成功时在业务事务内更新目标、变化字段和 `succeeded`；拒绝或异常时独立更新 `denied/failed` | 成功审计失败回滚业务；失败终结失败时保留 `started` 并触发 critical 告警 |
| 请求元数据日志 | Middleware 到 Redis Stream 再入库 | 仅元数据，不保存正文和凭据 | 不阻断普通请求；失败发出 critical 信号与丢弃计数，严禁静默 |

阶段 C 不复制参考项目按 URL 猜测 `module/action` 的通用审计中间件。Router 使用类型化 action 建立审计上下文，身份 Dependency 完成后预写带主体的意图，Service 使用同一 audit ID 完成语义化结果。未认证登录端点由登录事件承担安全证据。

请求元数据持久化使用 Redis Stream Consumer Group，入库成功后 ACK；消费者异常退出后使用 pending reclaim 恢复；非法消息进入独立 DLQ Stream。PostgreSQL 依赖 `request_id` 唯一约束实现幂等。此功能默认 `disabled`，启用值只允许 `metadata`，没有正文模式。

### 7.14 Redis Key SPEC

统一格式：

```text
{project}:{environment}:{domain}:{purpose}:v1:{opaque-id-or-hmac}
```

| 用途 | Key 示例 | TTL/规则 |
| --- | --- | --- |
| C 会话缓存 | `...:auth-web:session:v1:{session_id}` | 不超过 Access TTL；缓存未命中回源 DB |
| B 会话缓存 | `...:auth-admin:session:v1:{session_id}` | 同上，C/B 分离 |
| Refresh 互斥 | `...:auth-web:refresh-lock:v1:{token_hmac}` | 10 秒，`SET NX`，数据库行锁仍是最终并发边界 |
| 登录 IP 限流 | `...:auth-web:login-ip:v1:{ip_hmac}` | 原子窗口 TTL |
| 登录标识限流 | `...:auth-web:login-id:v1:{identifier_hmac}` | 原子窗口 TTL，不暴露用户名 |
| 管理员确认 | `...:auth-admin:confirm:v1:{token_hmac}` | 5 分钟，一次消费，绑定 Admin、Session、Action |
| 请求日志 Stream | `...:system:request-log:v1` | 有界长度、Consumer Group、DLQ 和积压指标 |

限流通过 Lua 或等价原子服务器端操作同时完成计数、TTL 和剩余时间。Redis 不可用时，登录、刷新、二次确认等安全入口返回 503；普通只读业务是否依赖 Redis由对应领域明确声明，不能自动降级。

### 7.15 Admin 前端 SPEC

1. `/login` 提供管理员用户名、密码、提交状态、限流反馈和通用凭据错误，不显示账号是否存在。
2. 受保护布局启动时请求 `/admin/auth/me`，401 进入登录页，403 显示无权限，503 显示依赖不可用并允许重试。
3. 导航由代码目录与当前权限交集生成，直接访问路由仍执行页面守卫和后端权限。
4. 用户管理覆盖筛选、分页、详情、状态、密码重置和会话撤销。
5. 管理员管理覆盖列表、创建、修改、启停和角色分配，并保护当前账号与最后超级管理员。
6. 角色管理覆盖列表、创建、编辑、删除和权限分配；权限目录只读。
7. 安全日志覆盖登录事件、审计事件和启用时的请求元数据，支持时间、主体、动作、结果和 request ID 过滤。
8. 高风险操作通过统一二次确认 Modal 获取 action-bound Token，然后立即提交目标操作。
9. TanStack Query 管理服务端数据，Zustand 只保存非敏感 UI 状态。Cookie 由浏览器管理，统一 HTTP 层添加 CSRF Header、解包响应和处理 401。
10. 页面覆盖加载、空数据、失败、无权限、成功、并发冲突和危险操作确认，保持 Ant Design 与 ProComponents 体系。

### 7.16 Web 前端 SPEC

1. `/login` 和 `/register` 是可提交的真实表单，包含服务端错误、限流、禁用注册和无障碍状态通知。
2. `/account` 为受保护用户中心，服务端首屏读取 Cookie 并显示当前用户真实资料。
3. 用户中心提供资料修改、密码修改、会话列表、撤销其他设备、退出和账户注销。
4. Next.js 同域 Route Handler 或服务端请求入口只转发必要 Cookie 和 CSRF，不把 Token 暴露到 Client Component。
5. 浏览器客户端请求统一 `credentials: include`，从 CSRF Cookie 读取值并添加 Header。
6. 401 进入明确的登录失效流程，不能无限 Refresh；同一页面并发 401 只允许一次 Refresh，失败后清理查询缓存并跳转登录。
7. 页面覆盖桌面和移动端、键盘、焦点、错误提示、加载和横向溢出；关键页面执行 axe。

### 7.17 OpenAPI 与生成 Client

1. Backend Router 使用准确的请求 Schema、响应 Schema、Cookie 安全说明、HTTP 状态和错误示例。
2. Cookie 是运行时凭据，生成 Client 不接收或返回 Access/Refresh Token 字段。
3. 后端完成后导出根 `openapi.json`，再运行 `pnpm generate-api`，最后适配 Admin 和 Web。
4. 生成 Client 的公共 HTTP 配置启用 Credentials，但具体 CSRF 和 401 Refresh 编排由各应用的受控客户端入口负责。
5. CI 重新导出 OpenAPI、重新生成 Client 并检查无 Git 差异。

### 7.18 Alembic、初始化与权限同步

- 按拥有领域拆分小粒度 Alembic revisions，先基础账户与 RBAC，再会话，再安全事件与审计，再可选请求日志。
- 每个 revision 审查 UUID、UTC、外键删除规则、唯一约束、CHECK、索引、表注释和 downgrade 边界。
- 空库执行 `alembic upgrade head`，已有阶段 B 空 schema 重复升级保持幂等，禁止 `create_all()`。
- `scripts/create_initial_admin.py` 只从交互输入或环境变量读取用户名和密码，密码无默认值、不回显、不写日志；已有管理员时默认拒绝，显式 reset 需再次确认并撤销会话。
- `scripts/sync_permissions.py` 提供 `--check` 与 `--apply`，默认只检查。生产应用启动不自动改权限表。
- 初始化和同步脚本连接数据库前执行与测试同等级的目标环境与数据库名检查。

### 7.20 失败、恢复和并发规则

1. PostgreSQL 是用户、管理员、角色、权限、会话和审计的权威来源，不可用时相关请求返回 503。
2. Redis 在阶段 C 认证启用后是安全关键依赖，生产必须使用 `REDIS_MODE=required`。启动和 Readiness 检测其可用性。
3. 数据库会话提交失败时，删除本次创建的 Redis Session 缓存与确认状态；补偿失败记录 critical 并使 Readiness 不健康，不能返回成功。
4. Refresh 并发由 Redis 短锁减少竞争，PostgreSQL `SELECT ... FOR UPDATE` 与唯一约束给出最终结果。
5. 角色收权、账号停用和密码修改先提交数据库版本与撤销，再清 Redis。缓存删除失败时旧缓存项必须通过短 TTL 和版本不匹配失效。
6. 请求元数据日志的队列故障不改变普通业务结果，但必须产生结构化 critical 日志、指标和恢复记录。安全审计与登录事件不采用此旁路策略。
7. 任何未知或部分状态都返回明确失败，不返回空权限、匿名身份、假退出或假审计成功。

### 7.21 保留、隐私和查询边界

- 登录安全事件和审计事件默认保留 180 天，请求元数据默认保留 30 天；派生项目可按法规与风险收紧。
- 阶段 C 提供显式清理命令和 dry-run，不在请求进程内自动全表删除。
- IP 使用 PostgreSQL `INET` 或标准化文本，前端默认掩码展示；User-Agent 截断并清理控制字符。
- 用户名用于日志时保存 HMAC 指纹，失败登录不保存原始用户名。
- `changed_fields` 只保存字段名和安全的新旧状态摘要，密码、hash、Token、Cookie、邮箱完整值不进入审计。
- 日志查询必须分页并限制最大时间范围，导出功能留给派生项目。

### 7.22 与两个参考项目的最终差异

| 主题 | `pinjie-standard` | `fastapi-mini-standard` | 阶段 C 目标 |
| --- | --- | --- | --- |
| Access 传输 | JSON Bearer | JSON Bearer | HttpOnly Cookie，响应无 Token |
| Refresh 权威 | Redis 明文 Key | Redis 明文 Key，加 DB 会话审计 | PostgreSQL 摘要权威，Redis 只缓存与锁 |
| JWT 隔离 | 单 Secret，C 端弱 audience | 单 Secret，C 端弱 audience | C/B 双 Secret、强制 iss/aud/Claims |
| JWT 内容 | `sub/exp/type`，B 加 `aud/tv` | 同左 | 加 `sid/jti/iat/nbf/credential_version`，不放权限与 PII |
| CSRF | 无 | 无 | Origin allowlist 加 Session 绑定 CSRF |
| 可选身份 | 无效 Token 静默匿名 | 无效 Token 返回 401 | 采用 mini 的严格语义 |
| RBAC 存储 | Role JSONB 权限码 | Role JSONB 权限码 | 规范化 Role Permission 关系表 |
| 权限管理 | 运行时 CRUD 与正则扫描 | 运行时 CRUD 与增强同步 | 源码目录权威，后台只读，显式 check/apply |
| 动态菜单 | 数据库菜单树 | 数据库菜单树 | 前端代码导航按服务端权限过滤 |
| 登录日志 | 写失败放行 | 写失败关闭入口 | 安全事件是认证结果的一部分，失败关闭 |
| 业务审计 | 中间件推断，失败放行 | 预写 Fail Closed，加 Service 同事务审计 | 以 Service 同事务语义审计为权威 |
| 限流 | 多命令滑窗，Redis 故障放行 | 固定窗，Redis 故障 503 | 原子限流、稳定 Retry-After、故障 503 |
| 请求日志 | Redis List，恢复较弱 | List 加 spool/processing/DLQ | Redis Stream 元数据模式，无正文 |
| 初始化管理员 | 有默认密码风险 | 环境密码必填 | 一次性显式 CLI，无默认值，重置撤销会话 |
| 事务 | Service 内多处 commit | 外层 `@transactional` 和补偿 Hook | 沿用本项目 `transaction_scope` 与 Application Service 所有权 |
| UUID v7 | `uuid6` | `uuid6` | Python 3.14 标准库统一入口 |
| 业务范围 | 通用骨架含短信微信适配 | 电商全领域 | 只保留母版通用账户、RBAC、审计和系统能力 |

### 7.23 阶段 C 完成定义

阶段 C 只有在以下事实同时成立时才可标记已完成：

1. Backend、Admin、Web、Database、OpenAPI、API Client 和 E2E 均完成本 SPEC 适用项。

## 11. 风险与回滚

| 风险 | 预防 | 回滚边界 |
| --- | --- | --- |
| Cookie 与前端域名配置错误 | 精确 Origin、Credentials、Secure、SameSite 和 E2E | 回滚认证路由与 Cookie 配置，不保留双传输模式 |
| Rotation 并发误判重放 | PostgreSQL 行锁、唯一约束、并发集成测试 | 回滚到上一完整版本并撤销受影响会话，禁止放宽单次消费 |
| DB 与 Redis 跨资源不一致 | DB 权威、短 TTL、提交后缓存、失败补偿 | 清缓存并从 DB 重建，不把 Redis 反向覆盖 DB |
| 角色收权延迟 | credential version、会话撤销、短缓存 | 清除管理员会话并强制重新登录 |
| 审计写入拖累管理操作 | 同事务小记录、索引和容量测试 | 进入只读维护或修复审计依赖，不能关闭审计放行 |
| 日志隐私泄露 | 白名单字段、摘要、脱敏与安全回归 | 停止日志消费者、隔离受影响数据、按事故手册处理 |
| 管理员初始化误操作 | 无默认密码、目标检查、一次性显式 CLI | 保留最后超级管理员，撤销新账号与会话 |
| 大批次跨栈变更难回滚 | 按批次小提交、先契约后消费者、每批可验证 | 回滚当前批次源码和未部署迁移；生产数据库回滚需专项授权 |

生产迁移、密钥配置、初始化管理员、镜像发布和部署均属于后续独立授权动作。本计划确认只授权本地实现时，不能自动执行这些生产动作。

以下十项已按推荐值确认并实施：

8. 请求持久化只支持可选 `metadata` 模式，不保存请求体、响应体、Cookie、Authorization 和 Token。
9. 用户密码与管理员密码统一最少 12 个字符；管理员高风险操作使用 5 分钟一次性二次确认。
10. 用户已授权阶段 C 与阶段 B 剩余环境验收并行实施；阶段 C 可以开始修改源码，但未通过真实 PostgreSQL、Redis、镜像和跨栈 E2E 前不能标记为已完成。
