## 6. 现状分析

### 6.1 扫描结论

`pinjie-standard` 的 87 个主要源码与工程文件中，有 72 个在 `fastapi-mini-standard` 存在同路径文件，其中 17 个内容一致、55 个已经演进。`fastapi-mini-standard` 另有约 246 个工程和业务文件，绝大多数属于电商领域、业务迁移和后期可靠性改造。

关键事实如下：

- 基础骨架使用 Python 3.11、Conda 叙述和分散的 PostgreSQL 配置字段，本项目固定标准 CPython 3.14、纯 uv 和单一 `DATABASE_URL`。
- 基础骨架的配置环境值是 `local/dev/prod`，当前本项目模板又使用 `development`，阶段 B 必须统一为一组无别名值。
- 基础骨架把校验错误映射为 HTTP 400，本项目错误模型规定结构和字段校验使用 HTTP 422。
- 基础骨架 Startup 在本地和测试环境允许依赖探针失败后继续运行，与本项目 Fail Closed 规则冲突。
- 基础骨架数据库测试在 PostgreSQL 不可用时 `skip`，并使用 `create_all/drop_all`，与本项目迁移唯一来源和关键门禁不得跳过冲突。
- 基础骨架存在硬编码数据库 DSN、默认管理员密码和密码日志输出，禁止迁入。
- `fastapi-mini-standard` 的健康探针、事务工具、测试数据库校验和 AST 架构测试具有参考价值，但部分实现仍固定要求 Redis、允许集成测试跳过或使用 `create_all/drop_all`，需要继续收紧。
- `fastapi-mini-standard` 的 Dockerfile使用 Python 3.11 和 `requirements.txt`，没有按本项目 `uv.lock`、Monorepo 构建上下文和三个镜像协作方式实现。

## 7. 方案设计

### 7.1 Python 运行时与依赖锁定

Python 运行时长期边界以 [ADR 0009：Python 运行时基线决策](../docs/adr/0009-Python运行时基线决策.md)为准。阶段 B 按以下具体配置实施：

- 使用标准 CPython 3.14，保留常规 GIL 构建，不使用 free-threaded `3.14t`。
- `requires-python = ">=3.14,<3.15"`，Ruff 使用 `py314`，Mypy 使用 `3.14`，本地 `.python-version` 使用 `3.14` 系列。
- `tool.uv.dev-dependencies` 迁移为 `[dependency-groups]`，所有运行与开发依赖写入 `apps/backend/uv.lock`。
- uv 锁定必须覆盖 Windows x64 和生产 Linux x64；目标服务器若为 ARM64，实施前先把 Linux ARM64 加入目标环境并完成镜像验证。
- CI 显式安装标准 CPython 3.14，并在同步依赖前断言 `sys.version_info[:2] == (3, 14)`。
- 截至 2026-08-13，当前镜像候选补丁为 CPython 3.14.7；实施时必须重新查询官方当前受支持补丁，固定官方 slim glibc 基础镜像完整 digest，禁止使用浮动标签和 `3.14.0`。
- 1Panel 只运行仓库构建的 Backend 容器，宿主机 Python 下拉选项不参与项目版本选择。

`pyproject.toml` 的目标配置为：

```toml
[project]
requires-python = ">=3.14,<3.15"

[tool.uv]
required-environments = [
    "sys_platform == 'win32' and platform_machine == 'AMD64'",
    "sys_platform == 'linux' and platform_machine == 'x86_64'",
]

[tool.ruff]
target-version = "py314"

[tool.mypy]
python_version = "3.14"
```

生产为 Linux ARM64 时，在 `required-environments` 增加 `sys_platform == 'linux' and platform_machine == 'aarch64'`。阶段 B 不承诺其他 Python 主次版本或未登记平台。

### 7.3 Backend 配置契约

采用以下唯一值和唯一来源：

| 配置 | 决策 |
| --- | --- |
| `ENVIRONMENT` | 只允许 `local`、`test`、`production`，不接受别名或大小写归一化 |
| 数据库 | 运行只读 `DATABASE_URL`，测试必须显式提供 `TEST_DATABASE_URL` |
| 测试数据库 | PostgreSQL、库名以 `_test` 结尾、与运行库目标和身份隔离；本地只允许回环主机，CI 使用显式白名单 |
| Redis | `REDIS_MODE` 只允许 `disabled`、`required`；默认 `disabled` 且不创建客户端，`required` 时连接和探针失败均明确失败 |
| 密钥 | 阶段 B 没有签名或密码能力，不声明未使用的应用签名密钥和 Token 配置；阶段 C 引入能力时再定义并严格校验 |
| API 文档 | local/test 默认启用，production 默认关闭；生产开启必须显式配置 |
| 日志 | local/test 可读文本，production 结构化 JSON；生产禁用 diagnose 和本地文件 Sink |
| 发布版本 | `RELEASE_VERSION` 可选于本地，production 必填并进入日志和探针安全摘要 |

阶段 B 对 `apps/backend/.env.example`、运维文档和 CI 使用同一命名，删除现有 `development` 与 `local/dev/prod` 漂移。

运行行为：

1. `app.main` 导入只创建 Python 对象，不连接数据库、Redis，不创建文件，不运行迁移，不启动任务。
2. Lifespan 创建数据库 Engine、Session Factory并按模式创建 Redis Client，结束时有界关闭；阶段 B 不创建无消费者的生产 HTTP Client。
3. Startup 负责配置与本地资源初始化。短时依赖不可达通过 Readiness 返回 503，不让 Liveness 触发重启风暴。
4. `GET /health/live` 只返回进程存活。
5. `GET /health/ready` 是运维 Readiness，检查 PostgreSQL、Alembic head、必需 Redis 和已声明关键资源，每项具有严格超时，只返回最小安全摘要。
6. 当前无业务迁移时允许 Alembic 当前 revision 与 head 同为 `None`，禁止创建空 revision 伪造数据库能力。
7. 统一响应至少包含 `code`、`message`、`data`、`request_id`。时间和发布版本进入日志、响应头或探针，不强行扩展所有业务响应。
8. 输入结构错误返回 422；业务错误使用稳定码；未知异常返回 500 和 `request_id`，响应不包含内部细节。
9. `request_id` 只接受长度和字符集合法的外部值，否则生成 UUID v7；响应头回传同一值。
10. 阶段 B 只实现 Engine、Session Factory、请求级 Session 和事务工具；通用 CRUD Repository 等待阶段 C 的第一个真实领域按实际查询语义建立。
11. `GET /api/v1/system/status` 是前端业务中立状态契约，使用统一响应信封，只公开可用状态和请求关联信息；Admin、Web 和生成 API Client 不直接消费运维探针。

### 7.5 UUID v7 决策

Python 3.14 标准库已经提供符合 RFC 9562 的 `uuid.uuid7()`。阶段 B 已确认继续采用应用层统一生成 UUID v7，PostgreSQL 只保存原生 `uuid` 类型，不要求 PostgreSQL 18，也不设置 `server_default=uuidv7()`。

`app/core/identifiers.py` 是唯一生成入口，对外暴露返回标准库 `uuid.UUID` 的 `new_uuid7()`，其实现调用标准库 `uuid.uuid7()`。Model、中间件、Service、脚本和后续领域只能依赖 `new_uuid7()`，不得绕过统一入口分散调用生成函数。

SQLAlchemy Model 使用跨方言的 `sqlalchemy.Uuid(as_uuid=True)`，Python 类型标注使用标准库 `uuid.UUID`，主键默认值使用 `default=new_uuid7`。数据库、ORM、Pydantic Schema 和领域边界只暴露标准库 UUID 类型。

阶段 B 不添加 `uuid-utils`、`uuid6` 或其他 UUID v7 第三方运行依赖。Python 运行时升级时必须重新验证返回类型、版本、唯一性、排序行为、序列化和真实 PostgreSQL 往返，但不得改变调用方和数据库契约。

阶段 B 至少增加以下验证：

- `new_uuid7()` 返回值满足 `type(value) is uuid.UUID` 且 `value.version == 7`。
- 批量生成结果唯一，并按生成顺序具有本实现承诺的单调排序行为。
- Pydantic JSON 序列化与反序列化保持标准 UUID 契约。
- SQLAlchemy 2、asyncpg 与真实 PostgreSQL 的写入、读取和查询参数绑定成功。
- Model 默认值、request ID 和其他调用方均只经过 `new_uuid7()`，架构检查拒绝绕过统一入口和引入第三方 UUID v7 包。

本决策基于标准库边界、数据库版本独立性和依赖最小化，不把微基准性能作为主要依据。官方依据：[Python 3.14 uuid 文档](https://docs.python.org/3.14/library/uuid.html#uuid.uuid7)、[PostgreSQL 18 UUID 函数](https://www.postgresql.org/docs/18/functions-uuid.html)和 [SQLAlchemy Uuid 类型](https://docs.sqlalchemy.org/en/20/core/type_basics.html#sqlalchemy.types.Uuid)。

### 7.6 测试与门禁

Backend 测试分为：

| 层级 | 阶段 B 内容 | 依赖 |
| --- | --- | --- |
| 单元 | 配置、响应、错误码、UUID、探针结果、事务工具 | 无网络、无数据库 |
| API | Liveness、Readiness、422、404、500、request ID、安全头、CORS | 真实 FastAPI 入口，基础设施使用公开 Port 替身 |
| 架构 | 导入无副作用、层级方向、Router/Repository 事务禁令、循环依赖 | import-linter、AST、根边界脚本 |
| PostgreSQL 集成 | 连接隔离、Alembic 空库升级、重复升级、head 一致性、UUID 类型绑定和 Readiness | 显式 `_test` PostgreSQL 18.4 |
| 契约 | OpenAPI 导出、API Client 生成、无漂移、Breaking Change | 真实应用 Schema 与生成器 |

约束如下：

- 测试数据库不可用时关键集成测试直接失败，不使用 `skip`。
- 不使用 `Base.metadata.create_all()` 或 `drop_all()` 建立和清理结构。
- CI 为 Backend 提供独立 PostgreSQL 测试服务和专用测试身份，不依赖私有 Secret 才能运行普通 PR。
- 普通单元测试拦截未声明外部网络。数据库和跨栈测试只开放计划声明的本地服务。
- Backend 行与分支覆盖率最低 90%；Admin 与 Web 的语句、分支、函数和行覆盖率最低 80%。覆盖率不能替代行为断言。
- `uv run python -m pytest -q` 执行全部必需测试，集成测试不通过默认 marker 隐藏。

前端测试技术栈已确认如下：

| 层级 | 阶段 B 工具 | 环境与职责 |
| --- | --- | --- |
| 纯单元 | Vitest、`@vitest/coverage-v8` | `node` 环境测试纯逻辑、数据转换和客户端状态 |
| React 组件 | Vitest、React Testing Library、`@testing-library/jest-dom`、`@testing-library/user-event` | `jsdom` 环境按用户行为测试组件、Hook、表单和交互状态 |
| HTTP 边界 | MSW 2 | 为组件测试提供类型化的成功、空数据、业务失败和网络失败响应；未声明请求失败 |
| 跨栈 E2E | Playwright Test | 真实浏览器连接生产构建、Backend 和隔离 PostgreSQL `_test` 数据库 |
| 可访问性 | `@axe-core/playwright` | 扫描 Admin 与 Web 的关键页面和关键状态，并保留人工键盘、焦点和语义检查 |

Jest、Cypress、Storybook 和 Vitest Browser Mode 不纳入阶段 B 默认依赖。Web 异步 Server Component、流式渲染和跨 Server、Client 边界行为交给 Playwright，不用 Vitest Mock 框架运行时。详细执行标准以 `docs/architecture/testing-strategy.md` 为准。

### 7.7 OpenAPI 与 API Client

固定同步链：

```text
Backend 实现
-> 原子导出根 openapi.json
-> pnpm generate-api
-> packages/api-client/src 生成结果
-> Admin/Web 请求入口适配
```

要求：

1. 导出脚本只能从 `app.main` 获取 Schema，输出到显式参数路径，UTF-8 无 BOM并保留末尾换行。
2. API Client 生成目录禁止手工修改。
3. Admin 与 Web 分别在 `src/lib/api/` 配置运行地址、响应解包和错误分类，页面不直接配置生成 Client。
4. Admin 生产浏览器地址使用同域 `/api/v1`，减少构建环境耦合。
5. Web 服务端使用运行时 `BACKEND_INTERNAL_URL`，浏览器使用同域相对路径；公开变量不保存秘密。
6. 阶段 B 只消费 `/api/v1/system/status`，不引入认证 Token 行为；`/health/live` 与 `/health/ready` 保持运维用途。

### 7.10 容器与生产接线

三个 Dockerfile 统一要求：

- 基础镜像固定 digest，实施时查询并记录实际架构可用的官方镜像 digest。
- Backend 使用标准 CPython 3.14 的官方 slim glibc 镜像，固定实施时最新受支持补丁版和完整 digest；禁止 `3.14.0`、浮动标签与 free-threaded `3.14t`。

- 使用非 Root 用户和只读友好的文件布局。
- 不复制真实 `.env`、测试、缓存、Git 和本地构建产物。
- HEALTHCHECK 使用各应用真实健康入口。
- Backend 只安装 `uv.lock` 中运行依赖。
- Web 使用 Next standalone 输出。
- Admin 使用非 Root 静态服务器并提供独立 `/healthz`。

生产接线：

| 应用 | 容器内配置 | 健康路径 |
| --- | --- | --- |
| Backend | `apps/backend/.env` | `/health/ready` |
| Web | `BACKEND_INTERNAL_URL=http://backend:8000` | `/healthz` |
| Admin | 浏览器使用同域 `/api/v1` | `/healthz` |

`compose.prod.yml` 增加健康检查、Web 到 Backend 的内部地址和必要依赖关系。1Panel OpenResty 继续负责公网 HTTPS、同域 `/api/v1` 转发和三个应用入口，具体配置同步到运维文档，不在仓库保存真实域名或证书。

本地开发、生产容器和 E2E 必须具备等价的同域 API 路径：Admin 开发服务器与生产静态服务器代理 `/api/v1`，Web 通过运行时服务端入口代理浏览器 `/api/v1` 请求；两者的上游均由仅服务端可见的 `BACKEND_INTERNAL_URL` 配置。E2E 不依赖 1Panel 才能完成跨栈验证。

### 7.11 CI 与跨栈 E2E

1. Backend CI 显式安装标准 CPython 3.14，校验解释器版本，补齐 compileall、应用导入、OpenAPI、Ruff、format check、Mypy、import-linter、Alembic 和全部 pytest。
2. Frontend CI 补齐 Admin/Web 的 Vitest 单元、RTL 组件、MSW 网络边界与 V8 coverage，保留 Lint、Typecheck、Build 和生成客户端漂移检查。
3. 新增独立跨栈 E2E Workflow，使用 PostgreSQL 测试服务、Backend、Web、Admin、`@axe-core/playwright` 和标准 Playwright Chromium。
4. E2E 失败、浏览器未安装、端口冲突和依赖启动失败均返回失败，不用兜底冒烟替代 CI 结果。
5. 发布 Workflow 增加对跨栈 E2E push Workflow 成功结果的要求。
6. 本地 Windows 若标准 Playwright 浏览器不可用，可以用本机 Chrome 做补充诊断，但不能据此宣称标准 E2E 完整通过。
7. Pull Request 默认运行 Chromium；Firefox 与 WebKit 进入定时或发布验证。派生项目明确支持 Safari 时，WebKit 必须进入发布门禁。
8. CI 首次失败即视为失败；最多一次重试只用于采集 Trace，并保存必要截图与 HTML Report，禁止通过重试掩盖不稳定测试。

Backend CI 的解释器与依赖同步顺序固定为：

```yaml
- name: Install CPython 3.14
  run: uv python install 3.14

- name: Sync locked dependencies
  working-directory: apps/backend
  run: uv sync --locked --python 3.14

- name: Verify Python runtime
  working-directory: apps/backend
  run: uv run python -c "import sys; assert sys.version_info[:2] == (3, 14); print(sys.version)"
```

实际 Workflow 继续固定 Action 完整 Commit SHA；以上片段只固定 Python 相关步骤和顺序。

## 11. 风险与回滚

| 风险 | 控制措施 | 回滚方式 |
| --- | --- | --- |
| 三端同时进入 partial | 在同一计划和工作分支完成，未达到三个 ready 前不宣称治理通过 | 普通 Git 回滚本计划实现提交，保留计划记录 |
| 参考代码携带旧缺陷 | 文件级复核，不整仓复制；每个复用点配套测试 | 删除本次新实现并恢复当前 empty 骨架快照 |
| 阶段 B 侵入阶段 C | 只允许 system 健康领域，不迁入身份、权限和业务表 | 回滚越界文件，计划中记录范围纠正 |
| 测试误连开发库 | 显式 TEST URL、环境、主机、库名和身份多重校验 | 校验失败立即停止，不执行迁移或清理 |
| Alembic 清理误伤 | 不使用 create_all/drop_all，不自动删除数据库；测试对象精确归属 | 中止测试，依据隔离库备份或重新创建测试库 |
| Python 或运行平台变化 | 使用标准库 `uuid.uuid7()`、统一 identifiers 适配点、Python 3.14 受控范围、跨平台锁文件和真实 PostgreSQL 往返测试 | 回滚运行时和适配点，不改变已生成 ID；目标平台缺少可用 Wheel 时停止构建，不在生产临时编译原生扩展 |
| OpenAPI 生成漂移 | 固定生成链和 Git diff 门禁 | 回滚 Backend 契约或同步消费者，禁止手改生成物 |
| 前端空壳被误称业务完成 | UI 只呈现真实系统状态，索引明确阶段 C 待实现 | 修正文档和状态，不增加假数据 |
| Docker 构建依赖环境 | 固定镜像 digest、锁依赖、构建三个目标 | 回滚 Dockerfile 和 Compose，不发布镜像 |
| E2E 不稳定 | 独立端口、确定性数据、严格等待、禁止无限重试 | 修复根因；未通过前不进入发布门禁 |

数据库阶段 B 不新增业务表，预期无需生产迁移回滚。任何测试数据库创建、重建或清理都需要先核对目标，且不得由本计划自动删除开发或生产数据库。
