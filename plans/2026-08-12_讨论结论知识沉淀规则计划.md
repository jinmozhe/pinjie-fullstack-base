## 2. 背景

Codex 与 Antigravity 已经具备需求探索、实施规划、多步执行和验证能力，但对话本身不应成为项目事实的长期保存位置。当前仓库已经通过 PRD、ADR、架构文档、运维文档、蓝图、计划、全项目索引和 Changelog 分别维护不同类型的知识，缺少一条明确规则，要求将讨论中形成的确定结论路由到现有权威文档。

如果把全部讨论原样保存到独立 Brainstorming 目录，会同时保留临时猜测、被否决方案和过时观点，增加重复事实与误读风险。本计划先建立知识收敛规则，不创建空的 `docs/brainstorming/` 或 `docs/research/`。

## 3. 目标

1. 明确对后续开发有持续影响的已确认结论不得只保留在对话中。
2. 建立产品需求、技术决策、当前机制、操作步骤、业务蓝图、单次实施、长期规则、当前状态和交付事实的路由关系。
3. 明确只有用户确认或具备可核验证据的结论才能提升为项目事实。
4. 要求优先更新现有同主题权威文档，避免创建重复说明。
5. 在全栈计划结束前检查讨论结论是否已经完成知识路由。
6. 保留未来按实际需要创建 `docs/research/` 的空间，但当前不建立空目录和模板。

## 4. 非目标

1. 不保存或转录完整聊天记录。
2. 不要求每次问答、解释或临时探索都修改项目文档。
3. 不创建 `docs/brainstorming/`、`docs/research/` 或新的文档分类。
4. 不改变 PRD、ADR、计划、全项目索引和 Changelog 的现有职责。
5. 不修改 Backend、Admin、Web、API Client、数据库或部署实现。
6. 不删除、移动或重命名任何现有计划文档。

## 5. 现状分析

1. 根 `AGENTS.md` 已要求文档、规则、目录职责、权威来源和计划状态变化时同步索引，但没有覆盖只发生在讨论中的确定结论。
2. `plans/README.md` 已要求计划结束前同步当前系统行为、ADR 和 Changelog，但没有显式检查讨论结论是否仍散落在对话中。
3. `docs/README.md` 已是完整文档导航，现有分类可以承接当前讨论产生的长期知识。
4. `.agents/agents-index.md` 已维护权威来源与当前状态，无需增加 Brainstorming 状态体系。
5. 当前没有需要独立保存原始证据的长期技术调研，因此不满足创建 `docs/research/` 的实际条件。

## 6. 方案设计

1. 在根 `AGENTS.md` 增加“讨论结论与知识沉淀”章节。
2. 规则只要求沉淀会影响后续工作的已确认或有证据结论，不保存临时推测和普通聊天过程。
3. 使用现有权威来源完成知识路由：产品范围进入 PRD，重大技术取舍进入 ADR，当前机制进入架构文档，可执行步骤进入运维文档，派生业务进入蓝图，单次实施进入计划，长期强制约束进入 `AGENTS.md`，当前状态进入总索引，交付事实进入 Changelog。
4. 在 `plans/README.md` 的完成条件中增加知识路由检查，保证实施任务在结束前收敛讨论结论。
5. 只有独立调研持续时间长、证据需要复用且尚未达到正式决策条件时，后续任务才能评估创建 `docs/research/`。

## 10. 风险与回滚

1. 风险：规则要求过宽，导致每次普通问答都修改文档。控制方式是限定为“影响后续开发且已确认或有证据”的结论。
2. 风险：同一结论同时写入多个文件。控制方式是按信息类型选择唯一权威来源，其他位置只保留入口或链接。
3. 风险：为了保存讨论而创建大量低价值文档。控制方式是优先就地更新现有文档，当前不创建新目录。
4. 风险：未决观点被误写为项目事实。控制方式是未决事项只留在活动计划，低置信度内容必须标注。
5. 回滚：逐项回退本计划列出的治理文件内容修改。本次不涉及运行代码、数据库和外部系统。
