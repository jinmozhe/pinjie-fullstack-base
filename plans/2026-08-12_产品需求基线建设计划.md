# 产品需求基线建设计划

## 1. 当前状态

- 状态：已结束
- 结果：已完成
- 创建日期：2026-08-12
- 影响范围：全仓库产品基线、项目治理和文档入口

## 1.1 关联需求

`BASE-DOC-002`、`BASE-DOC-004`、`BASE-DOC-006`。

## 2. 背景

本仓库是用于派生 CMS、电商、博客、企业站和管理平台等业务项目的通用全栈 Monorepo 母版。现有 README、ADR、架构文档和业务蓝图分别描述了项目定位、技术决策、工程结构和部分业务扩展方向，但没有一份权威文档集中回答母版解决什么问题、面向哪些使用者、适合哪些场景、目标能力是什么、明确不做什么以及达到什么条件才算可用于派生项目。

当前 Backend、Admin 和 Web 均处于工程骨架阶段，因此产品需求必须清楚区分“目标能力”和“当前已实现状态”，避免把规划内容表述为已经交付。

## 3. 目标

1. 新建 `docs/PROJECT_REQUIREMENTS.md`，作为母版及派生项目的产品需求基线。
2. 明确目标用户、核心问题、典型场景、适用范围和不适用范围。
3. 为全局、Backend、Admin、Web、API Client、Database、Deployment 和 Documentation 建立稳定需求编号。
4. 明确母版目标能力、非目标、派生规则和可验证的完成标准。
5. 明确 PRD、ADR、架构文档、蓝图、计划、全项目索引和 Changelog 的职责边界。
6. 将 PRD 接入根规则、全项目索引、文档索引、根 README 和仓库结构说明。

## 4. 非目标

1. 不实现 PRD 中描述的目标能力。
2. 不修改 Backend、Admin、Web、API Client、数据库或部署配置。
3. 不在 PRD 中展开技术选型比较，相关理由继续由 ADR 和架构文档承担。
4. 不把 CMS、电商等具体业务需求写成母版通用能力。
5. 不创建只有一个文件的 `docs/product/` 二级目录。
6. 不删除、移动或重命名任何现有计划文档。

## 5. 现状分析

1. `README.md` 简述了母版定位、技术栈和业务边界，但没有完整目标用户和验收要求。
2. ADR 0001 记录 Monorepo 架构和粗粒度通用能力边界，职责是技术决策而非产品需求。
3. `docs/architecture/project-structure.md` 描述工程结构和实现约定，不承担产品范围定义。
4. `docs/blueprints/commerce/README.md` 描述派生业务方向，不能代替母版产品基线。
5. `PROJECT_INDEX.md` 记录当前阶段和实现状态，不能承担长期目标能力定义。
6. 当前尚无 `docs/PROJECT_REQUIREMENTS.md`。

## 6. 方案设计

1. PRD 直接放在 `docs/PROJECT_REQUIREMENTS.md`，避免为单一文件创建 `docs/product/`。
2. PRD 使用“产品需求基线”定位，长期维护母版做什么、为谁服务和如何验收。
3. 需求使用 `BASE-*` 编号，按全局、Backend、Admin、Web、API、Database、Operations 和 Documentation 分类。
4. PRD 只描述目标与验收，不复制技术选型论证、实现进度或具体计划步骤。
5. 当前实现状态统一引用 `PROJECT_INDEX.md`，已交付事实引用 `CHANGELOG.md`，实施路径引用 `plans/*.md`。
6. 根 `AGENTS.md` 规定新增或改变产品能力前必须读取 PRD，需求边界变化时同步 PRD。

| Admin | 否 | 只定义管理端目标需求，不修改规则和实现 | 现有 Admin 规则与架构事实 | 检查需求与规则无冲突 |

## 10. 风险与回滚

1. 风险：PRD 混入技术选型论证，与 ADR 重复。控制方式是技术理由只通过链接指向 ADR。
2. 风险：PRD 把目标能力误写为当前能力。控制方式是单设“状态边界”，当前实现统一引用总索引。
3. 风险：需求过细导致 PRD 变成实现方案。控制方式是需求只描述能力、边界和验收，代码结构留在架构文档。
4. 风险：派生业务污染母版。控制方式是具体业务需求进入蓝图和派生仓库 PRD。
5. 回滚：逐项回退本计划列出的文档和治理入口修改。本次不涉及运行代码、数据库和外部系统。
