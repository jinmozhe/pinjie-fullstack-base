## 背景

Web 首页当前始终显示“登录”和“创建账户”按钮。用户已经通过 HttpOnly Cookie 登录并能进入用户中心时，这两个入口仍然出现，界面状态与真实会话不一致。

截图显示 Web 访问令牌、刷新令牌和 CSRF 值位于 Cookie 中，`localStorage` 与 `sessionStorage` 没有令牌数据，符合当前 Browser Cookie Profile 的安全设计。

## 目标

1. Web 首页通过服务端现有用户身份接口判断真实登录状态。
2. 服务端确认用户已登录时，不渲染“登录”和“创建账户”按钮容器。
3. 未登录时继续显示两个入口；“用户中心”链接、系统状态和首页其他内容保持不变。
4. 保持令牌只存在于既有 Cookie 安全边界，不向客户端存储、页面源码或组件状态复制令牌。
5. 补充登录前后行为测试，并完成桌面和移动端浏览器验证。

## 非目标

- 不修改 Cookie 名称、路径、有效期、`HttpOnly`、`SameSite`、`Secure` 或 CSRF 机制。
- 不修改登录、注册、刷新、退出、用户中心或 Backend API 契约。
- 不隐藏首页顶部的“用户中心”链接。
- 不修改 Admin 端界面或认证行为。
- 不连接或修改数据库数据，不提交、不推送、不发布镜像、不部署生产环境。

## 现状分析

1. `apps/web/src/app/page.tsx` 是动态 Server Component，但当前只获取系统状态，操作按钮无条件渲染。
2. `apps/web/src/lib/api/server.ts` 已提供 `fetchCurrentUser()`，会把请求 Cookie 服务端转发给 `/api/v1/users/me` 并以真实响应判断身份。
3. 用户中心已经复用该服务端身份查询，`401` 时重定向到登录页。
4. 首页属于公开页面。身份接口返回 `401` 时应继续显示登录与注册入口；服务端无法确认身份时也不能把用户误判为已登录。
5. 当前跨栈 E2E 已检查 Cookie Profile、客户端存储无令牌、首页桌面与移动端质量，但未断言首页操作按钮随登录态变化。

## 方案设计

1. 在服务端 API 工具中增加首页所需的明确登录状态查询，复用 `fetchCurrentUser()`，不解析 JWT，也不依据单个 Cookie 是否存在作结论。
2. 首页并行获取系统状态与登录状态，避免不必要的串行请求延迟。
3. 只有身份接口成功返回当前用户时隐藏整个 `.home-actions`；匿名或无法确认身份时保留登录与注册入口。
4. 在真实跨栈 Web E2E 中断言匿名首页显示两个入口，注册登录后返回首页不再显示两个入口，并继续检查客户端存储无令牌。
5. 运行 Web 类型、Lint、组件测试、覆盖率、构建及适用的桌面与移动端浏览器检查。

## 风险与回滚

1. 风险：首页会增加一次服务端身份查询。系统状态和身份查询并行执行，避免串行放大首屏延迟。
2. 风险：过期或已撤销 Cookie 不能当作有效登录态。实现以 `/api/v1/users/me` 的成功响应为准，不读取或信任 Cookie 内容。
3. 风险：身份服务暂时不可用时无法确认登录状态。公开首页继续显示登录和注册入口，不能误显示为已登录。
4. 回滚：恢复首页无条件渲染 `.home-actions` 并删除对应测试即可，不涉及数据或 API 契约回滚。
