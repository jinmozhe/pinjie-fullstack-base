# 请求日志错误入参捕获与脱敏管道实施计划

## 1. 当前状态和结果

- 当前状态：已结束
- 结果：已完成
- 用户已提出需求：为现有高性能请求日志流水线（Redis Stream）增加错误请求入参（Request Body）捕获能力，并按照最佳实践落地“异常触发 + 敏感字段脱敏 + 最大长度截断兜底”三位一体机制。
- 当前进度：已完成脱敏工具、请求流水线、数据库迁移、契约和 Admin 展示。

## 2. 关联需求

- `BASE-BE-002`：统一成功响应、业务异常和请求追踪机制，错误包含可定位的请求标识且不泄露敏感信息。
- `BASE-BE-006`：系统级公共能力入口，健康、配置、审计、限流和请求日志等能力统一承载。
- `BASE-SEC-003`：日志和错误不得泄露敏感信息，凭据、完整令牌、密码和敏感个人数据不进入日志或响应。
- `BASE-SEC-006`：请求与安全事件可审计、可追踪，关联 `request_id` 与 `trace_id`。
- `BASE-ADMIN-003`：管理端提供系统日志与安全事件的可视化扩展位置。
- `BASE-DB-002`：数据库结构变更必须通过 Alembic 迁移演进，支持空库与重复升级。
- `BASE-OPS-003`：后端新增逻辑与质量门禁对齐，维持 90% 以上行与分支测试覆盖率。

## 3. 背景

当前母版在 `apps/backend/app/core/request_metadata.py` 与 `scripts/consume_request_logs.py` 中实现了基于 Redis Stream 的请求日志流水线，主要收集 `request_id`、`trace_id`、`method`、`route_template`、`status_code`、`duration_ms` 等轻量元数据，并由后台 Worker 异步批量落库到 PostgreSQL 的 `request_logs` 表。

当前实现严格遵循了隐私合规和零开销原则，未保存请求正文（Request Body）。但在实际业务运维和 Bug 排查过程中，当接口发生 4xx 业务校验失败或 5xx 服务端崩溃时，缺乏请求入参现场会导致排查人员难以精准复现问题。

用户希望在**不损害正常流量极致性能**、**不发生敏感凭据泄露**、**不被恶意大报文击穿内存**的前提下，为系统引入业界最佳推荐实践的请求 Body 捕获机制。

## 4. 目标

1. **三位一体安全捕获**：实现“异常触发（方案 A） + 路由黑名单与敏感字段脱敏（方案 B） + 4KB 体积保险丝截断（方案 C）”的工业级流水线。
2. **正常流量零损耗**：所有 `2xx` 成功请求保持原有轻量元数据流，不读取、不解析、不存储 Body，系统 QPS 吞吐量不受任何影响。
3. **精准捕获错误现场**：当 `status_code >= 400` 时，自动捕获请求入参 JSON，使开发与运维人员能够依据 `request_id` 一秒复现 Bug。
4. **隐私数据强力防护**：敏感路由（如登录、改密、二次确认）强制跳过 Body 记录；业务接口中的敏感 key（如 `password`、`token`、`secret`、`credit_card` 等）自动替换为脱敏掩码 `***`。
5. **内存与磁盘兜底防爆**：设置最大 Body 字符长度上限（默认 4096 字符），超出部分安全截断并附加 `...[truncated]` 标识，防止恶意超大请求打穿 Redis 内存与数据库。
6. **数据与管理端支持**：通过 Alembic 迁移为 `request_logs` 表补充 `request_body` 字段，并在 Admin 管理端日志详情中支持高亮展开查看入参。

## 5. 非目标

- 不对 `2xx` 成功请求记录请求正文。
- 不记录大文件上传（`multipart/form-data`）的二进制内容。
- 不记录响应正文（Response Body），响应结构已由 OpenAPI 契约和统一异常结构保证。
- 不将明文密码、会话 Token 或未经脱敏的敏感信息写入 Redis 或数据库。
- 不改变现有的 Redis Stream 削峰填谷与后台 Worker 批量消费架构。

## 6. 现状分析

| 模块/环节 | 当前实现 | 升级目标 |
| --- | --- | --- |
| 数据库模型 | `RequestLog` 仅包含 `request_id`、`method`、`duration_ms` 等 11 个元数据字段 | 增加 `request_body: Mapped[str \| None]` 字段，支持空值与大文本 |
| 数据迁移 | 仅有 20260815 阶段 C 迁移 | 新增 Alembic 迁移脚本，安全变更数据表结构 |
| API 请求拦截 | `publish_request_log` 仅提取请求元数据字段 | 拦截器判断错误状态码，对入参提取、脱敏、截断后存入 Stream 字段 `request_body` |
| 消息流字段 | Redis Stream 字段仅包含元数据字符串 | Stream 字段中按需增加 `request_body` 键值 |
| Worker 消费 | `_request_log()` 构造函数映射 11 个字段 | 映射并持久化 `request_body` 到 PostgreSQL |
| 管理端展示 | Admin 安全日志展示基本元数据 | 在请求日志抽屉/弹窗中，当存在 `request_body` 时以 JSON 格式化展示 |

## 7. 方案设计

### 7.1 捕获与脱敏流水线架构

```text
HTTP 请求进入 -> 业务处理/异常捕获 -> 产生响应 (status_code)
  │
  ├─ status_code < 400 (正常 2xx/3xx) ──> request_body = None (零开销跳过)
  │
  └─ status_code >= 400 (错误 4xx/5xx) ──>
        │
        ├─ 检查路由黑名单 (如 /auth/login, /change-password) ──> 命中则跳过 (防密码泄露)
        │
        ├─ 尝试解析为 JSON 并递归执行敏感字段正则掩码脱敏 (password -> ***)
        │
        ├─ 限制最大字节数 4096，超出执行字符串切片截断并标记 ...[truncated]
        │
        └─ 赋值为 request_body 字符串
  │
  ▼
写入 Redis Stream (XADD fields) -> 后台 Worker 消费 -> 写入 PostgreSQL (request_logs)
```

### 7.2 敏感字段脱敏规则与敏感路由黑名单

- **黑名单路由（强制不存 Body）**：
  - `/api/v1/auth/login`
  - `/api/v1/admin/auth/login`
  - `/api/v1/account/change-password`
  - `/api/v1/admin/account/change-password`
  - `/api/v1/admin/account/confirm`
- **敏感字段脱敏匹配正则（包含但不限于）**：
  - `password`、`new_password`、`current_password`、`confirm_password`
  - `token`、`access_token`、`refresh_token`、`csrf_token`、`secret`
  - `id_card`、`credit_card`、`cvv`、`cvc`、`card_number`

### 7.3 数据库模型与 Alembic 迁移设计

给 `apps/backend/app/db/models/identity.py` 中的 `RequestLog` 增加：

```python
request_body: Mapped[str | None] = mapped_column(
    Text,
    nullable=True,
    comment="脱敏后的错误请求入参，正常请求为 NULL",
)
```

生成新的 Alembic 迁移脚本 `20260820_01_request_logs_add_body.py`，执行 `op.add_column("request_logs", sa.Column("request_body", sa.Text(), nullable=True))`。

### 7.4 Admin 管理端可视化适配

- 在管理端的安全日志/请求日志表格中，对存在 `request_body` 的异常记录增加“查看入参”操作。
- 点击后以只读 JSON 代码块弹窗展示脱敏后的请求参数，极大便利问题排查与复现。

## 11. 风险与回滚

| 风险 | 影响 | 预防措施 | 回滚方案 |
| --- | --- | --- | --- |
| 敏感字段漏脱敏 | 少量自定义密码字段泄露进日志 | 采用泛化正则匹配（包含 `pass*`, `secret*`, `*token*` 等模糊匹配）并结合路由黑名单双重过滤 | 数据库执行清空敏感日志，更新脱敏正则 |
| Request Stream 读取耗尽 | 导致业务代码读取 Request 失败 | 在中间件或依赖层通过规范机制获取解析后的 JSON 对象，或在错误响应终结时提取 | 恢复原 `publish_request_log` 逻辑 |
| 数据库迁移失败 | 阻碍持续部署 | 编写纯 `nullable=True` 增量迁移，保证向下兼容 | 执行 `alembic downgrade -1` 回退字段 |
