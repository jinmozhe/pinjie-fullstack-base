## 3. 背景

仓库已经建立 PRD、全项目索引、计划、ADR、应用级规则、OpenAPI 唯一来源和 Git 追溯边界，但当前仍处于工程骨架阶段，尚无运行中的 Backend、Admin、Web 业务源码和测试。

现有规则主要表达原则，以下工程缺口已经核实：

1. Backend 和 Frontend CI 在源码、测试或锁文件不完整时会成功跳过质量检查。
2. OpenAPI 契约漂移检查仍是 `TODO` 占位步骤。
3. 生产工作流由 `main` 推送直接触发，CI、镜像发布和生产部署职责未完全隔离。
4. 生产 Compose 和发布工作流允许使用可变的 `latest` 镜像标签。
5. Backend 领域边界和前端 Feature 边界只有文字约束，尚无依赖方向门禁。
6. 仓库尚无 `SECURITY.md`、`CODEOWNERS`、Pull Request 风险模板和软件供应链扫描基线。
7. 当前单机 1Panel 部署缺少可恢复模式、高可用模式、SLO、RTO、RPO 和恢复演练边界。
8. GitHub 远端分支保护、Ruleset、环境审批和漏洞告警状态因本地 GitHub CLI 未认证而尚未核验。

需要在业务开发前建立统一治理基线，并把能够机械验证的红线转成违反即失败的仓库门禁。

## 4. 目标

1. 确立“模块化单体、领域所有权、单向依赖、Fail Closed、受控迁移窗口、不可变发布物和全链路追溯”的长期基线。
2. 明确定义禁止兜底、禁止永久或隐式兼容、模块边界、认证授权、测试、迁移、发布和 AI 开发规则。
3. 把产品验收边界、技术决策、当前机制、运维步骤和 Agent 执行规则分别写入正确的权威来源。
4. 建立符合空骨架阶段的 CI 状态机，任何部分实现、缺失门禁或伪装成功必须失败。
5. 建立 OpenAPI、模块依赖、文本、安全供应链和不可变发布的自动检查路径。
6. 为后续工程基础设施和通用业务能力开发提供可直接引用的规则和验收清单。
7. 保持母版业务中立，不在本阶段引入具体业务实现。

## 5. 非目标

1. 不新增或修改 Router、Service、Repository、Model、Schema 和领域业务逻辑。
2. 不实现登录、用户、RBAC、审计、限流、缓存、健康探针和可观测性运行代码。
3. 不新增数据库业务表、Alembic 业务迁移或种子数据。
4. 不实现 Admin 页面、Web 页面、业务组件和业务 E2E 流程。
5. 不接入真实生产密钥、域名、数据库、Redis、1Panel 或其他生产资源。
6. 不自动提交、推送、发布镜像、创建 Git Tag、部署或修改生产环境。
7. 不在本阶段承诺具体 SLO、RTO、RPO 数值；具体数值由派生项目依据业务确认。
8. 不把当前单机 Compose 描述为高可用部署。

阶段 B 工程基础设施会涉及应用运行源码和测试基础设施，阶段 C 通用业务能力会涉及核心业务代码。两者均不属于本计划，未来必须分别创建新的全栈计划，并引用本计划产出的规则和架构决策。

## 7. 方案设计

### 7.1 总体原则

采用以下基线：

```text
模块化单体
-> 领域所有权和公开端口
-> 单向依赖与机械门禁
-> 明确失败和受控故障隔离
-> 受控迁移兼容窗口
-> 不可变构建与部署
-> 从需求到运行请求的证据链
```

当前不拆分微服务。只有出现独立团队、独立发布、独立扩缩容、明确数据所有权和可承担分布式成本等证据后，才通过新 ADR 评估服务拆分。

### 7.2 模块与依赖边界

Backend 采用以下长期边界：

- Router 禁止直接访问 Repository、Model 或数据库 Session。
- Service 承载业务规则和事务；Repository 只负责持久化，不得自行 `commit`。
- 领域禁止导入其他领域的 Repository、Model 和内部实现。
- 跨领域调用只能通过公开 Application Service、Port、DTO 或领域事件。
- 跨领域写流程由 `app/services/` 应用编排层负责，领域只能写入自己拥有的数据表。
- 普通写模型禁止跨领域 JOIN；报表、搜索和只读聚合使用独立 Query Service 或 Read Model。
- 使用 `import-linter`、AST 架构测试或经验证的等价工具建立 CI 门禁。

Frontend 采用以下长期边界：

- Web 与 Admin 保持物理隔离，只通过公共包和后端契约共享。
- 页面或路由只负责入口与编排，Feature 内部实现不得被其他 Feature 直接导入。
- 跨 Feature 复用必须提升为业务中立的公共组件、基础设施或明确公共 API。
- TanStack Query 管理服务端数据；Zustand 只管理非敏感客户端状态，不保存 Token 或服务端数据副本。
- 缓存新鲜度按数据语义设置，允许统一默认值，不全局禁止 `staleTime: 0`。

### 7.3 禁止兜底与失败模型

禁止以下模式：

- 捕获异常后返回 `None`、空集合、默认值或假成功。
- Router 捕获业务异常后返回 HTTP 200。
- 配置缺失时启用弱密钥、默认管理员、默认生产地址或不安全模式。
- 外部依赖失败后伪造完整业务结果。
- 生成、测试、迁移或安全检查未执行却允许发布。
- 使用 Mock、SQLite 或假数据替代明确要求真实 PostgreSQL 的验收。
- 镜像版本缺失时自动使用 `latest`。

允许超时、有限重试、熔断、背压、明确只读状态、HTTP 失败响应和前端错误边界，但必须具有正式契约、日志、指标、告警和恢复条件，不得静默发生。

统一错误模型至少覆盖 `400`、`401`、`403`、`404`、`409`、`412`、`422`、`429`、`502`、`503`、`504` 和 `500`。全局 `500` 处理器只负责隐藏内部信息、返回关联 ID 并记录未处理异常，不承担业务降级。

### 7.4 受控迁移兼容

禁止永久兼容、隐式兼容、自动猜测协议版本和无期限双轨。为支持无停机或滚动发布，允许经过确认的短期 Expand、Migrate、Contract 迁移窗口。

每项临时兼容必须具备计划或 ADR 依据、负责人、删除日期、适用消费者、观测指标、回滚条件和删除测试。完成迁移后必须删除临时兼容。

Breaking Change 包括删除字段、改变字段语义或类型、改变 HTTP 方法或路径、收紧调用方可见约束以及改变错误契约。跨栈 Breaking Change 必须在同一计划内完成 Backend、OpenAPI、API Client、Admin 和 Web 的同步或明确不涉及依据。

### 7.5 认证、授权与审计职责

- Middleware：请求 ID、Trace 上下文、安全头和日志上下文。
- Dependency：身份凭据解析、会话校验和通用权限依赖。
- Router：声明端点需要的身份和权限。
- Service/Policy：执行依赖资源归属、资源状态和业务数据的授权。
- Database：执行唯一约束、外键和适合数据库保证的数据不变量。

浏览器凭据优先使用 `HttpOnly`、`Secure`、`SameSite` Cookie。授权默认拒绝，客户端隐藏不得代替服务端判断。管理员登录、权限变化、账号禁用、数据导出和其他高风险操作必须进入脱敏审计链。

### 7.6 测试与质量策略

后续源码实现采用五层验证：

| 层级 | 验证目标 | 主要约束 |
| --- | --- | --- |
| 领域单元测试 | 纯业务规则、状态转换和边界值 | 不访问真实数据库，不 Mock 被测对象内部实现 |
| Service 测试 | 编排、授权、事务和失败行为 | 通过 Port、Fake 或 Stub 隔离外部依赖 |
| Repository 集成测试 | 查询、约束、并发和持久化语义 | 使用真实独立 PostgreSQL `_test` 数据库 |
| API 测试 | 认证、授权、输入、错误和响应契约 | 使用真实应用入口和受控依赖 |
| 跨栈 E2E | 关键用户流程和契约集成 | 覆盖关键成功与失败路径 |

同时建立架构依赖、Alembic 空库升级和重复升级、OpenAPI 漂移、权限矩阵、幂等、并发、故障路径及前端桌面和移动端验证。覆盖率是风险信号，不作为唯一质量目标。

### 7.7 空骨架与 CI Fail Closed 状态机

当前仓库没有业务源码，CI 既不能伪装成完整应用验证通过，也不能因合法空骨架永久失败。每个应用采用三态完整性检查：

1. `empty`：规定的源码、锁文件和测试入口均未开始，明确报告“工程骨架未实现”，只运行当前可执行的治理检查。
2. `partial`：任意入口已出现但其他必要项缺失，必须失败，禁止部分实现进入主分支。
3. `ready`：必要源码、锁文件和测试入口全部存在，必须运行完整 Lint、类型、测试、构建、迁移或契约门禁。

工作流名称、Job 名称和 Summary 必须区分“治理检查通过”与“应用质量检查通过”。首次工程基础设施计划必须把相关应用推进到 `ready`，不得通过删除入口退回 `empty`。

Backend 尚未进入 `ready` 时只验证 OpenAPI 占位状态没有被部分修改；Backend 进入 `ready` 后必须重新导出契约、重新生成客户端并以 Git 差异作为失败条件。

### 7.8 安全开发与供应链

采用 NIST SSDF、OWASP ASVS、CISA Secure by Design 和 SLSA 作为参考基线，结合项目风险落地：

- 建立 `SECURITY.md`、`.github/CODEOWNERS` 和 Pull Request 模板。
- 定义漏洞等级、修复时限、高风险变更和专项评审要求。
- 规划秘密扫描、SAST、依赖漏洞和容器漏洞扫描。
- GitHub Actions 使用最小 `permissions`，第三方 Action 固定完整 Commit SHA。
- 发布阶段生成 SBOM 和构建来源证明。
- 远端分支保护、Ruleset、环境审批和漏洞告警在具备认证后先只读核验，再单独取得配置授权。

安全扫描不得使用无期限 `continue-on-error`。初次接入发现既有问题时，记录基线、责任人和清理期限；新问题立即阻断。

### 7.9 不可变发布与物理追溯

- 每次构建绑定完整 Commit SHA，镜像至少提供 `sha-<commit>` 标识。
- 生产部署固定镜像 digest，禁止使用 `latest` 或其他可变标签作为部署依据。
- Git Tag、GitHub Release、镜像发布和生产部署保持独立授权。
- 正式母版版本默认评估 SemVer；若采用 CalVer，必须新增 ADR。
- CI、镜像发布和生产部署拆分为独立工作流，生产部署具备环境审批、并发锁和回滚入口。

目标追溯链：

```text
BASE 需求
-> 实施计划
-> ADR 或威胁模型
-> Pull Request 与评审
-> Commit SHA
-> CI 证据
-> SBOM 与构建来源证明
-> 镜像 digest
-> Alembic Revision
-> 部署记录
-> release.version
-> request_id、trace_id 和 audit_id
```

### 7.10 可靠性与部署等级

| 等级 | 定位 | 最低要求 |
| --- | --- | --- |
| 单机可恢复模式 | 当前 1Panel 默认路径，允许短时中断 | 不可变版本、健康检查、备份、恢复验证和快速回滚 |
| 多实例高可用模式 | 有明确连续性需求的派生项目 | 多应用实例、负载均衡、数据层高可用、故障转移和滚动发布 |

后续工程设计覆盖 Liveness、Readiness、Startup 探针、优雅停机、请求和依赖超时、连接池与并发边界、日志、指标、Trace、告警、容量测试和事故处理。具体 SLI、SLO、错误预算、RTO 和 RPO 由派生项目依据用户链路和业务损失确认。

### 7.11 AI 开发与高风险变更

- AI 必须先读取索引、适用规则、活动计划和权威文档。
- 实现类任务必须创建或继续原计划并取得用户确认。
- AI 不得降低安全、测试、类型、迁移、契约和发布门禁。
- 修改缺少测试覆盖的区域时必须补测试；无法补充时记录未验证风险，不得宣称完成。
- AI 可以在隔离测试数据库验证迁移；共享开发库、预发布和生产迁移需要人工审查与明确授权。
- 不可逆迁移必须具有备份、恢复、数据校验和专项确认。
- 生产部署工作流、权限模型、公开 API、数据库删除和安全配置属于高风险变更。
- AI 不得自动提交、推送、打 Tag、发布、部署或执行生产操作。

## 8. 全栈影响矩阵

| 范围 | 是否涉及 | 工作内容 | 前置依赖 | 验证 |
| --- | --- | --- | --- | --- |
| Backend | 涉及 | 定义分层、领域依赖、失败、授权、测试与迁移规则；不实现业务源码 | 本计划确认 | 规则复读、依赖门禁配置验证 |
| Admin | 涉及 | 定义 Feature、API、状态、安全与就绪门禁；不实现页面 | 本计划确认 | 规则复读、配置检查 |
