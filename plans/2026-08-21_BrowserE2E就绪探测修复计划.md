# Browser E2E 就绪探测修复计划

## 当前状态和结果

- 状态：已结束
- 结果：已完成

## 关联需求

- 无。本计划修复既有 Browser E2E 工作流的就绪探测缺陷，不改变产品能力或验收边界。

## 背景

2026-08-21 读取 GitHub Actions 运行 `32390365537` 的失败日志后确认，当前提交的 Backend、Frontend、Governance 和 Security 工作流均通过，Browser E2E 在 Admin 跨栈用例中失败。失败响应为 HTTP 2xx HTML，测试随后将其作为 JSON 解析并抛出 `Unexpected token '<'`。

线上时间线显示浏览器测试已经开始后，Admin Webpack 才完成首次编译。当前 E2E 启动器只检查 `/umi.js` 是否返回 2xx，Umi 编译期间的 HTML 回退页也会满足该条件，导致启动器过早放行。

## 目标

- Admin E2E 只在 `/umi.js` 返回真实 JavaScript 资源后启动 Playwright。
- 保留现有 Web、Admin、Backend、数据库和 Redis 启动方式及全部跨栈断言。
- 为错误响应提供可直接定位就绪探测问题的验证依据。

## 非目标

- 不修改 Backend 登录接口、Cookie Profile、CSRF 或 RBAC 行为。
- 不修改 Admin 页面、交互和视觉样式。
- 不弱化登录响应不得包含 Token 的安全断言。
- 本地修复完成后不自动提交、推送或重跑线上工作流。

## 现状分析

- `scripts/e2e/run-e2e.mjs` 的 `isAvailable` 只判断 `response.ok`。
- Admin 启动等待地址为 `http://127.0.0.1:3001/umi.js`。
- Umi 初次编译完成前可能对该地址返回 2xx HTML 回退页。
- 当前失败用例在 Admin 编译完成前调用登录 API，经开发服务器得到 HTML 后在 `response.json()` 处失败。

## 方案设计

扩展 E2E 启动器的服务探测条件，使调用方可以声明预期响应类型。Web 首页继续沿用 2xx 判定；Admin `/umi.js` 除 2xx 外还必须返回 JavaScript Content-Type。探测失败时继续等待，并保持现有 120 秒超时、子进程退出检测和清理逻辑。

## 风险与回滚

- 若 Umi JavaScript 响应类型与预期不一致，Admin 服务会等待到超时。实现应接受标准 JavaScript MIME 类型，并通过本地实际响应验证。
- 更严格的就绪条件可能延长 Browser E2E 启动时间，但不会改变 120 秒总超时。
- 回滚时恢复启动器原有的 2xx 判定即可，不涉及业务数据和线上状态。

## 实施结果

- E2E 启动器支持按服务声明预期 Content-Type；Web 保留 2xx 就绪条件，Admin `/umi.js` 必须返回 JavaScript 类型。
- Admin 登录响应在 JSON 解析前校验 `application/json`，代理回退为 HTML 时会直接报告响应类型不符。
- 真实 Umi dev server 完成首次编译后，`/umi.js` 返回 `200 application/javascript; charset=utf-8`；同一服务的 2xx HTML 首页被新条件拒绝。
- Playwright 已成功发现受影响的 Admin Desktop 用例；Markdown、文本编码、工作区、模块边界、Node 语法和 Git 差异检查均通过。
