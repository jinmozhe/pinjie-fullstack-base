## 背景

公开注册当前由 Backend 启动环境变量 `REGISTRATION_MODE=open|closed` 控制。该方式适合部署参数，但管理员运行时修改需要重启，缺少配置级权限、并发控制和审计，也无法在 Admin 提供完整保存状态。

Web 根 Metadata 和多处品牌文本仍固定为 `Pinjie`。项目需要让管理员维护站点名称、LOGO、标题、关键词和描述，并由 Web 服务端可靠消费。同时需要为未来邮箱、支付等设置保留扩展能力，避免每个配置域产生一张只有一行的表。

### 方案演进

1. **环境变量**：适合数据库地址、密钥、Cookie 策略和存储根目录等启动参数；不适合运行时业务设置。站点资料和注册开关不继续以 env 为权威来源。
2. **本地 JSON**：单机简单，但容器和多实例下存在副本一致性、锁、原子写入、权限、备份和持久卷问题；不采用。
3. **每个配置域一张表**：列级类型明确，但会产生大量单行表、模型、迁移和仓储；用户已明确放弃。
4. **每项配置一行并保存 `key/type`**：适合动态配置平台，但同一 Tab 需要跨多行事务，类型元数据、Backend Schema 和前端组件会形成多份事实；本阶段不建设动态表单。
5. **单表、分组行、JSONB 值**：一个 Tab 对应一条记录，Backend 固定 Schema，Admin 固定组件，revision 保护并发；确定为最终方案。
6. **LOGO 作为普通资产**：普通资产面向多文件、上传主体、列表和独立生命周期；站点 LOGO 是唯一槽位和覆盖更新语义。最终确定为独立配置媒体，不进入 `assets` 表。

## 目标

- 创建单一 `system_settings` 表，第一阶段只建立 `site` 与 `registration` 两条固定分组记录。
- Backend 按分组使用固定 Pydantic Schema，Admin 按 Tab 使用固定 Ant Design 组件。
- 站点设置支持名称、LOGO、标题、关键词和描述。
- 注册开关以 PostgreSQL 为唯一权威来源；读取失败、缺行或内容无效时不开放注册。
- Web 使用站点资料生成 Metadata 和公共品牌；Admin 继续固定使用 `Pinjie Console`。
- LOGO 使用固定媒体槽位、安全校验、原子替换和失败补偿，不关联文件资产。
- 配置写入经过管理员会话、CSRF、准确权限、revision 乐观并发和审计。
- 移除 `REGISTRATION_MODE` 永久双轨。
- 后续设置沿用“固定分组、固定 Schema、固定接口、固定 Tab”的扩展方式。

## 非目标

- 不建设动态表单、低代码配置平台或数据库驱动组件渲染器。
- 不增加逐字段 `setting_key`、`value_type` 或 `component_type`。
- 不允许客户端访问任意分组或写入任意 JSON。
- 不把数据库、Redis、密钥、Token 和存储根目录等部署参数迁入数据库。
- 不实现邮箱、短信、支付、主题等后续配置。
- 不修改 Admin 登录页、控制台 LOGO 和 `Pinjie Console` 名称。
- 不把配置媒体写入 `assets` 表或展示在文件资产页。
- 不支持 SVG、GIF、动画 WebP、远程图片导入、裁剪和图片编辑。

## 方案设计

### 1. 数据表

新建 `system_settings`：

| 字段 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| `id` | `UUID` | 主键，UUID v7 | 项目统一标识 |
| `setting_group` | `VARCHAR(50)` | `NOT NULL`、唯一 | 固定分组名 |
| `setting_value` | `JSONB` | `NOT NULL`、根值必须为 Object | 一个 Tab 的完整值 |
| `revision` | `INTEGER` | `NOT NULL`、默认 1、`CHECK > 0` | 乐观并发修订号 |
| `updated_by` | `UUID` | 可空，外键 `admins.id`，删除管理员时置空 | 最后修改者 |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL` | 创建时间 |
| `updated_at` | `TIMESTAMPTZ` | `NOT NULL` | 更新时间 |

数据库增加 `UNIQUE(setting_group)`、`CHECK(jsonb_typeof(setting_value) = 'object')` 和 `CHECK(revision > 0)`。分组名不做数据库枚举，方便以后迁移新增分组；应用层仍只允许源码声明的分组。

`revision` 表示记录修改次数，不表示数据库迁移版本或 JSON Schema 版本。客户端读取 revision 7 后提交，Backend 只在数据库仍为 7 时接受并写为 8。数据库已为 8 时返回 `412 SETTINGS_REVISION_MISMATCH`，防止静默覆盖。

### 2. 初始记录与固定 Schema

Alembic 迁移插入两条记录，应用启动不隐式补种：

```json
{
  "setting_group": "site",
  "setting_value": {
    "name": "Pinjie",
    "logo": null,
    "title": "Pinjie",
    "keywords": [],
    "description": "通用全栈应用基础"
  },
  "revision": 1
}
```

```json
{
  "setting_group": "registration",
  "setting_value": { "enabled": false },
  "revision": 1
}
```

字段和组件一一对应：

| 分组 | 字段 | Backend 约束 | Admin 组件 |
| --- | --- | --- | --- |
| `site` | `name` | 去首尾空格，1 至 100 字符 | `Input` |
| `site` | `logo` | `null` 或服务端生成的媒体元数据 | `Upload` + `Image` |
| `site` | `title` | 去首尾空格，1 至 150 字符 | `Input` |
| `site` | `keywords` | 去空项、稳定去重，最多 20 项，每项最多 64 字符 | `Select mode="tags"` |
| `site` | `description` | 去首尾空格，最多 500 字符，可为空 | `Input.TextArea` |
| `registration` | `enabled` | 严格布尔值 | `Switch` |

所有 Schema 使用 `extra="forbid"`。数据库 JSON 缺字段、含未知字段或类型错误时明确失败并记录错误，不能猜测、补齐或返回假成功。

`logo` 内部值固定为：

```json
{
  "path": "site/logo.png",
  "mime_type": "image/png",
  "file_size": 48321,
  "sha256": "64位小写十六进制摘要"
}
```

只保存相对路径和可信元数据，不保存绝对路径、资产 ID、上传原名或公开域名。公开 URL 由 Backend 按基础路径和 revision 生成，例如 `/static/settings/site/logo.png?v=7`。

### 3. Backend 分层与接口

- Model 描述表结构。
- Repository 负责固定分组读取、`FOR UPDATE`、revision 条件更新和数据库异常传播。
- `SystemSettingsService` 负责 Schema 解析、读取、更新、审计和错误映射。
- `SettingsMediaService` 负责 `site_logo` 槽位、校验、暂存、原子替换、补偿和 URL。
- Admin Router 负责管理员会话、CSRF、权限和强类型响应。
- Public Router 只公开站点资料和最小能力，不暴露 revision、updated_by、哈希或内部路径。

禁止提供接受任意 `{group}` 的通用读写接口。固定接口为：

```text
GET    /api/v1/admin/settings/site
PATCH  /api/v1/admin/settings/site
PUT    /api/v1/admin/settings/site/logo
DELETE /api/v1/admin/settings/site/logo
GET    /api/v1/admin/settings/registration
PATCH  /api/v1/admin/settings/registration

GET /api/v1/system/site-profile
GET /api/v1/system/capabilities
```

契约规则：

- Admin GET 返回分组值、revision、updated_at 和可公开的修改者摘要。
- `PATCH site` 使用局部更新语义：revision 必填，四个文字字段均可选但至少提供一项；Service 与当前 JSON 合并后使用完整 Site Schema 校验，始终保留现有 logo，客户端提交 logo 字段按未知字段拒绝。
- `PATCH registration` 必须携带 revision 与 enabled，不提供局部空更新。
- Logo PUT 使用 multipart `file + revision`；DELETE 使用 `revision` 查询参数；均返回完整站点设置和新 revision。
- revision 冲突返回 HTTP 412 与稳定错误码 `SETTINGS_REVISION_MISMATCH`。
- 参数错误为 422，权限不足为 403；缺行、JSON 无效、数据库或媒体存储故障为明确 503。
- `site-profile` 只返回 `name`、`logo_url`、`title`、`keywords`、`description`。
- `capabilities` 继续只返回 `registration_enabled`。
- 公共响应继续使用项目统一 `ResponseModel[T]`。不增加单字段、动态 `{group}/{key}` 或 `fields=` 接口；只需要 LOGO 等部分字段的 Web 消费者仍读取完整 SiteProfile 后在本地选择，完整响应保持强类型且体积受控。
- Admin GET 的修改者摘要固定为 `updated_by: { id, display_name } | null`；迁移初始记录或管理员已经不存在时返回 null，不额外暴露用户名、角色或权限。

### 4. 注册 Fail Closed 与并发

公开注册与关闭开关使用确定的数据库顺序：

1. 注册事务读取 `registration` 行并取得共享锁。
2. 缺行、内容无效、`enabled=false` 或数据库异常时不创建用户；数据库异常返回 503。
3. 开启时在同一事务继续用户、会话和安全事件创建。
4. Admin 更新开关取得排他行锁并校验 revision。
5. 注册先取得锁时，该笔注册在关闭提交前完成；关闭先提交时，后续注册读取关闭并被拒绝。

`GET /system/capabilities` 读取异常也返回 503。Web 将其映射为 unavailable，隐藏注册入口并阻止显示注册表单。前端隐藏不承担安全控制，注册 POST 始终再次检查数据库。

实施时移除 `REGISTRATION_MODE`。升级前即使 env 为 `open`，迁移初始值仍为 `false`，管理员需要明确重新开启，这是有意的安全默认行为。

### 5. 权限与审计

新增可分配权限：

```text
settings:site:read
settings:site:update
settings:registration:read
settings:registration:update
```

- 超级管理员沿用现有规则自动拥有全部权限。
- 至少拥有一个设置读取权限时显示菜单；两个 Tab 分别判断 read/update。
- 有 read 无 update 时显示只读表单，不显示保存、上传和删除动作。
- LOGO 上传和删除归 `settings:site:update`，不复用资产权限。
- 权限目录版本递增，目标环境继续先 `--check`，经独立授权后 `--apply`。

审计动作固定为 `settings.site.update`、`settings.site.logo.update`、`settings.site.logo.delete`、`settings.registration.update`。changed_fields 只记录变化字段和安全媒体元数据，不记录二进制内容。

### 6. 独立配置媒体

新增公开模板配置：

```text
SETTINGS_MEDIA_ROOT=本地可写根目录
SETTINGS_MEDIA_BASE_URL=/static/settings
```

生产固定使用 `/app/storage/settings`，继续复用现有 `/app/storage` 持久卷。正式目录、staging 和 trash 位于同一文件系统，只有正式 settings 目录可以被静态访问。

首个槽位固定为：

```text
slot: site_logo
directory: site/
basename: logo
result: site/logo.png | site/logo.jpg | site/logo.webp
```

安全策略：

- 最大 2 MiB，请求层和流式暂存层都限制，禁止无界读入内存。
- 只接受 PNG、JPEG、WebP 静态图片。
- 扩展名由 Magic Number、完整解码格式和真实 MIME 共同决定，不信任原文件名和客户端 Content-Type。
- 服务端统一把 JPEG 映射为 `.jpg`，PNG 映射为 `.png`，WebP 映射为 `.webp`，不产生 `.jpeg` 双轨。
- 禁止 SVG、GIF、动画 WebP、损坏和截断图片。
- Pillow 是本阶段必需运行依赖，用于完整解码；最长边不超过 4096 像素，总像素不超过 1600 万，拒绝解压炸弹。
- 首阶段保留合法原始字节，不裁剪、不重新编码。

部署拓扑边界：本地配置媒体只支持单 Backend 实例，或全部实例挂载同一可读写共享文件系统。多个实例各自使用独立本地目录会产生媒体不一致，属于不支持配置；未来多节点部署必须通过专项计划切换到共享存储或对象存储。PostgreSQL 继续作为元数据权威来源。

上传一致性流程：

1. 流式写入同卷 staging，同时计算字节数和 SHA-256。
2. 校验 Magic Number、MIME、解码、帧数、尺寸和像素数。
3. 开启事务，`FOR UPDATE` 锁定 site 行并校验 revision。
4. 根据真实格式确定固定目标名，生成持久化操作清单，记录操作 ID、旧新元数据、预期 revision、正式路径、staging 和 trash 路径；清单与目录都执行 fsync。
5. 将旧 LOGO 和其他允许后缀的同名文件移动到可恢复 trash。
6. 用 `os.replace` 将 staging 原子替换到正式路径，更新并 fsync 操作清单状态。
7. 更新 JSON、revision、updated_by 和审计事件。
8. 数据库提交成功后把清单标记为已提交，再清理旧文件和清单；清理失败记录 Critical 日志并保留人工清理候选。
9. 数据库提交失败时删除新文件并恢复旧文件；恢复失败返回 503并记录 Critical，禁止报告成功。

应用启动在对外就绪前扫描未完成操作清单：数据库仍是旧 revision 与旧元数据时恢复旧文件；数据库已经是预期新 revision 且哈希匹配时完成清理；其他组合视为未知状态，记录 Critical、使设置媒体恢复检查失败并拒绝 Readiness，禁止自动猜测。孤立 staging/trash 不按年龄静默删除，必须由有审计输出的维护流程处理。

删除采用相同补偿模型：锁行、校验 revision、暂存删除、写 `logo=null`、提交后清理；提交失败恢复。跨扩展名更新清理旧后缀。公开 URL追加 revision 查询参数解决浏览器缓存。

数据库存在 logo 元数据但正式文件缺失、哈希或 MIME 不匹配时，公共 site-profile 返回 503并记录 Critical，Web 使用内置品牌回退；Admin 读取明确显示媒体异常。重新上传允许修复漂移并写审计，删除也允许清空失效元数据并记录修复原因。

### 7. Admin 固定页面

新增独立 `/settings`“系统设置”页面，保留 `/system` 作为只读“系统状态”。至少拥有一项 settings read 权限时显示菜单；只渲染有 read 权限的 Tab，默认激活第一个可读 Tab。没有任何 read 权限时客户端路由显示无权限页，Backend 仍逐端点拒绝。

**站点设置 Tab**：

- 请求完成后再初始化 Form，失败时不能用空默认值覆盖数据库。
- 名称和标题用 Input，关键词用 tags Select，描述用 TextArea 和 500 字符计数。
- LOGO 使用受控 Upload、自定义请求与 Image 预览，展示格式和大小。
- 普通文字字段由 Tab 内保存按钮一次提交；LOGO 上传和删除独立提交。
- Logo 操作成功会产生新 revision。页面只更新 logo 与 revision，必须保留尚未保存的名称、标题、关键词和描述草稿。

**注册设置 Tab**：

- Switch 表示开放或关闭，使用独立保存按钮。
- 开启时说明公开注册影响，不增加危险操作弹窗。
- 成功后使用响应刷新当前值和 revision。

两 Tab 均覆盖加载、失败重试、无权限、只读、保存中、成功和 412 冲突。冲突时保留草稿并要求用户重新加载，禁止自动覆盖或自动重试写入。

### 8. Web 消费与品牌边界

- 新增 server-only `fetchSiteProfile()`，所有 Web 消费者统一读取完整 SiteProfile，再在本地选择需要的字段。同一次服务端渲染内去重，每个新的服务端请求重新读取，公共配置响应使用 `Cache-Control: no-store`。
- `generateMetadata()` 异步读取：default title 使用 `site.title`，template 使用 `%s | ${site.name}`，并映射 keywords 和 description。
- `apps/web` 内首页、登录、注册、账户中心及后续面向用户的品牌位置统一使用站点名称与 LOGO；Admin 完全隔离。
- 站点资料 503 或无 LOGO时，Web 使用内置 `Pinjie/PINJIE` 展示回退；展示回退不参与注册安全判断。
- 新增 `/static/settings/[...path]` 同源代理，沿用 uploads 代理的路径归一化、父路径拒绝、方法白名单、响应头过滤和错误处理。
- 带 revision 的 LOGO 响应使用长期浏览器缓存；新 revision 生成新 URL。SiteProfile 本身不缓存，确保下一次页面请求读取最新资料。
- Admin 的登录 Logo、控制台 Logo 和 `Pinjie Console` 不调用 site-profile。

### 9. 契约、迁移和部署顺序

公开 API 变化按“Backend 实现、导出根 `openapi.json`、运行 `pnpm generate-api`、Admin/Web 适配”顺序完成，生成文件禁止手工编辑。

Alembic upgrade 创建表、约束并用固定 UUID v7 插入两条初始记录。downgrade 删除表，但不自动删除配置媒体，避免不可恢复损失。应用回滚必须使用完整旧版本，并恢复旧版本需要的 `REGISTRATION_MODE`；不能只降数据库。

部署同步：

- 从 Settings、`.env.example`、Compose 和运维文档移除 `REGISTRATION_MODE`。
- 增加配置媒体根目录和公开基础路径模板。
- Dockerfile 创建 settings 目录并赋予运行用户权限；Compose 不新增卷。
- 备份同时覆盖 PostgreSQL 与 `/app/storage/settings`，使用同一备份窗口。
- 升级说明明确注册默认关闭，需要管理员按业务需要重新开启。

### 10. 后续扩展原则

新增邮箱、支付等设置时：

1. 先判断其属于运行时设置、部署 Secret 还是正常多记录业务实体。
2. 运行时单组设置在同表增加固定分组记录。
3. 新增固定 Schema、服务方法、专用权限、接口和 Admin Tab。
4. 有图片时登记独立固定媒体槽位和安全策略。
5. 支付渠道列表、邮件模板等多记录生命周期使用正常业务表，不能强塞进单行 JSONB。
6. 敏感凭据需要单独设计加密、密钥轮换和脱敏，不在本阶段预设。

字段规范补充：keywords 对每项执行 Unicode 空白 trim 和 NFC 规范化，移除空项，按规范化后的大小写敏感文本去重并保留首次出现顺序；`name`、`title`、`description` 同样执行 Unicode trim。`SETTINGS_MEDIA_ROOT` 本地默认值固定为 Backend 工作目录下的 `settings-media/`，公开基础路径固定为 `/static/settings`。

### 11. ADR 与当前事实同步

实施时新增 `docs/adr/0013-全局系统设置与配置媒体决策.md`，记录 env、JSON、多表、逐项动态配置与最终单表方案的取舍，以及配置媒体独立于 assets 的长期原因。当前机制进入系统设置架构文档；认证、资产边界、环境变量、容器、生产运维和 PRD 就地更新，不把完整事实复制到规则入口。

## 风险与回滚

| 风险 | 控制 |
| --- | --- |
| JSONB 被错误结构污染 | 固定 Schema、禁止未知字段、Object CHECK、专用写接口 |
| 管理员并发覆盖 | revision、行锁、412、保留草稿 |
| 关闭注册与创建用户竞争 | 注册共享锁、设置排他锁、同事务校验 |
| 数据库故障误开放注册 | capabilities 与 register 均 503，Web Fail Closed |
| 文件替换后数据库失败 | 同卷 staging/trash、原子替换、失败恢复 |
| 提交后旧文件清理失败 | 保持成功配置，Critical 日志和人工清理候选 |
| 伪造图片或解压炸弹 | 大小、Magic、MIME、完整解码、像素、帧数限制 |
| 更换格式残留旧文件 | 固定 basename 并清理其他允许后缀 |
| LOGO 缓存不更新 | URL追加 revision 查询参数 |
| 站点配置故障阻断页面 | Web 仅对展示使用内置品牌回退 |
| 升级后注册状态变化 | 迁移默认关闭并在部署说明中显著记录 |
| Admin 品牌被客户站点覆盖 | Admin 不消费 site-profile，并增加边界回归 |

回滚步骤：

1. 先备份两条设置记录与 settings 媒体目录，不把生产数据写入仓库。
2. 使用完整旧版本回滚 Backend、Admin、Web，并恢复旧版本需要的 `REGISTRATION_MODE`。
3. 确认旧应用不依赖新表后再评估 downgrade；普通应用回滚可保留新表。
4. downgrade 删除配置数据，属于破坏性数据库操作，需要单独备份和授权。
5. 媒体目录默认保留，确认不再需要后列为人工清理候选。
