## 背景与问题

当前 Admin 删除用户后，Repository 默认排除 `deleted_at` 非空记录；删除 Service 还会立即匿名化用户名并清空邮箱、显示名称。因此列表无法查看已删除用户，原身份资料也无法恢复。软删除只有保留可恢复状态并提供明确恢复入口，才能形成完整生命周期。

## 目标

1. 正常用户列表默认排除已删除用户，并增加“回收站”生命周期筛选。
2. 新删除用户保留可恢复身份资料，设置删除时间、操作者和原因，停用账户、提升凭据版本并撤销全部会话。
3. 回收站支持受 `users:restore` 权限控制的单条和批量恢复；恢复后保持停用，管理员另行启用。
4. 默认保留 30 天且可配置；到期后通过默认 dry-run、显式 `--apply` 的受控脚本匿名化，匿名化后永久不可恢复。
5. 已被旧逻辑匿名化的历史用户标记为不可恢复，只允许查看其删除记录。
6. 删除和恢复均使用专用 Backend 端点、固定锁顺序、单事务、显式权限、CSRF 和审计。
7. 同步根 OpenAPI、生成 API Client、Admin 页面、长期文档与变更日志。

## 非目标

1. 不恢复旧版本已清空的用户名、邮箱或显示名称。
2. 不自动启用恢复后的账户，不恢复历史会话或 Refresh Token。
3. 不在应用启动时自动匿名化，不在本次任务执行真实数据库迁移或目标环境权限同步。
4. 不改变管理员、角色、资产和安全日志的既有生命周期规则。
5. 不为软删除或恢复增加二次确认弹窗；统一标准警告弹窗继续只用于物理硬删除。

## 方案设计

### 数据生命周期

1. `User` 增加删除操作者、删除原因和匿名化时间字段；`deleted_at` 继续作为回收站入口。
2. 新软删除保留用户名、邮箱和显示名称，继续占用唯一值，避免恢复时产生身份冲突。
3. 删除时强制 `is_active=false`、提升 `credential_version` 并撤销全部 Web 会话。
4. 恢复时清除删除元数据，保持 `is_active=false`，再次提升凭据版本并保持历史会话失效。
5. 迁移把符合旧匿名化格式或关键身份资料已清空的历史删除用户标记为已匿名化；这些记录不可恢复。

### API 与权限

1. 用户列表增加生命周期参数：`active`、`inactive`、`deleted`、`all`，默认保持当前未删除列表行为。
2. 增加 `POST /api/v1/admin/users/{user_id}/restore`。
3. 增加 `POST /api/v1/admin/users/restore/batch`，每次接受 1 至 100 个唯一 UUID。
4. 新增 `users:restore` 权限，Router 显式声明；目标环境使用前必须执行受控权限目录 `--check/--apply`。
5. 任一批量目标缺失、未删除、已匿名化或不可恢复时整批回滚。

### 到期匿名化

1. 增加 `USER_RECYCLE_BIN_RETENTION_DAYS`，默认 30 天并限定合理范围。
2. 增加独立维护脚本，默认只预览，只有显式 `--apply` 和数据库名确认后才匿名化到期记录。
3. 匿名化用户名为基于 UUID 的不可识别值，清空邮箱和显示名称，写入匿名化时间；不得物理删除用户或安全历史。

### Admin 交互

1. 用户页增加紧凑的生命周期筛选，正常列表与回收站共用现有 ProTable。
2. 回收站显示删除时间、删除原因、可恢复状态；不可恢复历史记录显示明确状态且禁用恢复。
3. 有 `users:restore` 权限时提供单条和批量恢复；成功后清空选择并刷新，失败保留选择。
4. 回收站不提供启停、资料编辑、密码重置、会话和再次删除操作。
5. 软删除和恢复直接提交，不显示标准警告弹窗。

## 风险与回滚

- 迁移只新增可空字段，代码回滚后旧查询仍可运行；真实升级前必须备份数据库并审查迁移。
- 新删除用户在保留期内继续占用用户名和邮箱，属于恢复能力所需约束；到期匿名化后释放邮箱并永久失去恢复能力。
- 旧匿名化数据缺少原身份资料，禁止伪造恢复；迁移显式标记为不可恢复。
- 恢复不启用账户，避免已删除身份在未审查情况下立即获得访问权。
- 新权限未同步时服务端默认拒绝；目标环境必须先运行权限目录检查并经授权应用。
