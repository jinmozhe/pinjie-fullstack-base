## 背景

当前母版提供公开用户注册端点 `POST /api/v1/auth/register`，Backend 已通过 `REGISTRATION_MODE=open|closed` 控制是否允许公开注册。代码默认值为 `closed`，本地示例环境使用 `open` 展示完整注册流程。

Admin 用户管理目前只提供列表、资料编辑、启停、软删除、恢复、密码重置和会话治理。现有权限目录也没有 `users:create`，因此即使派生项目把公开注册设置为 `closed`，管理员仍无法通过管理端创建可登录用户。

## 目标

1. 在 Admin 用户管理中提供受独立权限控制的“新建用户”能力。
2. 管理员创建用户不受公开注册开关影响，不自动创建登录会话。
3. 保留 `REGISTRATION_MODE=open|closed` 作为 Backend 的公开注册权威开关。
4. Web 根据 Backend 公开能力契约决定是否展示注册入口，并在关闭注册时禁止进入注册表单。
5. 新用户继续复用现有用户名、密码、邮箱、启停、软删除、恢复和会话生命周期。
6. 创建操作形成不含密码和邮箱明文的管理员审计记录。

## 非目标

1. 不实现邀请邮件、短信、验证码、一次性注册链接或邮件验证。
2. 不实现首次登录强制修改密码、密码过期或密码历史。
3. 不实现批量导入用户、Excel 导入或批量创建。
4. 不增加组织、部门、租户、会员等级或具体业务画像字段。
5. 不允许 Admin 绕过用户名、邮箱唯一性和密码规则。
6. 不修改用户软删除和长期恢复策略。
7. 不新增 `created_by_admin_id` 等用户表字段，创建来源由不可变审计事件记录。

## 现状分析

### 已有能力

- `Settings.registration_mode` 已接受 `open` 和 `closed`，默认值为 `closed`。
- 公开注册关闭时，`AuthenticationService.register()` 返回 `REGISTRATION_CLOSED` 和 HTTP `403`。
- 公开注册会创建用户、Web Session、Refresh Token 和注册登录事件，并自动登录。
- Admin 已有创建管理员的独立权限、Schema、Service、审计和表单实现，可作为交互与安全模式参考。
- `User` 已包含创建用户所需的用户名、可选邮箱、可选显示名称、密码摘要、启用状态和凭据版本，无需新增数据库字段。

### 缺口

- 缺少 `POST /api/v1/admin/users`。
- 缺少 `users:create` 权限目录项和目标环境权限同步。
- 缺少 Admin 创建用户 Schema、Service 用例、API 适配和表单。
- Web 首页、登录页和 `/register` 当前不会读取 `REGISTRATION_MODE`，关闭注册后仍会显示注册入口，直到提交时才收到 `403`。
- 当前公共系统状态只返回可用性，没有公开可消费的注册能力摘要。

### 不能直接复用公开注册 Service 的原因

Admin 创建用户与公开注册具有不同业务语义。直接调用 `AuthenticationService.register()` 会错误套用公开注册开关和注册限流，并创建 Web Session、Refresh Token、登录 Cookie 所需产物及注册登录事件。Admin 创建应只创建账户和审计记录，因此使用独立的 `AdminManagementService.create_user()` 用例，并复用现有用户名规范化、密码策略、密码哈希和 Repository 约束。

## 方案设计

### Backend 管理端创建用户

1. 新增 `AdminUserCreateIn`：
   - `username`：必填，复用现有 3 至 50 位规范化规则。
   - `initial_password`：必填，6 至 64 个字符。
   - `display_name`：可选，最多 100 个字符。
   - `email`：可选，最多 320 个字符，规范化为小写；继续标记为未验证联系资料。
   - `is_active`：可选，默认 `true`。
2. 新增 `POST /api/v1/admin/users`，成功返回 HTTP `201` 和 `AdminUserRead`。
3. Router 同时声明管理员 CSRF 和独立 `users:create` 权限。
4. `AdminManagementService.create_user()` 在密码哈希完成后，通过 `AuditCoordinator` 在单一数据库事务中：
   - 检查用户名和邮箱是否已被任何现存或软删除用户占用。
   - 创建 UUID v7 用户，设置 `credential_version=1`，不创建 Session 或 Refresh Token。
   - 记录 `users:create` 审计事件；`changed_fields` 只记录 `created`、`is_active` 和是否填写可选资料，不记录密码、密码摘要或邮箱明文。
5. 数据库唯一约束继续处理并发冲突，统一映射为 HTTP `409` 安全错误。
6. 软删除用户继续占用用户名和邮箱。遇到冲突时引导管理员恢复原账户，禁止创建同标识的新账户。

### 权限目录

1. 新增 `PermissionCode.USERS_CREATE = "users:create"`。
2. 在 `PERMISSION_CATALOG` 中增加“创建用户”，并更新目录版本。
3. 更新权限目录一致性检查和受影响契约测试。
4. 代码交付后只执行 `scripts.sync_permissions --check`。目标环境的 `--apply`、角色授权和发布部署继续分别取得明确授权，应用启动不自动修改权限表。

### Admin 交互

1. 在用户列表工具栏增加带 `PlusOutlined` 的“新建用户”主按钮，只对 `users:create` 权限可见。
2. 使用现有 Ant Design 表单体系提供创建弹窗，字段为用户名、显示名称、邮箱、初始密码、确认初始密码和“允许登录”。
3. 确认密码只用于前端一致性校验，不进入 API 请求契约。
4. 提交期间禁用重复提交；成功后关闭并重置表单、刷新用户列表并显示成功反馈；失败时保留输入并展示统一错误。
5. 创建成功后不显示或复制密码，避免凭据在页面反馈、日志或审计中二次暴露。
6. 保留用户列表全部既有筛选、批量操作、回收站、操作列宽度和不换行样式。

### 公开注册开关联动

1. 保留 `REGISTRATION_MODE`，不增加第二套 Web 侧注册开关。
2. 新增只读公共端点 `GET /api/v1/system/capabilities`，返回最小白名单字段 `registration_enabled: boolean`。不公开环境变量名称、内部配置或安全信息。
3. Web Server Component 通过内部 Backend 地址读取能力；读取失败时按“未知且不开放”处理，不渲染注册表单。
4. 当 `registration_enabled=true`：
   - 首页保留“创建账户”。
   - 登录页保留“立即注册”。
   - `/register` 正常展示注册表单。
5. 当 `registration_enabled=false`：
   - 首页和登录页隐藏全部注册入口。
   - 直接访问 `/register` 时服务端重定向到 `/login`。
   - Backend 公开注册端点继续返回 `403 REGISTRATION_CLOSED`，服务端行为不依赖前端隐藏。
6. 当能力查询失败时，首页和登录页隐藏注册入口；直接访问 `/register` 显示明确的服务不可用状态，不把未知状态误判为永久关闭。

### 契约与兼容

1. 先实现 Backend Schema 和 Router，再导出根 `openapi.json`。
2. 运行 `pnpm generate-api` 生成 `AdminUserCreateIn`、公共能力类型和 SDK。
3. Admin 和 Web 只消费生成类型，不复制 DTO。
4. 本次只新增端点、权限和字段，不移除或收紧既有公开契约；仍需运行 OpenAPI Breaking Change 检查。

## 风险与回滚

### 风险

1. 新权限未同步或未分配时，非超级管理员不会看到创建入口并会被 Backend 拒绝。
2. Admin 初始密码由管理员知晓，安全性低于一次性邀请或用户自设密码；必须通过安全渠道交付，且不能进入日志和审计。
3. Web 与 Backend 能力查询失败时如果默认开放，会短暂暴露无效注册入口，因此必须失败关闭并提供明确不可用状态。
4. 软删除账户仍占用用户名和邮箱，管理员可能误以为可以重新创建；冲突提示必须引导检查回收站。
5. API Client 生成或 Web Server Component 边界处理错误可能造成类型漂移或错误的开放状态。

### 回滚

1. 数据库结构不变化，代码发布前可以整体撤销本计划变更。
2. 已创建用户属于正常用户数据，回滚代码不能自动删除账户；需要按现有停用或软删除流程处理。
3. 已进入共享环境后，不直接删除已公开的 API 和权限代码；优先前向修复，必要时通过权限撤回关闭 Admin 创建入口。
4. Web 注册联动异常时，Backend 的 `REGISTRATION_MODE=closed` 仍是最终拒绝边界。
