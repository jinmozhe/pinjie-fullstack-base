# CNB 三端独立镜像构建与发布证据改造计划

## 当前状态和结果

- 状态：实施中
- 结果：不适用
- 当前范围：只改造 CNB 的 Backend、Web、Admin 独立镜像构建、扫描、发布和证据链，并同步人工 1Panel 部署说明。
- 授权边界：用户已确认方案并授权本地实施和轻量验证；Git 提交、推送、Full Validation、CNB 发布和生产部署尚未授权。

## 关联需求

- `BASE-OPS-005`：继续提供 Backend、Web 和 Admin 三张独立生产镜像，镜像内不包含真实密钥。
- `BASE-OPS-006`：保持按固定镜像 digest 升级、健康检查和回滚的可执行边界。
- `BASE-OPS-007`：继续分离 GitHub 验证、CNB 镜像发布和生产部署授权。
- `BASE-OPS-008`：变更路由、构建、扫描、证据或不可变标签校验无法证明成功时必须停止。
- `BASE-OPS-009`：每张镜像独立绑定完整 Commit SHA、SBOM、构建来源证明和 digest。
- `BASE-SEC-001`：CNB Token、TCR 用户名、固定密码和生产凭据不得进入仓库、镜像或日志。
- `BASE-SEC-004`：镜像发布、生产部署和回滚继续分别取得明确授权。
- `BASE-SEC-005`：拆分流水线后不得弱化 Trivy、SBOM 和 provenance 供应链门禁。
- `BASE-SEC-006`：每端发布证据必须关联源码 Commit、CNB Build 和 TCR digest。
- `BASE-QUAL-001`：跳过、失败和无法可靠判断变更必须明确记录，禁止伪装成完整发布。
- `BASE-QUAL-002`：保留现有三个应用的 Dockerfile、运行配置、健康检查和发布安全能力。
- `BASE-QUAL-004`：任一外部依赖、镜像校验或证据错误必须显式传播。
- `BASE-DOC-003`：同步 ADR 0008 中的构建时间、发布单元和证据决策。
- `BASE-DOC-004`：通过本计划追踪跨流水线改造、确认、验证和回滚。
- `BASE-DOC-006`：保持发布、部署和回滚文档与实际 CNB、TCR、1Panel 流程一致。

## 背景

当前 CNB `main.push` 只有一条 Pipeline，顺序构建 Backend、Web 和 Admin。任一应用发生变化时，三个镜像都会重新构建、扫描、生成 SBOM 和 provenance，最后统一生成 `pinjie-cnb-tcr-release-v1` 三镜像发布清单。

现有方案已经验证不可变 SHA 标签、候选标签、TCR Registry 缓存、Trivy 阻断、失败附件和写后 digest 复核，但三个应用被绑定成同一个构建单元。只修改单端仍会占用另外两端的构建额度和时间。

当前构建还固定 `SOURCE_DATE_EPOCH=0`。它有利于不同 Commit 之间复用稳定文件时间戳，但会让 OCI 镜像创建时间显示为 Unix Epoch，1Panel 因此显示 `1970-01-01 08:00:00`。用户确认接受改用 Git Commit 时间，并将三端分别构建后，不要求三张镜像具有相同创建时间。

CNB 官方语法支持在同一事件下声明多个 Pipeline，并支持 Pipeline 级 `ifModify`。官方同时明确：新建分支 Push 无法统计上一提交、单次最多统计 300 个变更文件，超限时可能漏掉匹配。因此按路径构建必须同时提供显式全量构建入口和无法可靠判断时的 Fail Closed 规则。

## 目标

1. 将 CNB `main.push` 拆成 Backend、Web、Admin 三条相互独立的镜像 Pipeline。
2. 每条 Pipeline 只在自身镜像构建输入发生变化时运行，并允许三条 Pipeline 并行执行。
3. 每端独立完成候选构建、Trivy 阻断、CycloneDX SBOM、BuildKit provenance、不可变 SHA 标签发布和写后 digest 复核。
4. 将三镜像聚合证据改为单镜像证据，使每个 TCR digest 都能独立追溯源 Commit、CNB Build 和安全门禁。
5. 把 `SOURCE_DATE_EPOCH` 改为当前 `CNB_COMMIT` 的 Git committer time，使同一 Commit 重建使用稳定时间，并让 1Panel 显示可读的镜像创建时间。
6. 保留 TCR 个人版作为唯一生产镜像源，保留 `sha-<完整 Commit SHA>` 标签和生产按 digest 部署的规则。
7. 保留现有 GitHub Full Validation 和固定 SHA 源码交接门禁，不在本计划中降低完整验证要求。
8. 继续采用人工 1Panel 生产部署，不引入 SSH 自动部署。
9. 为首次运行、超过 300 个变更文件、变更基线不可用和路由规则变化提供显式三端全量构建入口。

## 非目标

- 不拆分或缩减 `.github/workflows/ci-e2e.yml` 的 pytest、Vitest、production build 和 Playwright Full Validation。
- 不修改 Full Validation Artifact 格式，不允许用未经校验的历史前端构建产物替代当前验证。
- 不启用 `.github/workflows/deploy-production.yml`，不把当前 GHCR 自动部署流程改造成生产入口。
- 不向 GHCR 发布新镜像，生产镜像继续只发布到腾讯云 TCR。
- 不自动连接生产服务器，不执行 1Panel 编排更新、数据库迁移、容器替换或生产冒烟。
- 不修改 Backend、Web、Admin 业务源码、OpenAPI、API Client、数据库模型或 Alembic 迁移。
- 不修改 `compose.prod.yml`、生产 `.env` 或 `apps/backend/.env`。
- 不删除现有 TCR 镜像、候选标签、SHA 标签、CNB Build 附件或历史发布记录。
- 不承诺不同 Commit 的镜像具有相同文件时间戳或相同 digest。

## 现状分析

- `.cnb.yml` 当前使用一个全局锁和一条顺序 Pipeline，正常附件固定要求 Backend、Web、Admin 三套证据同时存在。
- `scripts/ci/cnb-publish-images.sh` 的 `image_specs` 固定返回三个应用，`build` 和 `finalize` 都会遍历三端。
- `scripts/ci/cnb-scan-images.sh` 固定遍历三个 digest 文件并对三端执行扫描和 SBOM。
- `scripts/ci/create-cnb-release-evidence.mjs` 和 `check-cnb-release-evidence.mjs` 固定要求 `images` 精确包含三个应用。
- `scripts/ci/test-cnb-release-evidence.mjs` 和 `test-cnb-scan-images.mjs` 的夹具建立在三端同一证据目录和同一发布清单上。
- GitHub `Handoff Source to CNB` 已要求完整 Commit SHA、默认分支祖先、四个轻量 Push Run、同 SHA Full Validation Artifact 和三个应用 `ready`，本计划继续沿用。
- Web 和 Admin Dockerfile 都使用根目录作为构建上下文，并复制根依赖文件、两个前端的 `package.json`、`packages/**` 和 `patches/**`。当前路径路由必须反映这些真实输入。
- Backend Dockerfile 只复制 `apps/backend/**` 中明确列出的依赖、迁移、应用和脚本，不消费前端或 API Client 文件。
- `compose.prod.yml` 只决定运行期镜像引用、网络、环境、端口、存储卷和健康依赖，不是三张镜像的 Docker 构建输入。
- 当前生产通过 1Panel 人工使用 TCR 完整 digest 更新，GitHub 自动部署保持关闭。

## 方案设计

### 1. 独立发布单元

Backend、Web、Admin 各自成为一个发布单元。每个发布单元拥有独立的：

- CNB Pipeline 名称和按应用区分的锁。
- 允许的 `IMAGE_KEY`、Dockerfile 和 TCR 仓库映射。
- `buildcache-main` Registry 缓存。
- `candidate-<CNB Build ID>` 唯一候选标签。
- `sha-<完整 CNB_COMMIT>` 不可变标签。
- digest、metadata、Trivy、SBOM、发布清单和失败附件。

脚本必须只接受 `backend`、`web`、`admin` 三个固定键之一，并在内部映射 Dockerfile 和仓库名。禁止把任意外部字符串直接拼成 Dockerfile 路径或镜像仓库。

### 2. CNB Pipeline 结构

`.cnb.yml` 的 `main.push` 改为三个具名 Pipeline：

- `backend-image`
- `web-image`
- `admin-image`

每条 Pipeline 保留固定 AMD64 Runner、Docker 服务、固定 digest 构建环境、受限 TCR 密钥导入和凭据清理。锁键按应用拆分，例如 `pinjie-fullstack-base-tcr-backend-main`，让不同应用可以并行，相同应用的多个发布继续串行。

每条 Pipeline 的阶段保持相同顺序：

1. 校验 CNB 仓库、分支、Commit、Build ID、TCR 地址和应用键。
2. 从 Git Commit 计算和校验构建时间。
3. 构建并推送该端唯一候选镜像。
4. 核对候选 digest、OCI index、SBOM attestation 和 provenance metadata。
5. 对该候选执行 Trivy High/Critical 阻断并生成 CycloneDX JSON SBOM。
6. 检查该端 SHA 标签是否冲突，成功后创建或幂等确认标签。
7. 写后再次核对标签 digest。
8. 生成并校验该端发布证据。
9. 保存该端成功附件；失败时保存该端失败证据。
10. 无论成功或失败都清理临时 Docker 登录配置。

`ifModify` 必须覆盖真实 Docker 构建输入和发布基础设施。初始规则如下：

| `apps/web/**` 中除 `package.json` 外 | 跳过 | 构建 | 跳过 | Web 应用源码和 Dockerfile |
| `apps/admin/**` 中除 `package.json` 外 | 跳过 | 跳过 | 构建 | Admin 应用源码、Nginx 配置和 Dockerfile |
| `apps/web/package.json` | 跳过 | 构建 | 构建 | 两个前端 Dockerfile 当前都复制该文件 |
| `apps/admin/package.json` | 跳过 | 构建 | 构建 | 两个前端 Dockerfile 当前都复制该文件 |
| `package.json` | 跳过 | 构建 | 构建 | 两个前端的根依赖输入 |
| `pnpm-lock.yaml` | 跳过 | 构建 | 构建 | 两个前端的锁定依赖输入 |
| `pnpm-workspace.yaml` | 跳过 | 构建 | 构建 | 两个前端的 Workspace 安装输入 |

### 4. 无法可靠判断变更时的处理

CNB 自动按路径构建只用于已有 `main` 分支、变更统计可靠且不超过平台限制的 Push。以下情况必须进入显式三端全量构建：

- CNB `main` 首次建立或缺少可比较的前一 Commit。
- 一次 Push 的变更文件超过 CNB 官方统计上限 300。
- Git 历史深度不足、前一 Commit 不可达或变更检测报错。
- `.cnb.yml`、路径路由契约、构建发布脚本或证据脚本发生变化。
- 操作人员对影响范围存在疑问。

`.cnb.yml` 增加人工触发的三端全量构建入口。该入口只允许 CNB 当前受控 `main`，复用三条单端发布实现，不接收任意仓库、分支、镜像名或未经校验的 Commit 输入。

自动 Pipeline 被 `ifModify` 跳过只表示该端没有命中构建输入，不能记录为该端发布成功。完整发布资格只能来自实际执行并通过的单端证据。

### 5. Git Commit 构建时间

构建前在确认 `git rev-parse HEAD` 等于 `CNB_COMMIT` 后执行等价逻辑：

```bash
SOURCE_DATE_EPOCH="$(git show -s --format=%ct "$CNB_COMMIT")"
export SOURCE_DATE_EPOCH
```

脚本必须要求结果为正整数，并生成 UTC ISO 8601 时间用于 OCI 标签和证据。每张镜像增加标准 OCI 元数据：

- `org.opencontainers.image.revision=<完整 Commit SHA>`
- `org.opencontainers.image.created=<Commit UTC 时间>`
- `org.opencontainers.image.source=<权威 GitHub 仓库 URL>`

同一 Commit 多次构建将得到相同 `SOURCE_DATE_EPOCH`。不同 Commit 使用各自提交时间。该设置用于可读创建时间和同 Commit 时间稳定性，不承诺镜像 digest 仅由时间值决定。

### 6. 单端构建、扫描和 Finalize

重构现有脚本，使 `validate`、`build`、`scan`、`finalize` 和 `cleanup` 都以固定 `IMAGE_KEY` 为边界。现有安全行为必须完整保留：

- 使用完整小写 40 位 `CNB_COMMIT`。
- 构建前拒绝已存在的唯一候选标签。
- 使用 `linux/amd64`、最大级别 BuildKit provenance 和 SBOM attestation。
- 使用对应 TCR 仓库的 `buildcache-main`。
- 从 Buildx metadata 读取 digest，并与候选标签及 OCI index 三方核对。
- Trivy 阻断存在修复版本的 High 和 Critical 漏洞。
- SHA 标签已指向不同 digest 时失败，禁止覆盖。
- SHA 标签不存在时从精确候选 digest 创建，存在且相同时幂等通过。
- 失败附件不得包含 TCR 凭据或 Docker 配置目录。

### 7. 单镜像发布证据

新增单镜像证据 Schema，例如 `pinjie-cnb-tcr-image-v1`。每份清单至少包含：

- `image_key`
- `source_commit_sha`
- `source_commit_epoch`
- `source_commit_time`
- CNB repository、branch、pipeline、Build ID、Build URL、开始时间和结束时间
- TCR registry、namespace、repository
- 完整 digest 引用和不可变 SHA 标签
- Trivy、CycloneDX SBOM 和 BuildKit provenance 状态
- OCI revision、created 和 source 元数据

校验器必须使用精确字段集合，拒绝未知应用键、错误仓库、错误 Commit、错误 Build ID、非法时间、非法 digest、缺少扫描结果、缺少 SBOM 或缺少 provenance。

旧 `pinjie-cnb-tcr-release-v1` 保留在 Git 历史和既有 CNB 附件中，不修改历史文件。新发布只生成新 Schema，运维文档明确两种历史证据的读取边界。

### 8. 多端同时变更的发布门禁

独立构建允许各端并行完成，但同一 Commit 同时影响多个应用时，发布操作仍需保持兼容性门禁：

1. 根据路径影响契约得到该 Commit 的预期影响端集合。
2. 等待预期集合中的每条 Pipeline 全部成功。
3. 核对每份证据的 `source_commit_sha` 完全相同。
4. 任一预期端失败、缺失或被错误跳过时，该 Commit 不能进入人工生产部署。
5. 只有单端受影响时，允许只使用该端的成功证据和 digest 更新生产。

这条规则只约束同一次代码变化需要共同验证的应用。生产环境允许 Backend、Web、Admin 分别运行来自不同 Commit 的已验证 digest，并必须分别记录版本。

### 9. 人工 1Panel 部署和版本记录

生产继续使用 1Panel 人工操作：

1. 从该端成功 CNB Build 附件读取并校验单镜像发布证据。
2. 在 TCR 核对 `sha-<Commit>` 标签解析出的 digest 与证据一致。
3. 在服务器根 `.env` 中只更新目标端的完整 `@sha256:<digest>` 镜像引用，保留其他两端现有 digest。
4. 使用 Compose 配置检查确认三个镜像变量和共享基础设施网络有效。
5. 通过 1Panel 更新编排；若要求严格只重建单端，则使用现有 Compose 文件执行目标服务的 `up -d --no-deps --wait`。
6. 核对目标容器实际 `.Config.Image`、健康状态、Backend ready、Web HTTP 和 Admin healthz。
7. 分别记录 Backend、Web、Admin 的 Commit、digest、CNB Build ID、证据引用和部署时间。

服务器上的可编辑版本记录用于运维查询，不能替代 CNB 不可变构建附件、TCR digest 和受保护 Git 历史。

### 10. 权限与并发

- GitHub 到 CNB 的固定 SHA 交接权限保持不变。
- 三条 Pipeline 继续只从现有受限密钥仓库读取同一 TCR Publisher 凭据。
- 每条 Pipeline 只写自己的 TCR 仓库、缓存标签、候选标签和 SHA 标签。
- 按应用拆分锁，同一应用禁止并发覆盖候选流程，不同应用允许并行。
- TCR 个人版缺少服务端不可变保证，写前冲突检查和写后 digest 复核继续作为强制门禁。
- 生产服务器继续只保存 TCR Puller 凭据，不获得镜像写权限。

| 范围 | 是否涉及 | 工作内容 | 前置依赖 | 验证 |
| --- | --- | --- | --- | --- |
| Backend | 不涉及 | 不修改后端源码；仅把其 Dockerfile 作为独立构建输入 | 现有 Backend Dockerfile | 路径路由夹具、CNB Backend 真实构建 |
| Admin | 不涉及 | 不修改管理端源码；仅把其 Dockerfile 和依赖作为独立构建输入 | 现有 Admin Dockerfile | 路径路由夹具、CNB Admin 真实构建 |
| Web | 不涉及 | 不修改用户端源码；仅把其 Dockerfile 和依赖作为独立构建输入 | 现有 Web Dockerfile | 路径路由夹具、CNB Web 真实构建 |
| API Client | 不涉及 | 不修改生成契约；其路径变化触发 Web 和 Admin | 当前前端消费关系 | 路由夹具核对两个消费者 |
| Database | 不涉及 | 无数据库模型、迁移、数据或共享 PostgreSQL、Redis 变化 | 无 | 不适用 |

## 实施顺序

1. 用户确认本计划的范围、非目标、路径矩阵、单镜像证据和多端发布门禁。
2. 为单端应用键、路径路由、Commit 时间和证据 Schema 增加失败优先的自动夹具。
3. 重构 `cnb-publish-images.sh`，使校验、构建和 Finalize 每次只处理一个固定应用。

## 风险与回滚

- **路径漏判**：遗漏真实 Docker 输入会跳过必要构建。路径矩阵必须来自 Dockerfile COPY 和依赖事实，使用自动夹具核对；无法证明时执行三端全量构建。
- **CNB 300 文件限制**：超限可能导致 `ifModify` 漏判。此类发布不得直接进入生产，必须使用人工全量入口。
- **多端部分成功**：多个受影响端并行时可能只有部分 Pipeline 成功。全部预期端成功前禁止部署该 Commit 的任一新镜像。
- **证据弱化**：拆分后可能遗漏原三镜像清单中的字段。新 Schema 逐字段映射原能力，并增加错误应用、错误 SHA、错误 Build、错误 digest、缺失扫描、缺失 SBOM 和缺失 provenance 负向夹具。
- **不可变标签冲突**：相同应用的 `sha-<Commit>` 已指向其他 digest 时必须失败，不覆盖、不删除。
- **构建时间改变缓存**：Git Commit 时间会使不同 Commit 的输出时间戳变化，可能降低已验证的跨 Commit COPY 层命中率。通过单端按需构建控制总成本，并用真实连续 Run 记录缓存差异，禁止虚报优化比例。
- **1Panel 时间语义误解**：1Panel 显示 OCI 镜像创建时间，不代表服务器拉取时间。运维文档明确两种时间的区别。
- **混合版本兼容性**：生产三端可能来自不同 Commit。Backend 契约变化仍受 Breaking Change、Full Validation 和多端影响集合约束；不兼容变化必须按同一受控迁移计划共同部署。
- **并行凭据使用**：三条 Pipeline 会并发使用同一 TCR Publisher。每条构建使用独立临时 Docker 配置和按应用锁，结束时独立清理。
- **回滚代码**：通过普通反向提交恢复上一版单 Pipeline、三镜像脚本和证据 Schema，禁止改写 Git 历史。
- **回滚镜像**：现有 TCR digest、旧 `pinjie-cnb-tcr-release-v1` 附件和已部署 digest 全部保留，可按原完整 digest 恢复，不重新构建旧代码。
- **回滚生产**：人工把目标端镜像变量恢复为上一个已验证 digest，再只重建目标端并完成健康检查。数据库没有变化，无数据库回滚步骤。
