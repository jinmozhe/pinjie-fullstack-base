## 背景

生产服务器使用与仓库一致的 `compose.prod.yml` 更新 1Panel 编排时，三个应用容器已经按 TCR 完整 digest 创建并通过健康检查，但 1Panel 的镜像预拉取步骤把 `${BACKEND_IMAGE:?提示}` 当作镜像名称原文，最终将任务标记为失败。Docker Compose 命令行可以正确处理该必填变量语法，1Panel 当前 Web 编排的镜像预处理与该语法不兼容。

## 目标

1. 让四个应用服务的镜像字段兼容 1Panel Web 编排预处理。
2. 保留根 `.env` 作为三张不可变镜像引用的单一部署输入。
3. 保持生产配置门禁对变量名称、完整 digest、网络隔离和日志策略的验证。
4. 记录真实生产健康检查与 1Panel 任务状态不一致的事实。

## 非目标

- 不修改 Backend、Admin、Web 业务源码或公开 API。
- 不修改数据库模型、迁移或已完成的生产数据库初始化。
- 不重新发布镜像，不连接服务器，不重启或删除线上容器。
- 不把真实镜像 digest、密码或生产 `.env` 写入仓库。
- 不在本次修复中改变用户临时采用 Redis `default` 用户与 DB 1 的线上选择。

## 现状分析

- 四个 `image` 字段使用 `${VAR:?提示}`，Docker Compose 支持该必填语法。
- 1Panel 更新日志证明其镜像预处理没有正确展开该形式，并向 Docker 传入了包含 `${BACKEND_IMAGE` 的无效引用。
- 线上三个应用容器仍成功启动，Backend、Web、Admin 均为 `healthy`；Backend Readiness 返回数据库、设置媒体和 Redis 全部 `ok`。
- Backend 脱敏环境检查确认连接 `postgresql:5432/pinjie_fullstack_prod` 与 `redis:6379/1`。
- `WEB_PUBLIC_ORIGIN` 不参与镜像预拉取，可以继续保留 Compose 必填表达式。

## 方案设计

- 四个应用镜像字段改用 Compose 基础插值 `${BACKEND_IMAGE}`、`${WEB_IMAGE}` 和 `${ADMIN_IMAGE}`。
- 不在 Compose 中硬编码生产 digest，避免仓库随每次发布产生环境值提交。
- 缺失镜像变量时，Compose 因服务缺少有效 `image` 或镜像引用无效而失败；仓库门禁继续要求准确变量名，并在变量存在时验证完整 `@sha256:` digest。
- `WEB_PUBLIC_ORIGIN` 继续使用 `${WEB_PUBLIC_ORIGIN:?WEB_PUBLIC_ORIGIN must be set}`，保留明确必填错误。
- 调整生产门禁正反向夹具，以错误变量名替代旧的“非必填变量”负向场景。

## 风险与回滚

- 基础插值不再提供自定义缺失变量提示，但缺失或空镜像仍会使 Compose 明确失败，生产门禁继续验证变量名和 digest。
- 1Panel 的环境变量来源必须包含根 `.env` 中四个公开部署值；未加载时编排会失败，不能使用可变标签兜底。
- 回滚只需恢复四个镜像字段及门禁期望值，不涉及数据库、容器数据或公开契约。
